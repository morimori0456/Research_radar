# OpenART: Scaling Agent Red Teaming via Open-Ended Environment Evolution

**topic:** sns_wildcard (EXPLORE 枠・本日唯一) ・ **arXiv:** 2608.00677 ・ **published:** 2026-07-31 ・ **hf_upvotes: 252**

> **wildcard 枠を使う理由:** 分野は LLM エージェントの安全性で、運転とは無関係に見える。**だが実験プロトコルの形が、P1 の closed-loop 評価が抱えている問題とそのまま同型である。**
>
> **主張を一行で:** **タスクの目標は固定したまま、環境の状態だけを進化させて失敗を探す。** そして **環境が複雑になるほど、この探索の優位が広がる (単純環境で +2% → 最も複雑な環境で +17% 超)。**
>
> **P1 への含意はこれ以上ないほど直接的だ —— 固定シナリオ集で測った失敗率は、体系的に過小である。**

## 何を解決する論文か

AI エージェントは **persistent environment (状態が残り続ける環境)** で動く。**初期に起きた小さな状態変化が、遠い先の判断に影響する。** 通常の言語モデルとの一問一答と違い、エージェントの振る舞いは**共有された状態**を介して、長い作業の中で繰り返し書き換えられ再利用される。

**既存の安全性ベンチマークは、短く静的なタスクに寄っているので、この累積的なリスクを捉えられない。** OpenART は **red teaming (攻撃者の視点からシステムの弱点を能動的に探す作業)** を、**環境そのものを進化させる**形でスケールさせる。

規模は **50 ドメイン・10,000 以上の検証済み状態付きシナリオ**、**50 万以上のツール/スキルのプール**から構成され、**1 タスクあたりツール呼び出しが中央値 97 回**。**75 種類のエージェント構成**を同じ土俵で評価する。

## 手法の核心

- **EMHA (Evolutionary Markov Hypergraph Attack) —— black-box で、パラメータ更新を一切しない。** 対象モデルの内部にも勾配にもアクセスしない。**環境の状態遷移を組み合わせて、失敗を引き出す状態へ環境を進化させる**方策である。**hypergraph (通常のグラフが 2 頂点を結ぶのに対し、1 本の辺が任意個数の頂点を束ねられるグラフ。「複数の要素が同時に関与する状態遷移」を表すのに向く)** で状態空間を表現している。

- **設計上の最重要点: 遷移は "authorized" なものに限る。** **環境の正規の操作だけを使って状態を作る。** これにより **発見された失敗は「あり得ない入力を無理やり食わせた結果」ではなく、正当に到達しうる状態での失敗**になる。**外挿的なノイズで壊すのは簡単で、価値がない** —— この制約こそが本手法を評価手法として意味あるものにしている。

- **タスクの目標は固定し、変えるのは環境の状態だけ。** 評価の交絡を切る、きれいな実験設計。**「難しいタスクを与えたから失敗した」のではなく、「同じタスクなのに環境状態のせいで失敗した」**が言える。

- **結果: 全構成をプールした ASR (Attack Success Rate; 攻撃成功率) が 85.0%。** そして **本論文で最も重要な数字は 85.0% ではない** —— **指示文だけを進化させる手法に対する優位が、単純な環境での約 2% から、最も複雑な環境では 17% 超へ広がる**という点である。**環境の複雑さが上がるほど、環境を動かす探索でしか見つからない失敗が増える。**

## 追っているプロジェクトへの適用可能性

- **P1 / R1 —— 「固定シナリオ集での評価は失敗率を過小報告する」という主張に、他分野からの定量的な裏付けが 1 つ付いた。最重要。** nuScenes や NAVSIM は**固定されたシーン集合**であり、シナリオを能動的に進化させない。**本論文の複雑さスケーリング (2% → 17%) が運転でも成立するなら、シーンが混雑するほど固定集合の甘さが広がる**ことになる。**これは R1 が「評価手法の新規性」を主張するときの土台として使える** —— しかも **我々の分野の外からの独立した証拠**なので、査読で「自分の都合のよい引用」と言われにくい。

- **P1 —— プロトコルがそのまま輸入できる。** 「**目標を固定し、admissible な編集だけで環境を進化させる**」は運転シミュレーションに逐語的に移る: **経路と目的地は固定し、他車の初期位置・速度・行動パラメータを、交通規則と物理制約の範囲内でのみ進化させる。** **「authorized transitions のみ」という制約が、"物理的・法的に起こりうるシナリオのみ" に綺麗に対応する** —— ここが噛み合っているので、輸入コストが低い。

- **P1 —— 指標の形も持ち帰れる。** 本論文は **失敗率を「探索予算の関数」として**報告する構造になっている。**単一の数値ではなく曲線**である。**本日の FIRE-VLA の「evaluation-persistent failure prevalence」と組み合わせると、「どれだけ探せば、どれだけ失敗が残るか」という R1 向きの指標の形が見えてくる。**

- **P2 / P3 への波及は薄い。** 蒸留にもアーキテクチャにも直接は繋がらない。

- **留保 (この枠は特に厳しく読む):** (1) **ドメインが完全に違う。** LLM エージェントのツール呼び出しと、車両の物理的な相互作用では、状態空間の性質が異なる。**移植できるのはプロトコルであって、結果ではない。** (2) **ASR 85.0% は著者自身が構築したアリーナ上の自己申告値**で、外部の追試は無い。**「プールした」値なので、構成ごとのばらつきも見えない。** (3) **物理ドメインへの転移の証拠はゼロ。** (4) red teaming は「見つけた失敗が現実的にどれだけ起きるか」を答えない —— **発見率が上がることと、実運用のリスクが定量化できることは別。** R1 が保証を語るなら、この差は埋める必要がある。

### 試すべき実験

1. **「目標固定・環境進化」プロトコルを closed-loop 運転シムで最小構成で回す (最優先)。** ルートとゴールを固定し、**他車パラメータを admissible な範囲で進化させる**探索と、**ランダムサンプリング**を、**同じシナリオ生成数**で比較する。**測るのは 1 つ: 単位予算あたりの失敗発見数。** 差が出れば R1 の実験節が 1 つ埋まる。

2. **複雑さスケーリングを運転で検証する —— これが本命で、単独で結果になる。** シナリオの密度 (周辺車両数・交差点の複雑さ) を段階的に上げ、**進化的探索とランダムの優位差がどう変化するかを引く。** 本論文の 2% → 17% に相当する曲線が運転でも出れば、**「固定シナリオ集は混雑場面で特に甘い」という定量的な主張**になり、**これは R1 の新規性そのものになりうる。**

3. **admissible 制約の定義を先に固める。** 「物理的に可能」「交通規則に違反しない」「他車が非合理な自爆をしない」の 3 条件を明示的に書き下す。**ここが緩いと発見された失敗が「そんなの起きない」で片付けられ、実験全体が無価値になる。** 実装前にやる作業。

4. **予算-失敗率曲線として報告する形式を試す。** 単一の失敗率ではなく、**探索予算を横軸にした曲線**で planner を比較する。**曲線が交差するなら「どちらが安全か」は予算に依存する**ことになり、**それ自体が評価手法上の指摘になる。**
