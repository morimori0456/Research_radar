# Where Is VLA Inference Time Spent? Bottlenecks and Optimization Interactions Across GPUs (2611.06710)

- トピック: next_arch に分類 → P1 (VLA 型 planner の実機展開) として採用 / プロジェクト: P1 (P3 にも関連) / スコア 4.0
- URL: https://arxiv.org/abs/2611.06710

## 何を解決する論文か

VLA (Vision-Language-Action; 画像と言語から行動を出す model) は backbone が大きく、行動生成も繰り返すため、推論がロボット (車) の次の行動の締め切りに間に合わないことがある。量子化・枝刈りなどの高速化手法は多数あるが、報告は 1 種類の GPU・数個の model に限られ、**ボトルネックが何で、手法を組み合わせると何が起きるか**が分かっていない。この論文は測定でそれを埋める。

## 手法の核心

- 7 つの VLA family 、4 種類の GPU (datacenter の H100 から embedded の Jetson Thor まで) で、7 系統の高速化手法 (CUDA graphs、compilation、token pruning、quantization など) を測る measurement study。
- CPU の kernel launch overhead (GPU に仕事を投げるまでの CPU 側の遅延)、メモリ帯域、kernel 効率が、手法ごとの効果をどう決めるかを分析する。
- 1 つの手法を適用すると、別の手法の効き目が変わる (相互作用) ことを示す。
- そこから VLA-Triage という指針を導く。latency 予算の下で手法を積む順序、どの段階で必要な削減が得られるか、どの組み合わせを実際の実行 mode で再検証すべきかを示す。

## 適用可能性 (P1 / P3)

- 手元の実機が Jetson Thor なので、**「どの手法がこの GPU で効くか」の一次情報**になる。昨日の LoopQ (量子化は Thor で速くならない) と同じ系統の知見で、組み合わせの相互作用まで見ている点が新しい。
- 結論の数字 (どれだけ速くなるか) は abstract に無いので、論文本文で Thor の行を確認する価値がある。
- 注意: 対象は VLA の manipulation 系が中心とみられ、運転用 planner の構造 (複数カメラ、長い履歴) では比率が変わる可能性がある。

## 試すべき実験アイデア

1. 手元の VLA 型 model を Thor で eager mode と CUDA graphs で動かし、1 回の推論の GPU 時間と CPU launch 時間を分けて測る (最小の確認)。
2. CPU 側が律速なら compilation / CUDA graphs を先に、メモリ帯域が律速なら量子化を先に、という VLA-Triage の順序を 1 つの model で検証する。
3. token pruning と量子化を同時に入れ、片方だけの効果の和と実測が合うか (相互作用の大きさ) を見る。

## 注意

abstract のみに基づく。対象 model 名と各手法の速度向上率は未確認。
