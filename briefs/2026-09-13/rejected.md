### 機構 —— `lookback_days` が測っている時刻が、API に出てくる時刻ではない

arXiv API の `published` は**投稿 (submit) された時刻**である。一方、API に論文が現れるのは **announce された後**で、announce は平日の夜に 1 回ずつしか走らない。**この 2 つの時刻の間には 1〜4 日の遅れがある。**

`fetch_candidates.py` は `parse_entries()` で `pub_dt < cutoff` として**投稿時刻に対して**窓を切る。そのため:

- **窓の手前側 (新しい側) が、announce 待ちの論文で構造的に空になる。**`lookback_days: 2` の 2 日のうち、**手前の 1〜2 日は最初から空**である。
- **土曜に実行すると、announce 済みの最新は木曜 18:00Z 前後まで。cutoff もちょうど木曜 18:00Z。窓の幅が実質ゼロになる。**
- **日・月はそこに週末の announce 休止が足されるので、さらに深く空になる。**

**つまり `lookback_days: 2` は「2 日分を見る」設定ではない。「火〜金は約 1 日分、土日月は 0 日分を見る」設定である。**これが、これまで別々の症状として記録してきたものの共通の原因である:

- **「fm_distill が `max_results: 30` の天井に張り付く」** (09-10〜09-12 の 3 日連続) —— **窓が実質 1 announce 日分しかなく、その 1 日分だけで 30 件を超えるから。**
- **「next_arch の最古が cutoff の 2 分後」** (09-12) —— **窓の下端に論文が詰まっているから。**窓が狭いことの別の見え方。
- **「① の 2 つ (`lookback_days` と `max_results`) は独立でない」** (09-10 に数値確定) —— **`lookback_days` を広げないと 2 announce 日目に届かず、`max_results` を上げないと届いた分が上位 30 件の切り捨てで消えるから。**片方だけでは動かない理由がこれで説明される。

### §0.1 本日の新しい注意点: **土日月は `lookback_days` を上げても「新しい論文」は増えない**
