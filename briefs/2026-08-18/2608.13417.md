# Beyond Final Scores: A Systematic Evaluation of Agents for Long-Horizon AI Research and Development

**topic:** sns_wildcard (EXPLORE) ・ **arXiv:** 2608.13417 ・ **published:** 2026-08-12 ・ **hf_upvotes: 38**

> **分野は完全に外である。** LLM agent が自律的に研究開発をどこまで回せるかを測った論文であり、運転にも蒸留にも直接は関係しない。**wildcard 枠 1 件をこれに使う。**
>
> **主張を一行で:** **最終スコアだけを見ている限り、agent が「どこで得をして、どこで損をしたか」も「経験が次の判断を良くしたか」も分からない。** 本論文は **run の中の振る舞いを 3 つの局面に分解して測る**枠組みを作り、7 つの frontier model を 36 の long-horizon タスクで走らせた。
>
> **なぜ我々が読むか。理由は 2 つあり、どちらも「手法を借りるため」ではない。** (1) **同じ病が P1 の planner 評価にある** —— 衝突率という最終スコアだけでは、planner がなぜ失敗したかは出てこない。(2) **この research_loop 自体が、まさに評価対象の long-horizon agent である。**

## 何を解決する論文か

**自律 agent は、モデル・システム・その他の技術的成果物を、長期の実験を通じて改善できるようになりつつある。** ではその能力は今どこまで来ているのか。**しかし評価が最終スコアに留まる限り、この問いには答えられない。** 最終スコアは **進歩がどこで生まれ、どこで失われたかを示さず**、**積み上がった経験が後の判断を改善したかどうかも示さない。**

本論文は **rule-based metrics (LLM 判定ではなく、ログから機械的に判定できる規則ベースの指標)** によって **run の内部の振る舞いを特徴づける**枠組みを提示し、あわせて **統制された比較によって experience reuse (一度得た経験を後の判断に再利用できているか) を、同一タスク内と別タスク間の両方で測る。**

**結論は明快で、かつ辛い: 現在の agent は自律的な研究者というより engineering optimizer (工学的な最適化屋) として振る舞う。** 実用的な解を定式化し実装することはできる。**しかし run ごとの性能のばらつきが大きく、最も強い解でさえ既存技術の適応か組み合わせにとどまり、方法論としての真の新規性はいまだ稀である。**

## 手法の核心

- **run 内の振る舞いを 3 局面に分解する: Solution Framing (問題をどう立てたか) ・ Execution (立てた案をどう実装・実行したか) ・ Feedback Control (得られた結果をどう次の手に反映したか)。** **この 3 分解が本論文の中心的な道具である。** 最終スコアが同じ 2 つの run でも、**詰まっている局面が違えば、打つべき対策は全く違う。**

- **指標は rule-based。** LLM を審判に使わず、ログから機械的に判定する。**再現性が確保され、審判モデル自体の癖が混入しない。** 我々が同種の評価を自作するときにも、この選択はそのまま真似る価値がある。

- **experience reuse を統制比較で測る。** 「経験が溜まれば後の判断が良くなる」は自明ではない。**論文の観測は、経験の再利用が助けにもなれば、誤誘導にもなりうる (can help or mislead) というものである。** **過去の経験は無条件の資産ではない。**

- **規模: 7 つの frontier model × 36 の long-horizon タスク。** 単一モデルの逸話ではなく、**モデル横断で共通する構造として報告している。**

- **harness design が性能の安定性に効く。** モデルそのものではなく、**agent を走らせる足回り (ツール構成・ループの組み方・状態の持たせ方) が run 間のばらつきを左右する。** **同じモデルでも harness が違えば結果が違う** —— 評価の話であると同時に、**運用の話でもある。**

- **同じ最終成績の裏に、異なる process bottleneck が隠れている。** これが「最終スコアを超えて見よ」という題名の実質である。

## 追っているプロジェクトへの適用可能性

- **P1 / R1 —— 構造がそのまま重なる。ここが本ブリーフの最大の収穫。** R1 は **「衝突率だけでなく、過保守さや介入頻度を保証付きで測る」**という問題意識から出発している。**本論文はまったく同じ不満を、別の分野で、より一般的な形で述べている: 最終スコア (衝突率) は、失敗がどの局面で生まれたかを教えない。** 3 分解を運転に写すと自然な対応がつく —— **Solution Framing → 状況をどう認識し、どの挙動を選んだか。Execution → 選んだ挙動を軌道としてどう実現したか。Feedback Control → 環境の反応を受けて次の周期でどう修正したか。** **「同じ衝突率でも詰まっている局面が違う」という主張は、closed-loop の planner 評価でそのまま成り立つ。** R1 の新規性を確認する際、**この 3 分解を先行例として引用でき、かつ「conformal prediction (予測の外れ率を分布の仮定なしに保証する統計手法) で局面ごとに保証をつける」という差分が、我々の貢献として立つ。**

- **P1 —— rule-based に徹する設計判断を輸入する。** 運転の評価でも「LLM や学習済みモデルに良し悪しを判定させる」誘惑があるが、**審判が学習物だと保証の議論ができなくなる。** R1 が保証付きの指標を狙う以上、**判定はログから機械的に決まる形に保つべき**であり、本論文はその立場の先行例になる。

- **この research_loop 自体 —— 評価される側として読める。** 本 loop は **毎日 candidates を読み、brief を書き、過去の記録を参照して判断する long-horizon agent** である。論文の 3 つの所見は、そのまま自己診断のチェックリストになる: **(1) run 間のばらつき** —— 日によってブリーフの質が振れていないか。**(2) experience reuse が誤誘導になりうる** —— 過去の brief を参照することが、新しい候補を過去の枠組みに押し込める方向に働いていないか。**(3) harness design が安定性を決める** —— **これは今まさに当たっている問題である。** `fetch_candidates.py` の欠陥で 3 日連続 in-field 候補が 0 件になっているのは、**モデルの能力ではなく harness の問題**であり、**論文の指摘そのものである。**

- **P2 / P3 —— 直接の関係はない。** 蒸留にもアーキテクチャにも寄与しない。

- **留保:** (1) **対象は LLM agent であり、運転の planner ではない。** 3 分解の対応づけは我々による類推であって、**論文が主張していることではない。** 論文として引くときは「先行する問題意識」として引くべきで、手法の借用として書くと無理が出る。(2) **rule-based metrics の具体的な定義は abstract からは読めない。** 輸入するなら本文の指標定義の節だけを読めば足りる。(3) **hf_upvotes 38 は本日 3 件中最下位** であり、コミュニティの注目度は高くない。**それでも採ったのは relevance の判断による。**

### 試すべき実験

1. **R1 のサーベイに「局面分解型の評価」という列を足す (最優先・調査タスク・半日)。** R1 の次のアクションは **既存評価指標のサーベイと新規性の確認**である。**本論文は、そのサーベイの枠組みを 1 つ増やす:** 既存の planner 評価指標を「最終結果型 (衝突率・完走率)」と「局面分解型」に仕分ける。**もし運転側に局面分解型がほとんど無いなら、それが R1 の新規性の置き場所になる。** 逆に既にあるなら、R1 は指標の分解ではなく **保証のつけ方** に新規性を寄せる必要がある。**どちらであるかを決めるのが、この作業の目的である。**

2. **3 分解 × conformal で、R1 の主張の形を 1 枚に書き出す。** 「衝突率に保証をつける」ではなく、**「Framing / Execution / Feedback Control の各局面の失敗率に、それぞれ分布仮定なしの保証をつける」**と書けるか。**書けるなら R1 の輪郭が一段はっきりする。書けないなら、どこで詰まるかが分かる。** 実装は不要、**紙の上で 1 時間。**

3. **本 loop 自身に experience reuse の点検を入れる (小・ただし今日的)。** 過去 2 週間の brief を、**「過去の記録を参照した判断」と「新規に評価した判断」に仕分け**、前者が良い方向に働いた回と誤誘導になった回を数える。**論文の主張どおり両方あるはずで、あるなら参照の仕方に規則が要る。** 08-17 の Alaya-EVOKE 繰り上げは前者の成功例、**「wildcard ラベルを額面通り読まない」という判断の常態化は誤誘導になりうる側**である。

4. **harness 側の修正を評価より優先する (実験ではなく決定事項)。** 論文の「harness design が安定性を決める」は、**本 loop では既に発火している。** [[fetch-duplicate-candidates]] の 5 欠陥、とりわけ **arXiv 失敗の握り潰し** を直さない限り、**ブリーフの質を上げる努力は入力の欠落に食われる。** **評価の工夫より配管の修理が先、というのが本論文の実務的な含意である。**
