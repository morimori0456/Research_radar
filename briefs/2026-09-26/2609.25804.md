# The Tasteful Agent: Measuring and Improving Taste in Long-Horizon Tasks

- **arXiv:** https://arxiv.org/abs/2609.25804
- **topic (割当):** sns_wildcard (探索枠) / hf_upvotes 134
- **スコア:** P1 **2.5** / P2 **2.5** / P3 1.0
- **根拠:** abstract と arXiv HTML 版の本文 (§3 benchmark の構築、§4 結果、§5 蒸留、Appendix G の蒸留の設定) を読んだ。
- **公開物:** データ https://huggingface.co/datasets/wenbopan/taste-bench ・ コード https://github.com/wbopan/tastebench

## 何を解決する論文か

LLM agent が長い task (コード修正や ML 実験) をこなすとき、成否を決めるのは途中の分岐である。どの仮説を試すか、どの実装を土台にするか、といった分岐だ。既存の benchmark は最終的な成否しか測らず、**分岐での判断の良し悪し (著者はこれを taste と呼ぶ) を測るものが無かった。**この論文は、過去の agent の実行記録から分岐の問題を自動で作り、判断力を測る。さらに、その判断力を蒸留で小さいモデルに教えられることを示した。

## 手法の核心

- **decision fork (分岐点) を過去の実行記録から自動で掘る。**同じ task を複数回走らせると、途中で方針が分かれることがある。最終結果の良かった方が「正解の方向」になる。1 本の記録の中の detour (一度進んで引き返した寄り道) も分岐として使う。人手の注釈は要らない。hindsight (後から結果を見て、過去の判断の良し悪しを決めること) で正解ラベルを付けている。
- **問題は二択で、分岐より後は見せない。**評価対象のモデルには分岐点までの状況と 2 つの候補だけを見せ、どちらが良いかを選ばせる。候補の提示順を入れ替えた 2 通りで聞き、位置による偏りを除く。元データは、SWE-bench Pro (実在リポジトリのバグ修正 task 集) の 517 task の 2,677 回の実行と、RE-Bench などの ML 研究 task 47 件の 1,132 回の実行 (METR の公開記録)。
- **結果 1: 最良のモデルでも正答率 59.7%。**二択なので偶然でも 50% になる。分岐の良し悪しの証拠が記録の後の方で出てくる問題ほど、どのモデルも正答率が下がった。**reasoning budget (推論時に考えさせる量) を増やしても、正答率は上がらなかった。**
- **結果 2: 最終成否の benchmark では差がつかないモデルが、ここでは分かれた。**SWE-bench Verified の上位 4 モデルは互いに 4.0 点以内だったが、Taste-Bench では 10.7 点開いた。
- **結果 3: 判断力は蒸留できる。**teacher と student は同じ Qwen3.6-27B で、入力だけが違う。teacher には「どちらが正解か」の答えを見せて推論させ、student には問題だけを見せる。student は teacher の推論の token 分布に寄せて学ぶ。これは privileged information distillation (teacher だけが特権的な情報を見られる状態で蒸留し、student はその情報なしで同じ判断を再現する) の一種である。task が重ならないように分けた held-out (学習に使っていない) の問題で、正答率は 30.0% → 47.9% に上がった。さらに student の判断を「助言」として別の agent に渡すと、SWE-bench Pro の held-out 41 task で成功率が 14.6% → 33.7% になった (全分岐で正解を助言した場合の上限は 39.0%)。

## 蒸留の recipe (P2 向けの具体値)

- LoRA (Low-Rank Adaptation; 重みの差分を低ランク行列だけで学習する PEFT の代表的手法) を rank 16 で、attention と MLP の全射影に付ける。学習する parameter は 79.7M。
- loss は forward KL (teacher の分布を正解として student を寄せる、標準的な蒸留の loss)。temperature 1.0。teacher の上位 100 token に「残りの確率質量」を 1 枠足した分布に寄せる。推論部分の最大 512 位置に掛ける。
- **leakage (答えの文面が student にそのまま漏れること) を構造で防ぐ。**出力は二択の答えで終わり、teacher に見せた正解の文面を写す部分が出力に無い。
- 蒸留の後に calibration (最終回答の位置だけを正解ラベルの cross-entropy で追加学習し、推論過程は変えない工程) を 1 epoch 行う。
- 1 fold あたり A100 80GB 1 枚で約 2 時間。

## プロジェクトへの適用可能性

### P2 (蒸留 + fine-tuning) — 2.5: 「答えを知っている teacher」から蒸留する recipe

P2 の蒸留は「大きい teacher → 小さい student」が基本である。この論文は別の軸を示している。**teacher と student は同じモデルで、teacher にだけ答え (未来の情報) を見せる。**運転に置き換えると、teacher には「この場面の数秒後に実際に何が起きたか」(将来の軌跡、周辺車両の実際の動き) を入力として与え、student には現在までの観測だけを与える、という形になる。

**実験アイデア (1〜2 日、GPU 1 枚):**
1. 既存の軌跡予測モデル (または小さい planner の scorer) を土台にする。teacher 版は入力に「3 秒後の周辺車両の実際の位置」を追加して fine-tuning する。student 版は現在までの観測だけを使う。
2. student の学習を 3 通り比べる: (a) 正解軌跡だけで学習、(b) 通常の大きい teacher から蒸留、(c) 未来を見た teacher から蒸留 (forward KL、この論文と同じく出力分布に寄せる)。
3. 評価は、場面の結末が途中で分かれる場面 (合流で譲るか先に入るか、など) に絞った minADE (予測した複数の軌跡のうち、正解に最も近いものとの平均誤差) と、分岐の選択の正答率で見る。
4. **判定:** (c) が (a)(b) を分岐の正答率で上回れば、「未来を見た teacher」は P2 の蒸留 recipe の選択肢になる。上回らなければ、未来情報は teacher 自身の推論を楽にするだけで、student に移せる知識になっていない。

### P1 (Planner AI + 評価) — 2.5: 最終成否でなく「分岐での判断」を測る評価

P1 の closed-loop simulation でも、同じ場面を planner に何度も走らせると、途中で方針が分かれる。**その分岐点を掘り出して「どちらの方針が最終的に良かったか」を正解にすれば、人手の注釈なしで planner の判断力のテスト集が作れる。**衝突率や完走率のような最終指標で差がつかない planner 同士でも、分岐の判断では差が出るかもしれない。論文の結果 2 がその実例である。

**実験アイデア (半日、既存のログがあれば GPU 不要):**
1. 既存の closed-loop の評価ログから、同じ初期場面で planner を seed 違いで 5 回以上走らせた記録を集める。
2. 各記録の自車軌跡が 1 m 以上離れた最初の時刻を「分岐点」として検出する。最終スコアの差が一定以上の分岐だけを残す。
3. 2 つの planner について、分岐点での選択が「良かった側」と一致する率を計算する。
4. **判定:** 最終スコアの差が 1 点以内の 2 つの planner で、この一致率に 5 点以上の差が出れば、分岐の判断を P1 の評価指標に加える価値がある。

## 読むときの但し書き

- 分岐の正解は「その方向に進んだ実行が最終的に良かった」で決めている。実行の上手さや偶然の影響を除くために judge (候補を判定する LLM) で絞り込んでいる。人手の抜き取り検査では 98.8% 一致と報告されているが、judge の判断に依存する部分は残る。
- 蒸留の end-to-end 評価は 41 task だけで、実行回数や分散の記載は本文から確認できなかった。
- 助言は「過去の実行から掘った分岐」に対して出している。**新しい task で、分岐を事前に知らずに使えるかは示されていない。**
- 探索枠で採用した理由: 3 件の wildcard のうち、残る SpeakerMem-R1 は全プロジェクトで 1.0 以下 ([rejected.md](rejected.md))。もう 1 件の Object Permanence は next_arch の枠で採用したので、この論文が wildcard 枠の唯一の候補になった。hf_upvotes によるタイブレークは使っていない。
