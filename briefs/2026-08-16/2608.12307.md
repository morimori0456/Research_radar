# AI4AI at Test-Time: Strong-to-Weak Capability Transfer via Harnesses

## 何を解決する論文か

蒸留 (knowledge distillation; 大きな teacher モデルの振る舞いを小さな student モデルに写す手法) は通常、**student のパラメータを更新する**ことで行われる —— teacher forcing (teacher の出力を正解として学習させる)、on-policy distillation (student 自身が生成した軌跡上で teacher に正解を付けさせる) など、いずれも学習時の手法である。

**本論文はこれを「学習時にやらなければならないのか」と問い直す。** 強い builder モデルが、弱い target モデルのための **推論時の足場 (harness)** を構築できるなら、**パラメータ更新をまったく行わずに** 能力を移せるのではないか。これを **strong-to-weak scaffolding** と呼び、Theory-of-Mind (他者の信念・意図を推論する課題) 系のベンチマーク 4 本で検証している。

結果は劇的で、**target モデルの平均性能が 0.49 から 0.91 へほぼ倍増する。** 著者の結論は「推論時の harness 設計は、従来の学習時の蒸留を置き換えるものではなく **補完するもの**」である。

## 手法の核心

- **builder と target の役割分離。** builder (強いモデル) は **harness を書くだけ**で、テスト時の推論には参加しない。target (弱いモデル) が harness の中で実際に解く。**両者の間で流れるのは重みでも logits でもなく、コードである。**

- **harness は反復的に作り込まれる。** builder は各ベンチマークの **データの 5% を validation セットとして使い、複数ラウンドかけて harness を改良する。** 確定後にフルのテストセットで評価する。**5% の正解ラベルを見て設計している**という点は、後述の留保の中心。

- **利得の中身が分解されている —— ここが本論文で最も価値のある部分。** 効いているのは以下の 3 つで、いずれも「モデルにもっと考えさせる」類ではない。
  - **不安定な推論を決定論的コードへ外出しする** (モデルが毎回ぶれる計算を、確実に同じ答えを返すコードに置き換える)
  - **benchmark-specific routing** (課題の型を判別して処理を振り分ける)
  - **厳格な回答形式の強制**

  著者は明示的に、**「target により長く推論させる」「より広くサンプリングする」ことからは来ていない**と書いている。

- **builder の reasoning effort (推論にかける計算量の設定) を上げると、harness の品質が単調に改善する。** 一方 **platform 効果 (どの実行環境・足場の上で組むか) は、builder 自身の能力差に比べれば小さい。** つまり **良い harness を書けるかどうかは、ほぼ builder の頭の良さで決まる。**

- **弱い target ほど利得が大きい。** 能力の低いモデルほど harness で持ち上がる余地がある。

## 追っているプロジェクトへの適用可能性

- **P2 / R2 —— 08-15 に決めた R2 の設計に、3 本目の軸が付く。最重要。** 昨日、R2 (蒸留の capacity gap 系統則) を「teacher/student の容量比」だけの 1 次元から、**容量軸 × 情報軸の 2 次元**へ組み替えることを決めた。**本論文はそこに「パラメータ更新の有無」という 3 本目の軸を置く。** しかも本論文の位置は **容量比は任意・パラメータ更新はゼロ**という、この空間の極端な隅である。**隅に強い点があると分かった以上、空間の張り方を決めるときに無視できない。**

- **P2 / R2 —— 実務上いちばん効く帰結は、対照群が 1 つ増えること。** **どんな蒸留手法も「teacher に student 用の harness を書かせて、重みは一切触らない」というベースラインに勝たなければならない。** このベースラインは **学習コストがゼロで、実装が数時間で、誰も回していない。** R2 の実験にこれを対照として入れると、**「何 GPU 時間をかけた蒸留が、コードを書かせるだけの手法にどれだけ勝つのか」**という形で主張が一段強くなる。**逆に勝てない領域が見つかれば、それはそれで R2 の主要な結果になる。**

- **P2 —— 車載への持ち帰りは「全部」ではなく「1 つだけ」。** W33 の課題レーダーが指摘した通り、Alpamayo 2 Super (34B の VLA) を車載サイズに落とす作業は必須経路である。**harness をそのまま持ち込むことはできない** —— routing も複数回の呼び出しもコード実行も、**推論時の遅延を増やす**方向であり、車載のレイテンシ予算と正面から衝突する。**ただし「不安定な推論を決定論的コードへ外出しする」という一点だけは、車載でこそ望ましい。** モデルがぶれる部分を抜き出してコードに固定するのは、safety critical な実装が元々やりたかったことである。**本論文はそれを「性能が上がる」側から裏付けている。**

- **P1 への波及は間接的。** 「決定論的に検証できる部分と、モデルの判断に委ねる部分を分ける」という設計原則自体は、**本日もう 1 本の Spark-to-Paper (2608.11924) がまったく同じことを主張している。** **同日に独立した 2 本が同じ分割を推している**という事実は、原則の側の信頼度を上げる。

- **留保 (この論文は特に厳しく読む必要がある):**
  1. **検証は Theory-of-Mind ベンチ 4 本のみ。** テキスト入力・離散的な回答・明確な正解、という条件が揃っている。**運転・制御・連続値の出力には検証がゼロ。** 「回答形式の強制」という利得源が、そもそも連続値ドメインには存在しない。
  2. **5% の正解ラベルへのアクセスを前提としている。** 実運用で「新しいドメインの正解つきデータが 5% ある」とは限らない。**これは少データ適合の手法ではなく、少データ *チューニング* の手法である。**
  3. **benchmark-specific routing が利得の主要因の 1 つだと著者自身が書いている。** これは **汎化の主張と正面から矛盾する。** 0.49 → 0.91 のうち何割がこれなのかは、abstract の範囲では分解されていない。**この分解が無い限り、「能力が移った」とは言えない。**
  4. **回答形式の強制による利得は、能力ではなく採点との噛み合いを直している可能性が高い。** ベンチマークのスコアは上がるが、モデルが実際にできることは変わっていないかもしれない。**0.49 という出発点の低さ自体が、形式ミスによる取りこぼしを含んでいる疑いがある。**

### 試すべき実験

1. **R2 の対照群として最小構成で回す (最優先、学習不要)。** 手持ちの teacher に student 用の harness を書かせ、**パラメータ更新ゼロ**で性能を測る。これを **既存の蒸留曲線の上に水平線として引く。** 容量比をどこまで開いてもこの水平線に勝てない領域があるなら、**それが R2 でいちばん強い図になる。** 学習を回す前にやるべき実験。

2. **利得の分解 —— 本論文がやっていない部分で、ここが空いている。** (a) 回答形式の強制のみ / (b) routing のみ / (c) 決定論的コードへの外出しのみ、の 3 条件で ablation する。**(a) だけで大半が説明できてしまうなら、本論文の主張は「蒸留」ではなく「採点との噛み合わせ」だったことになる。** 安く、決着がつく。

3. **連続値ドメインで成立するかを見る。** 軌道予測タスクで builder に harness を書かせる。**「決定論的コードへの外出し」が離散回答の外でも効くか。** 効かなければ本論文の適用範囲が確定するので、**どちらに転んでも結果になる。**

4. **validation データ量への依存を測る。** harness 構築に使うデータを 5% → 1% → 0.5% と減らし、**品質がどこで崩れるか**を見る。**これは P2 の relevance_criteria にある「少データでの適合」そのものの問いに直接答える。** 崩れる点が早ければ、この手法は実務では使えないと結論できる。
