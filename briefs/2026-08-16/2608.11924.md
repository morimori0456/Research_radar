## 何を解決する論文か

研究アイデアを 1 本の論文に仕上げる作業は、**文章生成だけでは足りない。** 文献を検索し、実験を設計して実行し、**得られた証拠に合わせて主張を書き換え**、出版に耐える図を作り、**長い生成のあいだ一貫性を保ち続ける**必要がある。

Spark-to-Paper はこれを **13 個の composable skill (組み合わせ可能な部品として定義された作業単位)** として、**既存の coding assistant の内側に**実装したシステムである。**専用の agent platform も orchestration service (複数のエージェントの実行を調停する基盤) も使っていない。** これが本論文の実務上の要点で、**特別な基盤を持たない環境でもそのまま真似られる**ことを意味する。

評価は 8 つの統制された研究テーマ上で行われ、**引用の妥当性 99.5%、図の編集可能性 96.4%** を報告している。

## 手法の核心

- **モデルの判断と、決定論的な操作を分離する。** 「判断が要ること」と「実行して機械的に検証できること」を混ぜない。**検証できるものは検証し、判断が要るものだけをモデルに残す。** システム全体がこの 1 つの分割の上に構成されている。

- **実験計画と報告を分離する —— これが最も移植価値が高い。** **必要な証拠を、結果を観測する *前* に確定させる。** そのうえで、**測定された結果に応じて原稿の主張を書き換える。** 順序が逆 (結果を見てから何を示すか決める) にならないよう、構造で強制している。

- **Self-Refutation Loop を有界化する。** 著者が名前を付けた失敗モードで、**実験を繰り返すたびに元の研究目的が棄却され続ける**状態を指す。放置すると無限に実験を回して何も結論しない。**明示的に上限を置いて打ち切る。**

- **整合性チェック (決定論的) と self-critique (モデルによる自己批評) を組み合わせる。** どちらか一方ではなく両方。**ablation の数字がこの組み合わせを支持している: 単一パスの下書きでの捏造検出 14% → 全部入りで 92%。**

- **図は「描かせる」のではなく「コードで作る」。** 実験結果は **programmatic plotting (プロットするコードを生成して実行する)**、手法の概念図は **code-based reconstruction (図を描くコードとして再構成する)**。結果として **編集可能な vector 図**が出る (ラスタ画像ではないので後から直せる)。

## 追っているプロジェクトへの適用可能性

- **research_loop 自身 —— 直接の宛先はここで、他のどのプロジェクトよりも当たっている。** 本ループの候補選別と DIGEST 生成は、**まさに「長い生成トラジェクトリ」であり、fabrication (もっともらしいが根拠のない記述) のリスクを構造的に抱えている。** そして **本ループの briefs は現状すべて単一パス生成である。** 本論文の数字を素直に読むと、**単一パスの下書きは捏造の 86% を見逃す。** 自分の出力に当てはめて考えるべき数字。

- **research_loop —— 今日から実装できる最小の 1 つは「数値の出典チェッカ」。** brief 中に現れるすべての数値が、`candidates.json` の該当 abstract に文字列として存在するかを機械的に照合する。**存在しないものは「abstract 外の主張」として明示的にフラグを立てる** (推測なら推測と書けばよく、消す必要はない —— 問題は *区別されていない* ことである)。**数十行のスクリプトで、モデルの判断を一切必要としない。** 本論文の「決定論的に検証できる操作を分離せよ」を、この repo に最も安く適用した形。

- **R1 / R2 / R3 —— 「結果を見る前に必要な証拠を確定させる」が、そのまま予備実験の作法になる。** 08-15 に R2 の予備実験 (teacher/student 比 {1.0, 2, 8} × 特権情報 {なし, 未来の一部, 未来の全部} の 3×3) を決めたが、**「何が出たら R2 を進め、何が出たら捨てるか」を先に書いていない。** 今書けば、**結果を見てから基準を動かす余地が消える。** `decisions/` に置くのが自然。

- **RESEARCH_PIPELINE —— Self-Refutation Loop の有界化が、そのまま欠けている機能を指している。** 現在のアイデア在庫の状態遷移 (種 → 調査中 → 予備実験 → 本実験 → 執筆 → 投稿) には **停止規則が無い。** 事実として **R1 は 7 月から「種」のまま動いていない。** **「予備実験が n 回続けて目的を棄却したら捨てる」**という規則を状態に足せば、**在庫が腐るのではなく decisions/ に「捨てた」という記録が残る。** RESEARCH_PIPELINE の「未定。次の quarterly で R1–R3 から 1 本に絞る (全部追うと全部落ちる)」は、**まさにこの停止規則が無いことの症状である。**

- **P1 / P2 / P3 の ML 的な中身への寄与はゼロ。** planner にもアーキテクチャにも蒸留にも一切効かない。**これは運用の論文であり、混同しないこと。** wildcard 枠でしか正当化できない採用である。

- **留保:**
  1. **すべて自己申告で、外部の追試は無い。** 8 テーマは著者が選んだ統制された設定であり、**このシステムが査読を通った論文を生んだわけではない。**
  2. **「引用の妥当性 99.5%」は、引用が実在し内容が合っているという意味であって、その引用が *適切* かは別問題。** 存在する論文を的外れに引くことは、このチェックを通過する。
  3. **捏造検出 92% は、裏を返せば 8% が残る**ということ。しかも **検出しているのは自分自身の批評である。** 自分で気づけない種類の誤りは、この数字に含まれない。
  4. **いちばん怪しいのは「図の編集可能性 96.4%」。** **編集できることと、図が正しいことは無関係である。** 測りやすい量を測っているだけの可能性が高い。
  5. **本ループへの適用で価値があるのは数字ではなく、2 つの分離 (判断/決定論、計画/報告) という設計原則のほうである。** 数字が再現されると期待しないほうがよい。

### 試すべき実験 (このリポジトリで)

1. **数値の出典チェッカを書く (最優先、1 時間程度)。** brief 中の数値を正規表現で拾い、対応する abstract 内に存在するか照合し、無いものを一覧にする。**まず過去の brief 5 本に対して遡って走らせる** —— 現状の捏造率が分かり、以降の改善の基準線になる。**基準線が無いまま手順を変えても、良くなったかどうか分からない。**

2. **予備実験の事前登録を 1 件だけ試す。** R2 の 3×3 について、**実験を回す前に**「どの結果が出たら進め、どの結果が出たら捨てるか」を `decisions/` に書く。**1 件で十分** —— 書けるかどうか自体が、その実験が設計できているかの検査になる。

3. **停止規則を RESEARCH_PIPELINE に足す。** 状態遷移の表に「棄却回数」の列を 1 つ増やすだけ。**R1 が 7 月から動いていないという事実を、この列が可視化する。**

4. **brief 生成を「単一パス」から「下書き → 決定論的チェック → 自己批評 → 修正」に変え、前後を比較する。** 対照は **過去の brief を 5 本サンプルし、abstract 外の主張を手で数えたもの。** 本論文の 14% → 92% がこの repo で再現するかは大いに疑わしいが、**改善の有無だけなら安く測れる。**
