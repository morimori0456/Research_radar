# SLAI T-Rex — trillion-scale MoE の full-parameter post-training を Ascend NPU で回し、solver で検証した合成データで OR ドメインに適合させる

**arXiv:** https://arxiv.org/abs/2607.20145
**topic:** sns_wildcard(分野外・探索枠 / 実質 P2 寄り)　**hf_upvotes:** 56　**published:** 2026-07-21

---

## 何を解決する論文か

trillion-parameter 級の MoE(Mixture-of-Experts; 入力ごとに一部の expert サブネットだけを活性化させる巨大モデル)を **full-parameter post-training**(LoRA 等ではなく全パラメータを更新する追加学習)しようとすると、メモリ逼迫・通信が計算と重ならない・kernel が非効率、という system 面の壁にぶつかる。本レポートは、GPU ではなく **Ascend NPU(Huawei 製の AI 学習アクセラレータ)の SuperPOD** 上でこの壁を越える end-to-end な最適化実践を示し、さらにその基盤の上で **Operations Research(OR; 数理最適化で意思決定を解く分野)タスク**にモデルを適合させる CPT+SFT レシピまでを一気通貫で報告する。

## 手法の核心

- **3 階層の最適化フレームワーク。** (1) model-level parallelism(モデル分割の並列化)、(2) computation-communication orchestration(計算と通信を重ねてオーバーラップさせる)、(3) low-level kernel execution(演算カーネルの実行最適化)を組み合わせ、**MFU(Model FLOPs Utilization; 理論演算能力のうち実際にモデル学習に使えた割合)34.22%** を達成。open-source baseline レシピ比 **2.93倍**、かつ学習の安定性を維持。
- **CPT → SFT の 2 段適合。** CPT(Continued Pre-Training; 事前学習の続きとして大量ドメインテキストで学習を継続)でドメイン知識を入れ、SFT(Supervised Fine-Tuning; 入出力ペアで指示追従を仕込む)で仕上げる。ターゲットは DeepSeek-V4-Flash。
- **solver-verified synthetic data。** 収集したドメイン資料に加え、**最適化ソルバで解の正しさを検証した合成の最適化ドキュメント**を混ぜて SFT データを作る。要は「正解ラベルを人手ではなくソルバで自動保証する」verifier-in-the-loop の合成データ生成。最終 SFT データは 4 タスク種別・3 種の問題表現をまたぐ **10K の高品質サンプル**。
- **結果。** 特化モデルが zero-shot Pass@1(1 回生成での正答率)で評価対象中トップの **71.81%**。GPT-5.4-Mini を +3.98pt、base の DeepSeek-V4-Flash を +11.27pt 上回る。「小さめの汎用強モデル」を、ドメイン特化 post-training で上回れることを示した事例。

## 追っているプロジェクトへの適用可能性

- **P2(FM 蒸留 + 適合)— 本命。** P2 が高優先とする「再現可能な recipe」「ドメインギャップの克服」「基盤モデルを別ドメインに転用」の直球事例。特に持ち帰る価値があるのは **solver-verified synthetic data**:自動運転なら「シミュレータや幾何ソルバで実行可能性・衝突判定を検証済みの軌道/シナリオ記述」を合成 SFT データに使う、という置き換えが効く。人手ラベル無しで正解を保証できるドメイン(=検証が生成より容易な問題)では、この verifier-in-the-loop パターンがそのまま転用できる。
- **P3(次世代アーキ)— 副次。** trillion 級 MoE の full-parameter post-training を「安定して・高 MFU で」回すための comp-comm オーバーラップ設計は、MoE ベースの大規模 driving/VLA モデルを自前で追加学習する時の system 前提知識になる。ただし数値・kernel の多くは Ascend NPU 固有で、GPU クラスタにそのまま移らない点は割り引いて読む。
- **P1(Planner AI)— 弱い。** 直接の planner/評価知見は無し。ただし「OR タスク = 制約付き最適化を LLM に解かせる」という枠組みは、制約付き motion planning を言語モデル/生成モデルで扱う際の周辺知識として緩く接続する。

## 試すべき実験アイデア

1. **verifier-in-the-loop 合成 SFT の回収率テスト。** 手持ちドメインで「生成は難しいが検証は容易」な小タスクを 1 つ選び、(a) 人手/既存ラベルのみの SFT と (b) ソルバ/シミュレータ検証済み合成データを混ぜた SFT を **matched sample budget** で比較。Pass@1 とドメイン汎化の差を測る。
2. **合成データの検証強度の効き方。** solver 検証を「厳密検証」「緩い heuristic 検証」「無検証」の 3 段で振り、SFT 後性能がどこで頭打ち/劣化するかを見る(データ品質のどこにコストを割くべきかの当たりを付ける)。
3. **comp-comm オーバーラップの自前計測。** 自社の分散学習で MFU を実測し、通信が計算に隠れているか(non-overlapped 時間の割合)を可視化。本レポートの 2.93倍という改善余地が自環境のどこにあるかを特定する。
