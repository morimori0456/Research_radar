## 何を解決する論文か

camera ベースの E2E (end-to-end; 画像から直接 trajectory を出す) 運転 model の多くは、BEV (Bird's-Eye-View; 車を真上から見た格子状の表現) をすべての cell で同じ解像度で作り、同じ計算量を使う。しかし planning horizon 内に車が通るのはそのうちごく一部の cell だけである。BEVCast は、予測した走行 path に合わせて BEV の解像度を変え、計算を節約しながら精度を保つ。

## 手法の核心

- **2 段構成の BEV**。第 1 段で全体を粗い格子 (4.096 m 間隔の cell) で encode する。
- **heat head** (記録された走行 path で学習する小さな出力) が各粗い cell に heat (通る見込み) を割り当て、固定 budget の範囲で heat の高い cell だけを 1.024 m に refine する。
- 残りは粗いまま残すので、trajectory head が読む BEV は混合解像度でも scene 全体を覆う。HD map (高精度地図) も navigation command (右左折指示) も要らない。
- 同じ architecture・学習 recipe の全面 1.024 m 格子と比較: 10% の refinement budget で BEV query の 28% を encode し、batch size 1 の BEV encoder 時間は 66%。
- nuScenes で平均 displacement error 1.078 m (全面 1.149 m)、drivable area violation (走行可能領域からのはみ出し) 率 1.46% (同 2.29%)。NAVSIM navtest (非反応型の運転 benchmark) で平均 displacement error 0.577 m (同 0.598 m)、EPDMS (Extended Predictive Driver Model Score; 衝突・走行可能領域・進捗などを合成した運転の採点) 82.51 (同 81.28)。

## 適用可能性 (P3)

- 「計算の配分を task (走行 path) に追従させる」設計は、車載の推論コスト制約に直結する。精度を下げずに encoder 時間を 34% 減らしている点が実務的。
- 全面高解像度より精度が上がっているので、「重要でない cell の計算が noise になっていた」可能性も示唆する。P3 の E2E architecture の効率化の候補。
- 注意: 評価は open-loop 寄りの nuScenes と NAVSIM で、閉ループの安全性は分からない。heat head が path を外すと、本来必要な cell が粗いままになる failure mode がある (abstract に分析があるかは未確認)。

## 試すべき実験アイデア

1. 手元の BEV encoder で、粗い格子と細かい格子を併用し、refine する cell を「正解 path 周辺」で選ぶ oracle 版を作る (最小の実験)。heat head の精度を抜きにして、混合解像度の上限性能を見る。
2. refinement budget を 5% / 10% / 20% と振り、平均 displacement error と encoder 時間の trade-off 曲線を描く。
3. heat head の予測を外す (path を意図的にずらす) ことで、失敗時に何が起きるか (衝突・はみ出し) を調べる。
