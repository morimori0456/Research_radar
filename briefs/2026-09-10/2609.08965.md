## 何を解決する論文か

**scenario-based testing (シナリオを列挙して自動運転システムに当て、危険な場面での挙動を検証する手法)** は ADS 検証の標準的な枠組みだが、実務では**シナリオ生成・検索・改変・実行・結果分析がバラバラのツールで行われる断片的なパイプライン**になっている。ツール間で情報が繋がらないので、「この planner はどのシナリオ群で弱いのか」を回して詰めることができない。

**PlannerForge は、この全段を LLM agent の 1 つの枠組みに入れる。**さらに従来の 5 段の後ろに **ADS Enhancement (弱点に基づく改善)** と **ADS Benchmarking** の 2 段を足し、**評価が改善に折り返す閉路**にしている。

## 手法の核心

- **測定の規模が大きい。****既製の LLM 10 種 × 6 タスク** (Generation / Selection / Modification / Module Routing / Planner Testing / Enhancement) **× prompt 条件 5 種。**タスクごとの最良スコアは **0.88〜1.00。**
- **open-source モデルが商用 API に並ぶ。****20〜35B 級の open-weight モデル (例: Qwen3.6:35B) が 5 タスク中 3 つで商用 API と同等。****手元の計算資源で回せる範囲、という意味で実務的に重要な結果である。**
- **端から端まで繋ぐと目減りする。**モジュールを直列に連結すると、**seed query の 83% (商用) / 78% (open) しか最後まで残らない。**段ごとの精度が高くても、**7 段を通すと 2 割が落ちる。**
- **既存手法との比較 3 本。**自然言語からのシナリオ生成で **Scenario Factory 2.0 に対し 200 問中 193 対 144 が実行可能。**rank-1 での検索で **BM25 (単語頻度に基づく古典的な文書検索スコア) の 67.5% に対し 92.0%。**そして —— **物理的に妥当な改変で、From-Words-to-Collisions の 31% に対し 94% 以上。**
- **planner の改善まで到達している。****N=400 で cost-tuning により planner の成功率が 50.4% → 70.2%、衝突が 19.0% → 8.4%。**しかも**ドメイン特化の fine-tuning なし。**

## 追っているプロジェクトへの適用可能性

### (1) R1 の「抜け穴監査」に、本日いちばん強い数字がある

**「物理的に妥当な改変が 31%」は、比較相手 (From-Words-to-Collisions) の話である。**言い換えると —— **先行手法が生成した safety-critical シナリオの約 7 割は、物理的に成立していなかった。**

**R1 の 3 本柱のうち「抜け穴監査 (評価の分母が健全か)」は、まさにこれを問題にしている。**衝突率を分母 N 件のシナリオで割るとき、**その N 件のうち何割が物理的に成立しているのかを誰も報告していない。**成立していないシナリオでの衝突は、planner の欠陥ではない。

**R1 の introduction が使える形にすると 1 文になる:**

> 既存の safety-critical シナリオ生成では、生成されたシナリオの過半が物理的に妥当でないことが報告されている [PlannerForge]。**衝突率の分母が健全かどうかは、衝突率そのものとは別に測る必要がある。**

**これは自分で測った数字ゼロの状態でも引ける外部証拠である。**09-09 の [2609.04921](../2026-09-09/2609.04921.md) が「順位が入れ替わる」側の証拠だったのに対し、**本論文は「分母が汚れている」側の証拠**で、**R1 の 3 本柱のうち 2 本目に、初めて外部証拠が付いた。**

### (2) シナリオの供給側が、10 月の本実験の律速になる可能性がある

R1 の 10 月の計画は **「公開データ (nuPlan / NAVSIM ログ) で、指標が planner の順位を入れ替えるか」** である。**ここで必要なのは planner だけでなく、順位が入れ替わる程度に難しいシナリオ群である。**ログをそのまま使うと大半が平穏なので、**難シナリオを作るか選ぶ工程が要る。**

**本論文の Selection 段 (rank-1 で 92.0%) は、その「選ぶ」側に直接使える。**生成 (作る) より検索 (選ぶ) のほうが**既存ログの上で完結し、物理的妥当性の問題を丸ごと回避できる**ので、**10 月に取るならこちら。**

### (3) 「7 段通すと 2 割落ちる」は、この loop 自身に当たっている

**段ごとの成功率が 0.88〜1.00 でも、直列に繋ぐと 78〜83% しか残らない。**この loop は **fetch → 選別 → ブリーフ → 図 → 実験 → 執筆** の直列パイプラインで、**現在 3 段目までしか完走していない。****各段の質を上げても、繋がっていない段があれば出力はゼロである** —— これは 09-06 の HarnessDev、09-04 の Repo-To-Skill と同じ指摘の 3 度目である。
