# RouteOPD — 蒸留を「確率をどこからどこへ運ぶか」の問題として書き直す

**topic:** fm_distill_finetune (P2) / **project:** P2 (R2 の本線)
**hf_upvotes:** 0 / **公開:** 2026-09-08T07:07:39Z (本流・新規)
**スコア:** P1 1.5 / **P2 5.0** / P3 2.0

> **なぜ今日読むか:** R2 の現在の仮説は 09-06 に **「支配変数は loss ではなく、監督を当てる範囲である」** に移っている。**本論文はその「範囲」を、初めて明示的な数学的対象 (transport pair) にした。**しかも副産物として **routing fidelity / background leakage** という 2 つの診断量が付いてくる —— **これは過去の蒸留ログに後付けで計算できる。**R2 の次のアクション (「過去の蒸留ログに CLL を後付けする」) の、計算する量の候補が 1 つ増えた。

## 何を解決する論文か

**OPD (On-Policy Distillation; student 自身が生成した系列の上で teacher が教える蒸留)** は、student が実際に踏む状態の上で監督が当たるので、offline 蒸留より分布ずれに強い。ところが**計算を安くするために teacher 分布をサンプルで近似すると、teacher からの情報が「その token の確率を上げろ/下げろ」というスカラーの credit まで潰れてしまう。**

**潰れた結果、決定的な情報が落ちる —— 「下げた確率を、どこへ移すのか」が指定されない。**本論文はここを突き、**蒸留を「確率質量の輸送」として定式化し直す。**

## 手法の核心

- **不一致を 2 種類に分解する。**各位置で teacher と student の分布を比べ、**student-excess source (student が余分に確率を置いている token = 運び出す側)** と **teacher-deficit destination (teacher が求めているのに student が足りない token = 運び込む側)** に分ける。
- **source と destination を明示的に対にする (transport pair)。**従来は「下げる」「上げる」が独立に指示されるだけだったのに対し、**どこから抜いてどこへ入れるかを 1 つの操作にまとめる。**
- **pairwise log-odds を、実現可能な目標へ動かす。**目標値は **bounded teacher potential (teacher 側から作る、値域を抑えたスコア関数)** から導く。**「同時に達成できる組み合わせ」に目標を制限しているのが要点で、矛盾する要求で student が振り回されるのを防ぐ。**
- **輸送量を teacher demand の集中度に合わせて動かす。****teacher の要求が少数の token に集中しているときと、広く薄く散っているときで、動かす総量を変える。**
- **結果:** teacher-student の組み合わせ **4 通り** × 数学推論ベンチマーク **4 種**で、**sampled reverse-KL 型の OPD を一貫して上回る。**改善に伴って **routing fidelity (要求された行き先に実際に質量が入った割合) が上がり、background leakage (関係ない token へ漏れた質量) が下がる。**

## 追っているプロジェクトへの適用可能性

### (1) R2 の仮説に、直接ぶつかる

R2 では **「容量比 1.0 でも蒸留が効く反例 5 本」により、当初の前提 (容量差が破綻の原因) は既に棄却されている。**代わりに残っている候補は 2 本で、**しかも治療方向が正反対**なので対照群として並べられる、というのが現状の整理だった。

- **① CLL 集中度 (UC-MOPD)** —— 損失が少数の token に集中しすぎると壊れる、という側。
- **② clipping で切り捨てられる推論 token (Echo-GRPO)** —— 切り捨てすぎると壊れる、という側。

**RouteOPD は、この 2 本を同じ座標に載せる可能性がある。**本論文が「**teacher demand の集中度**に応じて**輸送 budget** を変える」と言っているのは、**①の集中度を測る側と、②の切り捨て量を決める側を、1 つの調整器の中に入れた**ということである。**つまり ① と ② は対立する仮説ではなく、同じ 1 本のダイヤルの両端かもしれない。**

> **これは R2 にとって、確認ではなく反証の機会である。**もし ① と ② が本当に 1 本のダイヤルなら、**過去の蒸留ログで「集中度が高い run ほど、切り捨てられた token 量も多い」という相関が出るはずである。**出なければ、1 本のダイヤル説は落ちる。**どちらに転んでも R2 は進む。**

### (2) 新しい診断量が 2 つ、ログに後付けできる

**routing fidelity** と **background leakage** は、**新しく学習を回さなくても、teacher 分布と student 分布のペアが残っていれば計算できる。**R2 の次のアクションは元々「過去の蒸留ログに CLL を後付けする」だったので、**同じ 1 回のパスで 3 つ計算できる。**追加コストはほぼゼロである。

### (3) P1 / P3 への転用は薄い

**運転の planner に直接効く話ではない。**強いて言えば「監督を当てる先を明示的に指定する」という発想は、R1 の指標設計とは無関係である。**混ぜないこと。**

## 試すべき実験アイデア

1. **【R2 再開時・半日】過去の蒸留ログ 7 本に、CLL 集中度・routing fidelity・background leakage を後付けで計算し、3 つを 1 枚の散布図に載せる。**狙いは相関の有無であって、性能の改善ではない。**① と ② が同じダイヤルの両端なら、点が 1 本の曲線に乗る。**
2. **【R2 再開時・1 日】容量比 1.0 の反例 5 本に限って、background leakage を見る。**容量差では説明できなかったのだから、**「漏れの量」で説明できるかを直接聞く。**5 本のうち leakage が低い側に固まれば、R2 の主張が 1 文になる。
3. **【やらないこと・今月】RouteOPD の実装と再現。****RESEARCH_PIPELINE の「今月は R1 に絞る」方針は本日も有効である。**本論文は**読んで診断量を 2 つ持ち帰るところまで**で止め、実装には入らない。**今日この論文で手を動かすと、RoboPAD と CVPR の両方から時間を引くことになる。**
