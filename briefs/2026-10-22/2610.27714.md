## 何を解決する論文か

LLM を運転 agent にして、過去の経験を memory (類似場面を検索して prompt に入れる仕組み) として使うと性能が上がる、という報告が複数ある。この論文は、それらの gain が本当に memory の設計によるものかを、統制した評価でやり直す。主題は手法ではなく、評価の作法である。

## 手法の核心

- **warmup pool を確率変数として扱う**: memory に最初に入れる経験の集合 (warmup pool) を 10 通りの互いに素な集合で resample する。単一の pool での比較だと、選んだ pool の運で結論が決まる。
- **token-matched filler**: memory が prompt に足す token 数と同じ長さの無関係な文を入れる対照。memory の中身ではなく「prompt が長くなったこと」の効果を分離する。
- **audited baseline**: 既存手法 (DiLu の port など) の再実装品質を監査し、port の不備が結論を反転させていないかを定量化する。比較対象は flat-text retrieval、single-frame grid、episodic temporal-graph memory、retrieval-free の consolidated rulebook、K-step の observation history。
- **結果 (HighwayEnv 上、gpt-4o-mini)**: (1) 報告された gain は warmup pool の引きに属し、報告された pool は 10 個中の最良。2 つの retrieval memory が No-Memory に勝ったのは 10 pool 中 1 つだけ (sign test p=0.011)。(2) どの retrieval 設計も token-matched filler を超えない。collision-only の上限は 15 token の注意文 1 つで届く。(3) 表現の洗練が頑健に効く場面は無い。(4) baseline の port 品質が結論を反転させる。

## 適用可能性と実験アイデア

- **P1 (Planner AI + 評価)**: 直接の planner 実装知見というより、**closed-loop 評価の統制項目のチェックリスト**として使う。planner の比較実験で、(a) 初期条件・seed・データ分割を resample して分散を見ているか、(b) 入力に足した情報の量だけの効果を無関係な情報で対照しているか、(c) 比較相手の再実装を監査したか、を確認する。
  - 実験案 1 (最小): 手元の planner 比較で、最近出した「改善」について seed / scenario 抽出を 10 通り resample し、改善幅が分散の中に収まるかを見る。
  - 実験案 2: 条件入力 (route、目標速度、intent) を足した planner に、同じ token / 次元数の無関係な入力 (ノイズ、シャッフルした値) を足した対照を作り、条件入力の中身が効いているかを確認する。
- **P3**: LLM / VLM に memory や reasoning を足す設計の効果検証にも同じ対照が使える。
- 注意: HighwayEnv は 1Hz の単純な高速道路 simulator で、LLM は gpt-4o-mini。結論は著者が自ら「each a property of this testbed」と限定している。実運転の planner に直結する知見ではない。新手法ではないので、面白さは評価設計の部分に絞って読む。
