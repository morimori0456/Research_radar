# Structured Representation Probing for Risk Anticipation in End-to-End Autonomous Driving (2610.37299)

- トピック: next_arch として届いたが、内容は運転 policy の runtime 監視・評価なので P1 として採用 / スコア 4.5
- URL: https://arxiv.org/abs/2610.37299

## 何を解決する論文か

end-to-end driving policy (画像から軌道・制御まで 1 つの network で出す運転 model) は、内部に「周囲の車・自車・道路」の表現を持っている。この論文は、その内部表現を読んで「これから数秒以内に重大な失敗が起きそうか」を事前に警告する monitor を作る。従来の runtime monitor は、軌道や制御値、手で設計した特徴 (例: 時間方向の軌道のぶれ) から危険を推定するが、policy が内部で何を見ているかは使っていない。policy 本体を変えずに、後付けで失敗を予告できるのが狙い。

## 手法の核心

- **SRP (Structured Representation Probe)**: 凍結した policy から、actor (周囲の物体)・ego (自車)・map の 3 種類の表現を読み出す軽量 monitor。
- 表現の source ごとに **linear probe (線形の分類器で表現から情報を読み出す手法) の risk direction** を別々に学習する。どの種類の表現が危険を示しているかが分けて見える。
- 要素ごとのスコアを **cardinality-normalized log-mean-exp pooling** で集約する。log-mean-exp は max に近い集約で、目立つ危険の証拠に敏感なまま、token 数 (物体数) への依存を正規化で減らす。
- **event-window supervision**: 「この先の hard failure」の直前の窓に risk ラベルを付けて学習する。さらに failure の種類を当てる補助 head を足し、複数の失敗モードで risk direction を共同学習する。
- 推論時は 1 つの generic score で alert を出し、policy は変更しない。Bench2Drive (CARLA の closed-loop 運転 benchmark) で DriveTransformer・UniAD・VAD の 3 policy に適用し、frame 単位の PR-AUC・ROC-AUC が評価した runtime baseline より高い。DriveTransformer で 2 秒先の ROC-AUC は 0.833 (temporal consistency は 0.715)、runtime overhead は 2.67%。未知の route でも失敗の予兆を区別できる。

## P1 への適用可能性

- P1 の「評価指標」の観点で、2 つの使い道がある。(a) 本番の runtime monitor、(b) closed-loop 評価で「失敗の何秒前に警告できたか」を policy の評価軸に加える (失敗率だけでなく予測可能性を見る)。
- 候補の planner が複数あるなら、同じ probe 設計を別 policy に当てて、どの表現 (actor / ego / map) に危険が現れるかを比べると、planner の弱点の切り分けに使える。
- 注意点: 比較は simulation (Bench2Drive) 内で、実走行 log での確認は abstract に無い。2.67% の overhead は DriveTransformer での値。また監視対象の policy の内部表現にアクセスできる前提で、黒箱の planner には使えない。

## 試すべき実験アイデア

1. 手元の closed-loop 評価で失敗 (衝突・route 逸脱) の n 秒前の窓を切り、policy の中間表現から linear probe を学習して PR-AUC を見る最小版。まず単一の source (actor 表現だけ) で、手法のおおよその効果を確かめる。
2. 同じ probe を「軌道のぶれ (temporal consistency)」の単純な baseline と並べて比べる。論文の差 (0.833 対 0.715) が手元の policy でも出るかを見る。
3. 学習に使っていない route / 天候で probe を評価し、汎化が崩れる条件を調べる (論文は new route で保てると言うが、条件の幅は未確認)。

## 注意

abstract のみに基づく。probe の学習に必要な失敗事例の数、event window の長さ、false alarm の頻度 (運用上の許容度) は未確認。
