# PROOF-Gen: From Optimized Data to Better Distillation

- arXiv: https://arxiv.org/abs/2608.23911
- topic: **fm_distill_finetune** (P2) / hf_upvotes **0**
- 公開日: 2026-08-24 (Mon)
- relevance: P2 **4.5** / P1 **1.5** / P3 **1.0**
- 著者: Anh Ta, Junjie Zhu, Shahin Shayandeh

## 何を解決する論文か

**tool-calling (LLM が外部 API や関数を呼び出して仕事を進める能力) を実運用のモデルに載せる標準手順は、強力な teacher に軌跡を生成させ、それを SFT (Supervised Fine-Tuning; 生成された正解例を教師データとして student を学習させる工程) で student に写すことである。**実際に出荷されている tool-calling エージェントの post-training は、この工程を日次・週次で回し、**そのたびに frontier teacher の推論コストを払っている。**

問題は機構が **generate-and-filter — teacher が成功した軌跡だけ残し、失敗は捨てる**ことにある。**失敗は何の信号も生まないので、毎サイクル同じ難シナリオが取り残される。**τ2-bench では **teacher の試行の 57% が失敗し、その 3 分の 2 は near-miss (ツール呼び出しの大半は正しく、決定的な 1 手だけを誤ったもの)** である。**PROOF-Gen は、この捨てられていた失敗からシナリオ単位のプロンプト最適化で正解軌跡を回収する。**

## 手法の核心

- **失敗ごとに reflector が原因を書く。**失敗したタスクについて、reflector が実行トレースと評価フィードバックを読み、**そのシナリオ専用の修正指示 (corrective guidance) を文章として書く。** teacher はその指示を与えられて再試行し、通る軌跡を出す。**モデルの重みは一切触らず、プロンプトだけを動かしている。**

- **足場は学習前に外す。**ここが設計上の要点で、**生成された軌跡から corrective guidance を剥がしてから student に食わせる。**student が学ぶのは、タスク固有の足場が付いていない**きれいなデモンストレーション**である。student は「指示があれば解ける」ではなく「解ける」を学ぶ。

- **回収率が高い。**失敗シナリオの **93%** がシナリオ単位の最適化で回収された。teacher は最初から能力を持っていて、**引き出せていなかっただけ**だったことになる。near-miss が 3 分の 2 という診断と整合する。

- **student 側の伸びが大きい。**回収分を合わせたデータで fine-tuning すると、Qwen3-4B-Instruct-2507 が **Pass^1 = 0.132 → 0.529**、Gemma 4 E4B-it が BFCL v4 の multi-turn で **+7.2 ポイント**。

- **実運用パイプラインと端末上のモデルまで通っている。**軌跡品質が goal completion で +6.3 ポイント、**端末上で動く出荷済みモデルにも +1.5 ポイント転移**し、**測定した全ロケールで正の効果 (非英語平均 +1.48 ポイント)。**ベンチマークだけで閉じていない点が、recipe としての信頼性を上げている。

## 読むときの但し書き

- **Pass^1 0.132 → 0.529 の出発点が低すぎる。**4B モデルの tool-calling が元々ほぼ機能していなかったところからの改善なので、**「捨てていたデータを回収した効果」と「単にデータ量が増えた効果」が分離できていない。**同量のランダム追加データを与えた対照が要る。
- **reflector に評価フィードバックを読ませているので、evaluator の質が上限を決める。**評価器が「なぜ失敗したか」を返せないタスクでは、この機構は動かない。**τ2-bench や BFCL のように自動評価が明確な領域に強く依存している。**
- **回収 93% には、evaluator に対する過適合が混じりうる。**「評価を通る軌跡」と「正しい軌跡」が乖離している場合、**student は評価器の穴を学ぶ。**held-out の評価器での確認があるかは要チェック。
- **teacher の再試行コストがかかる。**frontier teacher のコストを下げるのが動機だったのに、失敗シナリオごとに reflector + 再生成を回す。**正味のコスト収支が本文に書かれているかは重要。**

## P1/P2/P3 への適用可能性

### P2 (FM 蒸留 + 適合) — topics.yaml が高優先とする「再現可能な recipe」であり、しかも蒸留の見落とされた側面を突いている

**この論文の持ち帰りは 1 行に畳める — 蒸留の質は student 側の loss ではなく、teacher 側のデータ生成の歩留まりで決まっていた。**蒸留の研究は蒸留 loss の設計に集中しがちだが、**その手前で teacher の出力の 57% が捨てられていたなら、そちらの方が支配的である。**

**「失敗は信号を生まない」という診断は、蒸留一般に効く。**soft label や中間表現の蒸留であっても、**teacher が誤った例をどう扱うかは通常「除外」であり、除外は毎回同じ場所に穴を残す。**本論文が示したのは、**その穴が固定されていること、そして穴の大半が回収可能なこと**である。

**R2 (蒸留の capacity gap の系統則) にも直接効く。**capacity gap は通常「student が小さすぎて teacher を真似られない」と説明されるが、**この論文は「teacher のデータが難シナリオで系統的に欠けている」という別の説明を提示している。**両者は観測上そっくりに見える — **student が小さいほど、欠けたデータの影響を受けやすいからである。R2 の予備実験を設計するとき、この交絡は最初に潰しておくべきである。**もし capacity gap の一部がデータの穴で説明できるなら、それ自体が R2 の主張になる。

**P2 のもう一方の軸「他ドメインへの適合」にも移る。**新しいドメインでの teacher の失敗率は、元ドメインより必ず高い。**ドメインギャップが大きいほど捨てられる割合が増え、この recipe の効きも大きくなる**はずである。**論文が測っていない条件で、論文の主張が強まる方向の予測**なので、検証する価値がある。

### P1 / P3 — 薄い

reflector に実行トレースを読ませて修正指示を書かせる構造は、planner の失敗分析にも形が移るが、本論文からの直接の持ち帰りは少ない。

## 試すべき実験アイデア

1. **手元の蒸留データの「捨てた率」を数える (2 時間、実装ほぼゼロ)。**
   過去に回した蒸留のログで、**teacher の生成のうち何割をフィルタで落としたか、落ちたものはどのシナリオに偏っているか**を集計する。**57% という数字が自分の設定でも同じ桁なら、この論文はそのまま適用対象である。**5% なら適用対象ではない。**この判定を先に済ませるのが最も安い。**学習を回さずに済む。

2. **回収データ vs 同量ランダム追加の対照実験 (2〜3 日、論文の弱点を突く)。**
   論文が持っていない対照 — **(a) 回収した失敗シナリオを足す、(b) 成功シナリオを同量だけ増やす。**両者が同じなら、効いていたのはデータ量である。差が出れば「**失敗シナリオには成功シナリオにない情報がある**」という、論文より強い主張が自分の手で立つ。**独立の貢献になりうる形をしている。**

3. **capacity gap とデータの穴を切り分ける (1 週間、R2 の本命)。**
   同じ teacher・同じデータで student サイズを振り、**(i) 生成をフィルタしたデータ、(ii) 回収込みのデータ**の 2 系列で性能曲線を引く。**2 本の曲線の差が student サイズとともに広がるなら、従来 capacity gap と呼ばれていたものの一部はデータの穴だったことになる。** R2 が探している系統則の、最初の図がこれである。
