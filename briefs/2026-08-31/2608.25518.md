# Agentic Game Development as a Verifiable Trajectory Data Engine for Scaling World Models

**topic:** sns_wildcard (内容は next_arch) / **project:** P3 (主) · P1 (副) / **hf_upvotes:** 151 (本日最高)
**スコア:** P1 **4.0** / P2 1.5 / P3 **4.5**

## 何を解決する論文か

world model (環境が次にどう変化するかを予測・シミュレートするモデル) をスケールさせる標準的な戦略は「もっと多くの収集動画を、もっと多くの計算で学習する」だが、著者はこれを非効率だと断じる。**足りないのはデータ量ではなく、学習を導く報酬が接地していないこと**である。code agent が伸びたのは、コードが実行可能で、compiler や runtime が RL post-training (事前学習後に強化学習で仕上げる工程) のための高品質な報酬を返せたからだ。対して空間生成の世界は、いまだに CLIP score (画像とテキストの一致度を測る学習済みスコア) のような**曖昧な代理指標**に頼っている。本論文は、この欠けている報酬環境として **game development** を持ち出し、game engine の検証機能と開発者の受理判断を組み合わせた post-training 手法 **RLHEV (Reinforcement Learning with Human-Engine Verification)** を提案する。

> **注意:** abstract の範囲では定量結果が示されていない。**これは手法論文というよりパラダイム提案 (position paper) として読むべきである。**下の適用可能性は、数字ではなく「報酬をどこから取るか」という設計原理に対して書いている。

## 手法の核心

- **診断: bottleneck は data ではなく reward の質である。**fuzzy proxy (CLIP score のような、ずれていても気づけない粗い代理指標) の上では RL post-training が成立しない。**この主張自体が本論文の一番の中身であり、RLHEV はその帰結にすぎない。**
- **game engine のシーンを "executable world specification" (実行して検証できる仕様) とみなす。**engine は collision (衝突)、physics (物理的整合)、navigability (通行可能性)、bounded playability (プレイとして成立する範囲か) を**安く・自動で・大量に**判定できる。**判定できるということは、報酬にできるということである。**これが dense signal (各ステップに与えられる密な報酬) を供給する。
- **開発者の「このシーンを採用するか」という判断を、global な検証信号として使う。**engine が返すのは部分的なチェックの集合でしかなく、それらを束ねて全体として良いかを言えるのは人間だけ。**RLHF (Reinforcement Learning from Human Feedback; 人間の好み比較で報酬モデルを作る手法) と違うのは、この信号が開発作業の副産物として自然に発生し、専用のアノテーション作業を必要としない点である。**
- **game development の過程そのものが long-horizon trajectory data (長い時間にわたる行動と結果の系列) を生む。**crawl した動画と決定的に違うのは、**行動と、その結果と、それが受理されたか否かが紐づいていること。**著者が data engine と呼ぶのはこの循環 — モデルが作る → engine が検証する → 人が受理する → 次の学習データになる。
- **RLHEV = dense engine signal + implicit human acceptance の 2 段構え。**細かい正しさは機械が、全体の妥当性は人が持つ、という報酬の役割分担。

## P1 / P2 / P3 への適用可能性

**この論文の骨子を自動運転に移すと、主張はこう読み替わる —— 我々はすでに executable world specification を持っている。simulator である。**

collision check、kinematic feasibility (車両の運動モデル上その軌跡が実現可能か)、drivable area 内か、TTC (Time-to-Collision; 衝突までの残り時間) が閾値を割ったか。**これらはすべて、学習済みモデルを一切使わずに engine 側で計算できる検証量である。**W35 で R1 の主指標候補に浮上した **solvability (いまこの状態から、まだ助かる候補が何本残っているか)** も、まさにこの種類の量だった。

**本論文が足す視点は方向である。**我々は engine 由来の量を**評価指標**として見てきたが、この論文は同じ量を**学習の報酬**として使えと言っている。そして重要なのはその裏返しで、**学習の報酬として使える量は、必ず gameable (抜け穴を突かれる) である。**08-29 の [PDPO](../2026-08-29/2608.27158.md) が示した「エージェントは指標の抜け穴へ逃げる」は、**この論文と表裏一体で読むべきである** —— RLHEV は engine チェックを報酬にするが、engine チェックを全部 pass しながら人間には受理されないシーンは必ず存在する。**著者が human acceptance を別立てで置いているのは、まさにその穴を埋めるためである。**

**P1 にとっての本題はここにある。**「engine が判定できる量」と「人間が介入する事象」の差分こそが、R1 が 9 週間探している**過保守**の居場所ではないか。engine 的には全部安全なのに人が踏む — それが過保守。engine 的には安全なのに人が危険と感じる — それも記録されるべき何かである。

**P3 (R3: VLA × world model 統合) には別の角度で効く。**W35 で 5 本が独立に収束した「**画素は world model の言語として粗すぎる**」という結論に対し、本論文は**学習信号の側から同じことを言っている** —— 画素の再構成誤差を最小化しても、通行可能性や物理的整合は保証されない。**逆に、engine が判定できる述語 (collision する/しない、通れる/通れない) を予測対象に据えれば、world model の出力は下流の planner が実際に使う形になる。**

**P2 への直接の適用は薄い (1.5)。**ただし構造だけは同じで、08-27 の [PROOF-Gen](../2026-08-27/2608.23911.md) の「teacher の生成物を検証器で篩にかけ、歩留まりを管理する」は、**検証器で捨てるという同一の型である。**

### 試すべき実験アイデア

1. **【最優先・紙 + 既存ログ・2 時間】走行ログのシーンに「engine だけで判定できるチェック」を列挙し、yes/no 表を作る。**collision / kinematic feasibility / drivable area / 信号・標識の遵守 / TTC 閾値。**R1 の指標のうち何割が人手なしで自動判定できるかが、この 1 枚で出る。**W35 で計画済みの solvability 後付け計算と**同じログ・同じ運動モデルで走るので、追加コストはほぼゼロ**である (08-26 の Apodex 1.1 で立てた「成否を人手なしで判定できるかの yes/no 棚卸し」と統合してよい)。
2. **【R1 の核心・半日】介入 (takeover) を implicit human acceptance の否定として読み替え、残差を取り出す。**走行ログから **「engine チェックが全部 pass しているのに、人間が介入したケース」** を抽出する。**この集合こそが、engine では測れない何か — 過保守か、あるいは engine のチェック漏れ — である。**件数がゼロに近ければ「engine チェックで評価は尽きる」ことの証拠になり、まとまった数が出れば**その中身の分類がそのまま R1 の貢献になる。**どちらに転んでも主張が 1 つ確定する、安い実験。
3. **【R3・学習環境が要る】world model の学習信号を、画素再構成から engine 述語の予測に差し替える最小実験。**予測対象だけを (a) 未来フレーム / (b) 未来の occupancy・通行可能性 に振り、下流 head を固定して差の符号を見る。**08-26 の [GeoWAM](../2026-08-26/2608.23486.md) で立てた depth 版の実験と同じ骨格なので、そちらに 3 本目の腕として足すのが安い。**
