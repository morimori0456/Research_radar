### 1. [RLHEV: game engine を「報酬環境」として使う](2608.25518.md) — P3 **4.5** / P1 **4.0** / hf **151**

**理由: この論文が言っていることを我々の文脈に翻訳すると、「我々はすでに報酬環境を持っている。simulator である」になるから。**

著者の診断は、world model (環境が次にどう変化するかを予測・シミュレートするモデル) がスケールしないのはデータ不足のせいではなく、**学習を導く報酬が接地していないから**、というもの。code agent が伸びたのは compiler や runtime が「正しいか」を機械的に返せたからで、対して空間生成は CLIP score (画像とテキストの一致度を測る学習済みスコア) のような**ずれていても気づけない代理指標**しか持っていない。

そこで著者は game engine を持ち出す。**engine にとってシーンとは「実行して検証できる仕様」であり、collision・physics・通行可能性・プレイとして成立するかを、安く・自動で・大量に判定できる。**判定できるということは、報酬にできるということである。

**ここが我々に効く。**自動運転の simulator が計算している collision check、kinematic feasibility (その軌跡が車両の運動モデル上で実現可能か)、drivable area、TTC (Time-to-Collision; 衝突までの残り時間) は、**まったく同じ種類の「学習済みモデルを使わずに判定できる量」である。**W35 で R1 の主指標候補に浮上した **solvability (いまこの状態から、まだ助かる候補が何本残っているか)** も、この仲間だった。

**そして本論文は、その量に対して我々が持っていなかった方向を足す。**我々は engine 由来の量を**評価指標**として見てきたが、この論文は同じ量を**学習の報酬**として使えと言う。**裏返しが重要である —— 報酬にできる量は、必ず抜け穴を突かれる。**08-29 の [PDPO](../2026-08-29/2608.27158.md) が示した「エージェントは指標の抜け穴へ逃げる」と表裏一体で、**著者が engine の判定とは別に「開発者がそのシーンを受理したか」という人間側の信号を置いているのは、まさにその穴を埋めるためである。**

**この構造を走行ログに移すと、R1 が 9 週間探している「過保守」の居場所が 1 つ指定できる —— engine のチェックが全部 pass しているのに、人間が介入したケース。**それが TOP3 の 3 番。

> **注意:** abstract の範囲に定量結果は無い。**手法論文ではなくパラダイム提案として読むこと。**価値は数字ではなく「報酬をどこから取るか」の設計原理にある。
