## 何を解決する論文か

end-to-end 自動運転モデル (センサ入力から中間表現を挟まず直接軌跡を出すモデル) は、NAVSIM や Bench2Drive のような **simulation ベースの指標**で評価される。これらは「人間の軌跡との差」を測っていた旧世代のベンチマークを改め、**安全で交通規則に適合した運転を捉えるつもりで**設計されている。高スコアは「モデルが目の前のシーンを理解して、それに応じて行動できた」ことを意味するはずである。

**著者はこう問う —— そのスコアのうち、シーンの「動いている部分」に反応したことで得られた分はどれだけか。**

調べ方が本論文の全てである。**モデルからカメラ入力を丸ごと取り上げ、代わりに「同じ場所を過去に走ったときの記憶」を与える。**記憶は道路形状や場所ごとの走り方の規則性 (この交差点では大抵こう曲がる、等) を持っているが、**いま前に何がいるかという現在の交通状態は一切持っていない。**

**結果: NAVSIM では記憶だけでほぼ十分だった。**評価対象のシーンを実際には見ていないにもかかわらず、主要な end-to-end 手法に**並ぶか、上回った。**

## 手法の核心

- **手法ではなく「情報を抜いた対照条件 (null model)」を作ることが貢献である。**通常の ablation はモジュールを外すが、ここで外すのは**入力の情報チャネルそのもの**であり、しかも **「測りたいと主張している能力だけ」を狙って外している。**
- **記憶の中身の設計が重要。**同一地点の過去走行から検索した情報を渡すので、**静的な場面理解 (道路レイアウト) と場所条件付きの事前分布 (location-conditioned regularity) は残り、動的な交通状態だけが消える。**「センサを切る」ではなく「静的成分は残してカメラを切る」という切り方なので、**残ったスコアは静的な事前知識だけで説明できる分に等しい。**
- **したがって `score(記憶のみ)` は、そのベンチマークにおける「反応しなくても取れる点数」の実測値になる。**裏返せば **`score(フル観測) − score(記憶のみ)` が、そのベンチマークが実際に測っている「動的シーンへの反応」の幅**である。この量には名前が付いていないが、**本論文の実質的な出力はこの差分である。**
- **効果はベンチマーク依存で、そこが二番目の主張。**NAVSIM ではほぼ落ちないが、**Bench2Drive と RealEngine では大幅に落ちる。**つまり **「ベンチマークが壊れている」ではなく「ベンチマークごとに反応の余地が違い、それを測れる」**という話になっている。
- 結論は控えめかつ強い: **NAVSIM の高スコアは、planner が現在の交通シーンに反応できることを要求しない。したがって慎重に扱うべきである。**

## P1 / P2 / P3 への適用可能性

**R1 にとって、これは今週最も直接的な材料である。**R1 の 3 本柱のうち **「抜け穴監査 (分母の健全性)」**は、W35 以降ずっと「やるべきなのは分かるが、どうやるのかが決まっていない」状態だった。**本論文はその手順を一つ完成形で示している。**

手順を一般形に書くとこうなる —— **測りたいと主張している能力「だけ」を取り上げた対照エージェントを作り、同じ指標で走らせる。対照エージェントが同等の点を取るなら、その指標はその能力を測っていない。**

**これは R1 の主指標候補である solvability (いまこの状態から、まだ助かる候補が何本残っているか) と、道具が完全に共通する。**solvability は kinematic rollout (車両の運動モデルで数秒先まで空走させる計算。学習不要) だけで出せる安い量で、**必要なのは走行ログと運動モデル**である。**記憶のみ条件を作るのにも同じログしか要らない。**09-01 の [LoopArena](../2026-09-01/2608.28281.md) が持ち込んだ Type I / Type III の対応の議論とも道具が同じで、**08-31 以降ずっと同じ半日の作業を指している。**

**さらに R1 の主張の形が一段強くなる。**R1 はこれまで「衝突率の隣に置く量を定義する」という**提案**の形をしていた。本論文の型を借りると、**「既存指標が測れていないことを実測で示し、その穴を埋める量として提案する」**という**証拠付きの形**になる。**RoboPAD @ NeurIPS 2026 (09-10 AoE / 4–9p / open-problem・benchmark・perspective 歓迎) は、まさにこの形の論文を募集している。**

**P3 への波及は間接的だが本質的である。**「静的な事前分布だけで動的タスクのスコアが取れてしまう」という現象は、world model の議論そのものである。本日の [Video World Models](2608.30692.md) が示した **「見えていない状態は pixel loss では監督されない」**と、**同じ穴を評価側から見た姿になっている。**片方は「モデルが hidden state を持っていない」、もう片方は「指標が hidden state を要求していない」。**両方が同時に成り立っているとき、誰も気付けない。**

**P2 は 1.0。**蒸留・適合とは接点がない。

### 試すべき実験アイデア

1. **【最優先・半日・09-06 の gate に直接効く】自分の走行ログで「記憶のみ」条件を作り、solvability と並べて 1 枚の図にする。**必要なのは (a) 同一地点の過去走行から作る静的事前分布、(b) 現在の他車情報を落とした条件、(c) 両条件での solvability の時系列。**主張は 1 行 —— 「既存の集約指標は両条件を区別しないが、solvability は区別する」。**区別すれば R1 の中心的な図がその場で出る。**区別しなければ、solvability の定義に何が足りないかがその場で分かる。**どちらでも 09-06 の gate に判断材料が揃う。
2. **【1 時間・紙のみ】「情報チャネル剥奪ラダー」の表を書く。**本論文は 1 段 (カメラ → 記憶) しかやっていないが、**チャネルは複数ある** —— 他車の現在位置 / 他車の速度 / 信号状態 / 自車の過去軌跡 / 地図。**各チャネルを 1 つずつ落としたときのスコア低下量を並べれば、「その指標が実際に何を要求しているか」のプロファイルになる。**09-01 の LoopArena の「何を固定するか」の表と同じ紙に書ける。**前提条件ゼロ。**
3. **【調べ物・30 分】NAVSIM と Bench2Drive で差が出た理由を原論文で確認する。**abstract は「ベンチマーク依存」としか言っていない。**open-loop か closed-loop か、シーンの選び方か、指標の集約方法か —— どれが効いているかで、R1 が「どのベンチマークに対して何を主張できるか」が決まる。**RoboPAD 投稿では、この切り分けを引用抜きで書くことはできない。
