# Can Video World Models Track Unobserved World States? — pixel loss は「見えていない状態」を一度も監督していない

**topic:** next_arch / **project:** P3 (主) · P1 (副) / **hf_upvotes:** 0
**スコア:** P1 3.0 / P2 2.0 / P3 **5.0**

## 何を解決する論文か

video world model (行動を条件に次のフレーム群を生成し、シミュレータとして使うモデル) は、生成映像の見た目が良くなるにつれて「世界を理解している」と扱われるようになった。**著者はここを切り離す —— 映像の忠実度は、モデルが世界の隠れ状態を保持している証拠にはならない。**

そこで **action-conditioned video Shell Game** を作る。カップの下にボールを隠して入れ替える、あのシェルゲームの映像版である。設計上重要なのは、**「描画」と「隠れ状態の合成」が分離されていること** —— カップの入れ替えを描くこと自体は簡単で、**難しいのは入れ替えの列を合成して「いまボールがどのカップの下か」を保ち続けることだけ。**これは $S_5$ state tracking (5 要素の置換を順に合成し続ける課題。系列モデルの状態保持能力を測る標準的な難問) の視覚版にあたる。

**結果: 学習時の 5 回の入れ替えには全モデルが適合し、それより長い列では正答率が偶然水準まで落ちる。それでいて映像はもっともらしいまま生成され続ける。**

## 手法の核心

- **落ちたのは bidirectional Transformer / autoregressive Transformer / Mamba (state space model の代表格。系列を固定サイズの再帰状態で処理する) / 遷移固有値を非負に制限した linear attention —— 現行の主要な選択肢がほぼ全滅している。**denoising のステップ数を増やしても改善しない。**計算を足せば済む問題ではない。**
- **原因の説明が本論文の核心。**pixel を予測対象とする diffusion の loss は、**画面に写っていない隠れ状態を一度も監督しない。**したがって**生成されたフレームは隠れ状態を運べない。**運べないなら、**状態は token の中ではなくアーキテクチャの中に居るしかない。**
- **Transformer の場合、そのアーキテクチャ側の状態は append-only な KV cache だけである。**追記しかできないので、**モデルは chunk ごとに履歴全体から隠れた配置を毎回導出し直す必要がある。**これは長さとともに難しくなる。**「状態を持っていない」のではなく「持ち方が追記のみで、書き換えられない」ことが効いている。**
- **外挿できた仕組みが 2 つあり、両方とも「状態を chunk をまたいで運び、その場で書き換える」性質を共有する。**
  - **linear attention の遷移固有値に負を許すと成功する。**非負に制限すると失敗する。**符号の反転が置換の合成に必要だった**という、極めて具体的な設計条件である。
  - **TTT (Test-Time Training; 推論中にモデル内部の「速い重み」を入力に応じて更新し続ける方式) を非線形な fast weight で使うと成功する。**自分の状態を読み出すための特徴写像そのものを更新している。
- より難しい dynamic world exploration の課題でも同様の検討を行い、**stateful な video world model を作るための設計要件として結論している。**

## P1 / P2 / P3 への適用可能性

**R3 の分類マップの第 1 軸「時間をどこに持つか」に、決定的な形が入った。**これまでこの軸は「履歴を入れるか / 潜在状態を持つか」という粗い二分だったが、**本論文はそこを 3 段に切る:**

1. **token の中に持つ** (履歴を全部読み直す) —— **pixel を予測目標にしている限り、そこに隠れ状態は載らない。**
2. **追記のみのアーキテクチャ状態に持つ** (KV cache) —— **書き換えられないので毎回導出し直しになり、外挿しない。**
3. **その場で書き換えられる状態に持つ** (負固有値を許す linear attention / TTT の fast weight) —— **外挿する。**

**そして W35 の収束点「画素は world model の言語として粗すぎる」に、初めて機構レベルの理由が付いた。**W35 は 5 本が独立に同じ結論に達したと整理したが、根拠はどれも**結果**だった (画素で学ぶと下流性能が伸びない)。**本論文が言っているのはもっと強い主張である —— 粗いのではなく、勾配が一度も届いていない。**見えていないものは pixel loss の中に現れないので、**学習信号としてゼロである。**「解像度を上げる」「denoise を増やす」で埋まらないのは当然で、実際に埋まっていない。

**P1 (R1) への効き方も具体的である。**本論文の評価設計は **「見た目の妥当さ」と「状態の正しさ」を意図的に分離した課題を作る**というものだった。**運転にはこの構造がそのまま存在する —— occlusion (遮蔽) である。**前の車に隠れて見えなくなった歩行者は、まさに「観測されない世界状態」であり、**軌跡は最後まで滑らかでもっともらしく描けるのに、状態としては間違っている。**本日の [Driving on Memory](2608.31029.md) が「指標が動的シーンへの反応を要求していない」と示したのと、**同じ穴を モデル側から見た姿**になっている。

**R1 の主指標候補 solvability にとっては、遮蔽が最も価値の出る条件である。**見えている範囲だけで数えた逃げ道の本数と、**遮蔽の裏に何かが居ると仮定したときの逃げ道の本数**は違う。**その差こそが「見えていないものを勘定に入れているか」の測定値になる。**

**P2 は 2.0。**TTT の fast weight を「推論時の適合」と読めば PEFT の隣接領域だが、本論文の主題ではない。

### 試すべき実験アイデア

1. **【半日・実験の道具は R1 と共通】走行ログの遮蔽区間だけを抜き出し、solvability を「見えている範囲のみ」と「遮蔽の裏を最悪ケースで埋める」の 2 通りで計算し、差を時系列で並べる。**本論文の Shell Game を運転に翻訳したものにあたる。**主張は「集約指標はこの 2 条件を区別しないが、solvability の差は遮蔽の入りと同時に立ち上がる」。**R1 にとっては、**「起きなかったことで測る」という主張が最も鮮明になる条件**である。
2. **【調べ物・1 時間・R3 向け】自分が候補に挙げている world model 系アーキテクチャを、本論文の 3 段 (token / 追記状態 / 書き換え可能状態) に分類する。**分類マップの第 1 軸を、この 3 段で置き換えられるかを確認する作業。**負固有値を許すか否かという条件は実装レベルで確認できるので、机上で終わる。**ただし **R3 は今月着手しない方針** (RESEARCH_PIPELINE.md) なので、**軸の更新だけ記録して手は動かさない。**
3. **【原論文の確認・30 分】5 回より長い入れ替え列で、失敗が「偶然水準まで落ちる」のか「徐々に劣化する」のかを確認する。**abstract は "fall toward chance" と書いており、**崖なのか坂なのかで意味が変わる。**崖なら「学習した horizon の外は原理的に別物」であり、坂なら「延長で緩和できる」。**R1 が長 horizon の評価を設計するときに、この区別が前提条件になる。**
