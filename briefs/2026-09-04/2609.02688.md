# PDT Framework — 「proxy が良くなった」を「運転が良くなった」と読み替える瞬間を、監査で潰す

**topic:** planner_ai / **project:** P1 / **hf_upvotes:** 0
**スコア:** P1 **5.0** / P2 2.0 / P3 3.0
**著者:** Yikai Wu (単著) / 2026-09-02 公開

## 何を解決する論文か

proposal-based planner (候補軌跡を何十本か出して 1 本を選ぶ方式の自動運転プランナー) の界隈では、future-aware representation や world model を足して「選び方が良くなった」と主張する論文が増えている。しかしその主張の根拠は、たいてい **proxy objective** (本当に測りたい運転性能の代わりに学習中に最小化している補助的な目的関数。ここでは候補ごとの良し悪しを当てる分類 loss) の改善か、データの一部だけを使った改善である。

本論文の指摘は、**その improvement が「候補の並び順」「実際に選ばれた軌跡」「全データでの効用」「安全に関わる要素」のどれ 1 つも確認されないまま planning gain として読み替えられている**、というものである。著者は **PDT (Proxy-to-Decision Transfer) Framework** —— 学習された未来情報が「運転性能が上がった」という主張をどこまで支えているかを判定する分析枠組み —— を提案し、NAVSIM-v1 上で実際に適用して、**代表的な future-aware planner の改善が decision に伝わっていない**ことを示している。

## 手法の核心

- **Decision-Transfer Decomposition Module** — proxy から decision への価値の漏れがどこで起きたかを 3 つの量で切り分ける。
  - **score margin** (1 位と 2 位の候補のスコア差。小さければ選択は僅差で決まっており、proxy の改善が順位を動かさない)
  - **switch-conditioned utility** (proxy の改善によって選ぶ軌跡が実際に切り替わった場面だけを取り出し、その切り替えが効用を上げたか下げたかを見る)
  - **support-versus-selection regret** (「候補の集合の中に良い軌跡が在ったか」と「それを選べたか」を分離する。前者が生成側の問題、後者が scorer の問題)
- **Reliability-Constrained Validation Module** — 主張が通るために満たすべき 6 条件を明示する。**exact pairing** (同一シーンで対にして比較する)、**minimum meaningful effect** (意味のある最小効果量を事前に決める)、**scale-expanded confirmation** (小さいサブセットで出た差を全データで再確認する)、**safety non-compensation** (安全の劣化を他の項目の改善で相殺させない)、**sequential comparability**、**family-level robustness** (設定群全体で頑健か)。
- **実測 1: proxy と decision が逆を向く。**component BCE (binary cross-entropy; 候補ごとの良し悪しを当てる分類 loss) が **0.705 → 0.530** と大きく下がるのに、実際に選ばれた軌跡の **PDM** (Predictive Driver Model score; 衝突・走行可能領域・進捗・快適性を合成した NAVSIM の運転スコア) は **0.963 → 0.961** と**わずかに悪化する。**
- **実測 2: 小さい窓でだけ有意になる。**別の候補は 512 件の prefix で **+0.00909**、scene-bootstrap (シーン単位で再標本化して信頼区間を出す手続き) の 95% 区間は **[0.000744, 0.0177]** で 0 を含まない。**しかし 2048 件と全データの区間は 0 を含む。**
- **実測 3: 頑健性ゲートを誰も通らない。****432 通りの設定を選別にかけて、two-half / two-seed (データを 2 分割し、乱数 seed を 2 つ振って両方で再現するか) のゲートを通過したものはゼロ。**
- PDT の出力は「改善した/しなかった」の二値ではなく、**「どこで transfer が失敗したか」あるいは「判定不能 (indeterminate) か」**の局在である。

## P1 / P2 / P3 への適用可能性

**この論文は、R1 にとって本日いちばん重要であり、同時にいちばん危険である。**

主張の骨格が R1 と重なっている。R1 は「閉ループ評価で、衝突率の隣に置く量を定義する」を主張する。PDT は「集約スコアの改善という主張が、決定の段階で消えていることを示す監査手続き」を提案する。**どちらも「1 つの数字に畳んだ時点で、消えたものが見えなくなる」と言っている。**

**したがって R1 の差分は、いま 1 行で書けるところまで狭まった。**

- **PDT は事後監査である。**走らせた後の結果 (選ばれた軌跡、そのスコア) を対にして、主張が統計的に成立するかを検定する。**失敗が起きてからでないと数えられない。**
- **R1 の solvability (いまこの状態から、まだ助かる候補が何本残っているか) は事前量である。**衝突が起きる前に、状態そのものから計算できる。

**この対比は、W36 の課題レーダーで拾った ASCEND の 3 要件 (objective / repeatable / proactive) の言葉でそのまま書ける。PDT は前 2 つを非常に強く満たし、3 つ目を満たさない。R1 は 3 つ目を埋めに行く。****この 1 段落が RoboPAD の related work であり、同時に R1 の存在理由である。**

**危険な側も正確に書いておく。**PDT の `support-versus-selection regret` は、**「候補集合の中に良い軌跡が在ったか」を分離して測る量**である。**これは R1 の solvability に最も近い既存量である。**違いは、PDT が **「良い軌跡が在ったか」を正解 (logged/oracle) との比較で事後に判定する**のに対し、R1 は **「まだ助かる候補が何本あるか」を現在の状態から前向きに数える**点にある。**この違いを R1 の図 1 のキャプションに明示できなければ、査読者は「support regret の言い換え」と読む。**

P3 は 3.0。future-aware representation と world model を planner に足す潮流そのものを検定にかけているので、R3 の分類マップに「その軸の値が実際に効いているかを誰が確かめたか」という列を足す材料にはなる。ただし今月は着手しない。

### 試すべき実験アイデア

1. **【30 分・09-06 gate の前提作業】Reliability-Constrained Validation の 6 条件を、R1 の図 1 のチェックリストとして先に写す。**特に **minimum meaningful effect を、図を作る前に決める。**R1 の toy 実証は「solvability が planner の順位を入れ替える」ことを示す図だが、**入れ替え幅をいくつ以上なら意味があるかを後から決めると、この論文と同じ穴に落ちる。**先に数字を宣言しておけば、10 月の実データ実験でそのまま使える。
2. **【半日・gate 本体と同時】走行ログ or 2D toy で solvability を計算するとき、PDM 相当の集約スコアも同時に出し、`switch-conditioned utility` の型で比べる。**具体的には「solvability で順位が入れ替わった場面だけ」を取り出し、その場面で集約スコアが何を言っていたかを表にする。**入れ替わった場面が数件しかなければ、R1 の主張はその時点で弱い —— それは 09-06 に知っておくべき事実である。**
