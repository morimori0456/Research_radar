# Discriminative World Models — 未来を正確に当てるのをやめ、候補を見分けられるように学習させる

**topic:** next_arch / **project:** P3 (+P1) / **hf_upvotes:** 0
**スコア:** P1 **4.0** / P2 2.5 / P3 **4.5**
**著者:** Kelvin Li, Dhruv Pendharkar, Anish Pahilajani, Chuyi Shang, Leon Oks / 2026-09-02 公開

## 何を解決する論文か

web agent (ブラウザを操作してタスクをこなす LLM エージェント) の最近の構成では、行動を選ぶ際に **world model** (行動を取ったら次に世界がどうなるかを予測するモデル) を使う。候補行動をいくつか出し、それぞれの結果状態を予測し、**ranker** や **PRM** (Process Reward Model; 最終結果ではなく途中の 1 手ごとに点を付ける報酬モデル) で並べて 1 つ選ぶ。

この world model は、ふつう **supervised next-state prediction** (正解の次状態を教師にして、HTML や **AXTree** (accessibility tree; ページの要素構造を木で表した表現) のスナップショットを生成させる) で学習される。

**本論文の指摘は、その学習目的が下流の使われ方とずれている、というものである。**ranker が必要としているのは「予測が正解にどれだけ近いか」ではなく、**「候補どうしを見分けられるか」**である。**正確だが候補間でほとんど同じ予測を返すモデルは、ranker にとって無価値になる。**

## 手法の核心

- **predicted-state matching** という学習目的を導入する。予測した表現は、**「本当に起きた結果状態」を「別の行動を取った場合に到達した状態」から区別できなければならない。**生成の忠実度ではなく、**候補間の弁別性を直接目的に置く。**
- **そのために分岐したデータが要る。****WebArena** の **Go-Browse** 軌跡から **branching dataset** を作る —— **各決定点に、複数の代替行動と、それぞれの結果状態が揃っている。**通常の軌跡データには「実際に取った 1 本」しか無いので、この構造を作ること自体が寄与である。
- **評価を 3 段に分けている。**① 自作の predicted-state matching ベンチマークで、supervised next-state 学習の world model を上回る。② **WebPRMBench** で、行動だけを見る PRM と「supervised world model を足した PRM」の両方より ranking が改善。③ **WebArena-Lite** で、実際に行動選択に使うと end-to-end のタスク成功率が上がる。
- **①→②→③ の並びは「代理指標 → 中間タスク → 実タスク」であり、代理の改善が最後まで伝わることを段階で示している。**

## P1 / P2 / P3 への適用可能性

**P3 から見ると、これは R3 の分類マップに新しい軸を 1 本足す論文である。**

R3 の軸は現在 3 本 —— ① 時間をどこに持つか ② 未来を 1 本返すか分布か ③ 終点か過程か・自己訂正するか。**本論文が示すのは 4 本目の候補である: 「world model は何のために正確であるべきか」。**忠実度 (fidelity) に最適化するのか、**候補の弁別性 (discriminability) に最適化するのか。**これは ② とは違う —— ② は出力の形式の話だが、こちらは **loss を誰の都合に合わせるかの話**である。ドメインは web だが、**「候補を出して選ぶ」構成は運転側と同型なので、軸としてはそのまま移る。**ただし **R3 は今月着手しない方針**なので、**軸の候補として記録するに留める。**

**P1 から見ると、こちらの方が今月は重い。**

R1 が定義しようとしている solvability / mode coverage は、いずれも **「候補集合の中で、選択肢がどれだけ区別できる形で残っているか」**を測る量である。**本論文は、その考え方を評価指標ではなく学習目的として実装し、「弁別性を目的に置くと下流が実際に良くなる」という証拠を出している。**

**R1 にとっての使い道は 2 つある。**

1. **主張の裏付け。**「集約された忠実度ではなく、候補間の弁別性を見よ」という論法が、**運転とは無関係な web の領域で独立に効いている。**RoboPAD の導入で、R1 の主張が運転固有の細工ではないことを 1 文で示せる。
2. **指標の合格条件。**本論文の①は、**「予測が候補を見分けられているか」を測る専用ベンチマークを別に作っている。**R1 も同じことをすべきである —— **solvability が「良い指標」であることを、planner の順位で示す前に、「同じ集約スコアを持つ 2 つの場面を solvability が分けられるか」で示す。**この中間段があると、10 月の実データで順位が動かなかった場合でも、指標自体の主張は残る。

**そして本日の [Versatile Samples](2609.01799.md) と噛み合う。**あちらは **branching に相当するデータを、運転側で人間の軌跡の摂動として作る方法**である。**こちらは、そのデータで何を学習/測定すべきかを言っている。****2 本合わせると「運転版の branching dataset を作り、弁別性で測る」という手順が丸ごと揃う。**

P2 は 2.5。学習目的を下流の使われ方に合わせて張り替えるという発想は R2 の「監督をどこに当てるか」と同型だが、対象が蒸留ではないので系統則には乗らない。

### 試すべき実験アイデア

1. **【30 分・図 1 の補助】[Versatile Samples](2609.01799.md) の摂動で作った候補集合に対し、「集約スコアは同じだが solvability が違う場面のペア」を探す。**見つかった数がそのまま、R1 の指標が持つ弁別力の下限になる。**ペアが 1 組も無ければ、solvability は集約スコアの関数でしかない —— それは 09-06 に知るべき最悪の結果であり、早く知るほど良い。**
2. **【メモのみ・R3 用】分類マップの 4 本目の軸として「world model を忠実度で学習するか弁別性で学習するか」を記録する。**着手は 10 月以降。
3. **【要確認・15 分】①の predicted-state matching ベンチマークの作り方 (負例をどう選んだか) を本文で確認する。**負例の選び方が難易度を決めるので、**R1 が同型の中間ベンチマークを作るなら、ここの設計をそのまま借りられる。**
