# Alaya-EVOKE: From Linear-Scaling Supervision to Endless World

**topic:** next_arch (P3) ・ **arXiv:** 2608.13546 ・ **published:** 2026-08-13 ・ **hf_upvotes: 113**

> **08-15 に「繰り上げ最優先」と記録した 1 本を、本日ようやく採用した。** 08-15 は relevance 4.5 でありながら next_arch の quota 2 から溢れただけ、08-16 は候補ゼロで採れず。**3 日越しの回収である。**
>
> **主張を一行で:** interactive world model (ユーザーの入力に応じて未来映像を生成し続けるモデル) が長い session を保てないのは、**履歴を全部 context に抱えているから**である。**幾何を外部メモリに退避させれば context は有界になり、session はいくら伸びても計算量が増えない。**
>
> **そして P2 に効くのはここ:** 3 ステップの student が、**CFG なしで**、**単一 H200 で 1.5 秒ぶんを 2.11 秒**で出す。

## 何を解決する論文か

interactive world model には **persistent memory (前に見た場所に戻ってきたとき、同じ景色であること)**、**responsive interaction (入力に即応する低遅延)**、**long-horizon generation (数十秒〜無限に続く生成)** の 3 つが同時に要る。**この 3 つは互いに食い合う。** 履歴を denoiser (拡散モデルでノイズを除去していく本体ネットワーク) の context や **KV cache (Key-Value cache; attention の過去分の中間結果を貯めて再計算を避ける仕組み)** に持てば、**session が伸びるほどコストが増える** —— つまり「どこまで覚えるか」と「どこまで続けられるか」を天秤にかけざるを得ない。一方で低遅延は **few-step generation (数ステップで生成を打ち切る蒸留済みモデル)** に頼るしかなく、その能力は **teacher の能力で上から抑えられる。**

本論文は **この 2 つの限界を、別々の場所で外す。** memory 側は **外部化** —— 幾何を denoiser の外に出す。teacher 側は **再設計** —— teacher を「固定された生成器」ではなく **「長horizon の監督を与えるための装置」として作り直す。**

**重要なのは後者の発想である。** 蒸留は普通「既にある強い teacher をどう写すか」の問題として立てられる。**本論文は「student に持たせたい能力から逆算して teacher を設計する」という順序で立てている。** 長horizon の drift に強い student が欲しいなら、**まず長horizon を監督できる teacher を作らなければならない。**

## 手法の核心

- **camera-indexed world state bank —— 幾何を context の外に出す。** scene geometry を外部の bank に持ち、**カメラ姿勢で索引を張る。** 生成時は **現在の視界に関係する情報だけを retrieve する。** これにより **session がいくら伸びても denoiser の context は有界のまま。** 「全部覚えて全部見る」から「全部覚えて、必要な分だけ見る」への切り替えである。

- **teacher の sparse attention は 3 つの機構の合成。** (1) **chunk-wise grouping** (時間方向をチャンクに切って、その中で密に見る)、(2) **retrieval of selected distant frames** (遠い過去から選んだフレームだけを引く)、(3) **linear-attention global state** (linear attention: attention を系列長に対して二乗ではなく線形の計算量に落とす近似。ここでは「要約された全体状態」を保つ役)。**結果としてメモリ・計算がともに系列長に線形。** 二乗のままでは teacher 自身が長horizon を見られないので、**これは student の性能の前提条件になっている。**

- **長horizon の監督が「局所的にはもっともらしい drift」を暴く。** 短い窓で見ている限り、生成は妥当に見える。**破綻は窓の外でしか観測できない** —— 少しずつ色が変わる、部屋の構造が入れ替わる、といった **content drift** である。teacher が長horizon を見られるようになって初めて、**この誤差に損失をかけられる。**

- **per-chunk conditioning で、生成の途中に介入できる。** チャンクごとに条件を与えるので、**系列の途中で prompt を変えたりイベントを起こしたりできる。** 「最初に指示して後は流れるだけ」ではない。**responsive interaction の実体はここ。**

- **30 秒の distribution-matching + self-forced rollout で 3 ステップ student へ転移。** **DMD (Distribution Matching Distillation; student の出力分布そのものを teacher の分布に合わせる蒸留。1 サンプルずつの再現ではなく分布を合わせる)** を **30 秒という長さの単位で**かける。**self-forced rollout (student 自身の生成結果を入力に戻して転がす。teacher の正解を毎ステップ与える teacher forcing の逆)** の下で行うので、**student は自分の誤差が積もった状態で訓練される** —— これが drift 耐性の出所である。**得られた student は 3 ステップ、かつ CFG (Classifier-Free Guidance; 条件付き/なしの 2 回推論を混ぜて条件への忠実性を上げる定番技法。推論コストが 2 倍になる) を使わない。**

- **数字。** 単一 H200、384×640 で **1.5 秒チャンクを 2.11 秒**で生成。**WBench で SOTA**、VBench-Long / VBench-2.0 でも competitive (いずれも動画生成の品質ベンチマーク)。**リアルタイムには 1.4 倍届いていない**が、研究用途では十分に回る速度である。

## 追っているプロジェクトへの適用可能性

- **P2 / R2 —— 本日いちばん直接効く部分。** 「3 ステップ + CFG なし」は、**推論コストが素朴な拡散の数十分の一**になることを意味する。**注目すべきは蒸留の設計順序のほうである:** 本論文は **student に欲しい能力 (長horizon 耐性) を先に決め、teacher をそれが監督できる形に作り替えた。** R2 は capacity gap (teacher と student の容量差が開くと蒸留が破綻する現象) の系統則を狙っているが、**本論文は「gap を student 側の容量で埋めるのではなく、teacher 側の監督範囲で埋める」という第 3 の軸を出している。** R2 の実験計画に **「teacher の監督 horizon」を軸として足す価値がある。**

- **P2 —— self-forced rollout は exposure bias 対策としてそのまま輸入できる。** 「訓練時は正解を与え、推論時は自分の出力を食う」というズレ (exposure bias) は蒸留全般で起きる。**運転の軌道予測でも、1 ステップ先の教師あり学習で訓練したモデルが自己回帰で転がすと崩れるのは同じ構造。** 実装は「rollout を自分の出力で回す」だけで、追加データは要らない。

- **P3 / R3 —— 分類マップの「memory の置き場所」列が、本論文で埋まる。** R3 のマップは 08-16 時点で 3 軸 (融合の高さ / planner コストになるか / 反実仮想に使えるか) が揃っている。**本論文は 4 本目の軸を要求する: world state を context に持つか、外部に持つか。** 外部化は **運転の long-horizon シミュレーションで決定的**になる —— 交差点を一周して戻ってきたとき、**さっき見た駐車車両が同じ場所にあるか**は、まさに persistent memory の問題である。

- **P1 —— closed-loop シミュレーションの生成側として。** camera-indexed な retrieve は **自車が同じ場所を再訪する運転シーンと相性が良い。** ただし本論文の評価は動画品質ベンチであり、**「planner を評価できるほど物理が正しいか」は一切示されていない。** ここは期待しすぎないこと。

- **留保:** (1) **ドメインが一般動画/ゲーム的な世界であり、運転ではない。** (2) **外部 bank は幾何を持つので、動く物体をどう扱うかが abstract からは読めない** —— 静的なシーン幾何を前提にしているなら、**交通参加者だらけの運転シーンでは前提が崩れる。** ここは本文を読んで最初に確認すべき点。(3) **リアルタイム未達** (2.11 秒 / 1.5 秒ぶん)。

### 試すべき実験

1. **self-forced rollout を、手持ちの軌道予測 student に足す (最優先・低コスト)。** teacher は現状のまま、**訓練ループを「自分の出力を入力に戻す」形に変えるだけ。** long-horizon での崩れが減るかは 1〜2 日で分かる。**効けば R2 の論文に「teacher を変えずに student の horizon 耐性だけ上げた」という統制された結果が 1 つ手に入る。**

2. **「teacher の監督 horizon」を R2 の軸として測る。** 同じ student 容量に対し、**teacher が監督できる horizon を 1 / 4 / 16 チャンクと変えて capacity gap の破綻境界が動くかを見る。** 本論文の主張が正しければ、**破綻境界は容量比だけでは決まらない。** これは R2 の系統則そのものを一段複雑にする —— **仮説が壊れるならむしろ早いほうがよい。**

3. **外部 memory bank の運転版プロトタイプ。** camera-indexed の索引を **自車位置 (BEV グリッド)** に張り替えて、静的シーン (建物・車線・駐車車両) だけを bank に置く。**動的物体は context に残す。** 「同じ交差点に戻ったとき景色が一致するか」を再訪一貫性として測る。**R3 の 4 本目の軸を、机上ではなく実装で埋める作業になる。**

4. **CFG なし 3 ステップ student の再現価値の確認。** ここは **効果量が大きいので追試の価値が高い**が、**まず 1 と 2 を先に回すこと。** 本論文の輸入コストで最も高いのはこの部分である。
