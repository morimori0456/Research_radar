## 何を解決する論文か

汎用の言語モデルは推論と知識の統合はできるが、**現実の仕事には「ファイル・情報源・実行可能なコードと持続的にやりとりし、状態を保ち、失敗から復帰し、成果を検証可能な形で出す」能力が要る。**著者はこれを **working capability (実務遂行能力; 現実の目標に向けて持続的かつ検証可能に前進する能力)** と呼び、**推論能力とは別の軸として明示的に扱う。**

Apodex 1.1 はこの能力を **2 つのスケーリング軸**で伸ばす。複雑な専門業務・金融・科学研究・数学・コーディング・検索の各領域で、**多くのフロンティア系より大幅に小さいモデルでありながら先頭集団の性能に達した**と報告している。**35B の Apodex 1.1 Mini はローカル配備可能な形で working capability を保持する。**

## 手法の核心

- **軸 1: Environment Scaling。**モデルではなく**環境の側**を増やす。ファイル操作・検索・コード実行の環境について、**diversity (多様性) と verifiability (検証可能性) の両方を拡大する。**ここで verifiability が並置されているのが要点で、**「多様な環境を大量に作る」だけでは足りず、成否が自動判定できることが条件になっている。**

- **軸 2: Agentic Coordination Scaling。**長時間タスクの **decompose (分解) → delegate (並列に委譲) → integrate (非同期の結果を統合) → replan (再計画)** という一連の振る舞い自体を学習対象にする。**協調を prompt の工夫ではなく学習で獲得させる**立場。

- **共有実行基盤 (execution harness と AgentOS) がタスク状態と provenance (どの結果がどこから来たかの由来) を、複数のツール・複数エージェントをまたいで保持する。** **provenance を明示的に持つ設計は、検証可能性を後段で成立させるための前提**になっている。

- **学習は環境の trajectory (実行の軌跡) と coordination trace (協調の記録) を材料にする。** **環境を作る → そこで動かす → 出た軌跡を学習データにする、という閉じたループ**が全体の構造。

- **主張の形は「小さいモデルで先頭集団」。**スケールではなく**環境と協調の設計で性能を出した**という位置取りで、これが 167 upvotes の理由でもある。

## なぜ探索枠で採るか — P1 の「評価環境をどう作るか」に構造が一致する

**分野は全く違う。それでも採るのは、この論文が解いている問題の形が、P1 の未解決部分と同型だからである。**

本日同時に採用した **[From Generation to Simulation](2608.23070.md)** が示したのは、**world model を simulator の代わりに使おうとすると state feedback (状態の読み出し) と再現性が足りない**という結論だった。**言い換えれば、P1 に足りないのは「多様で、かつ成否が自動判定できる評価環境」である。**

**Apodex 1.1 の Environment Scaling は、まさにその問題を別分野で正面から扱っている。**環境を増やすときに **diversity と verifiability を同時に要求する**という原則、そして **provenance を基盤側で持たせる**という設計判断は、**driving の closed-loop 評価環境を組むときにそのまま輸入できる考え方である。**シナリオを大量生成しても、**各シナリオの成否が自動で判定できなければ評価にならない** — これは今まさに P1 が直面している論点と同じ形をしている。

**逆に、モデルの中身 (agent の協調学習、AgentOS の実装) は P1/P2/P3 のいずれにも移らない。**そこは読み飛ばしてよい。**この論文から取るのは 1 つの原則だけである: 環境を増やすときは、多様性と検証可能性を必ず対で増やす。**

## 試すべき実験アイデア

1. **自分の評価シナリオを verifiability で棚卸しする (2 時間、実装ゼロ)。**
   手持ちの closed-loop 評価シナリオを列挙し、各々について **「成否を人手なしで判定できるか」を yes/no で埋める。** no が多ければ、シナリオを増やしても評価能力は増えていない。**Environment Scaling の原則を自分の系に当てた最初の一手で、しかも今日できる。**

2. **判定可能なシナリオだけで評価セットを組み直す (半日)。**
   1 で yes だったものだけを残した小さい評価セットを作り、**既存 planner を回して分散を見る。**小さくても自動判定できるセットは、大きくて手動判定のセットより回転が速い。**評価の回転速度が上がることが、実験着手の障壁を下げる方向に効く。**

3. **シナリオ生成に「判定器も一緒に生成する」制約を課す (1〜2 日、上記の後)。**
   新しい評価シナリオを作るときに、**シナリオと判定条件をセットでしか作れない形式**にする。Apodex の環境設計から取れる最も具体的な移植で、**以後の評価環境が構造的に verifiable になる。**
