## 何を解決する論文か

continual world model (展開中に新しいデータで自分を更新し続ける world model) は、新しいデータが来るたびに「更新するか、今のままでいるか」を決めなければならない。既存の方式 (決まった間隔で replay する、予測誤差が大きければ更新する) が決めているのは**いつ更新するか**だけで、**その 1 回の更新に価値があったか**は測れない。1 本の実行ログからは「同じ時点で更新しなかったら、どうなっていたか」が観測できないからである。

この論文は、その反実仮想の比較を直接観測できる実験プロトコル **fork ledger** を提案する。そして実際に測ってみると、**固定の更新手法を毎回適用すると、3 つの制御タスクすべてで return が下がった。**

## 手法の核心

- **事前に登録した判断点 (pre-registered decision points) で、実行を 2 本に分岐させる。**片方は更新する (update)、もう片方は今のパラメータのまま (hold)。判断点を後から選べないようにしておくことで、都合のいい地点だけを報告することを防ぐ。
- **2 本の分岐は common random numbers (CRN; 比較する 2 条件で乱数列を共有し、差のばらつきを小さくする分散削減の手法) で走らせ、同じエピソードで評価する。**記録するのは差 **ΔR = R_update − R_hold** (R はエピソードの return)。環境の乱数が同じなので、ΔR には更新の効果だけが残る。
- **推論の単位はタスク。**タスクごとに 240 本の fork (事前学習済み checkpoint 5 個 × データの drift 方向 2 通り) を走らせ、信頼区間は checkpoint 単位の bootstrap (標本を再抽出して区間を見積もる方法) で出す。
- **「更新が発散したケース」も除外しない。**発散は更新を適用した結果として起きることなので、試みた fork を全部数える。発散しなかった 693/720 本に絞った感度分析も並べて報告している。
- **実測: 更新は一貫して損だった。**CartPole ΔR = −144.0 (95% CI [−185.4, −116.1]、収束時の return は約 650)、Walker −82.8、Cheetah −18.6。発散を除くと Cheetah だけは符号が確定しなくなる (−3.9, CI [−17.5, +13.0])。

## 追っているプロジェクトへの適用可能性

### P1 (Planner AI + 評価) — planner の A/B 比較にそのまま移せる

この論文の中身は world model についての主張ではなく、**「2 つの版のどちらが良いかを、少ない試行で、ごまかしなく比べる手順」**である。planner の評価で毎回起きている問題と同じ形をしている。

- closed-loop simulation (planner の出力が次の状況を実際に変える評価設定) で planner A と B を比べるとき、**他車の挙動・センサノイズ・シナリオの初期条件の乱数が A と B で違うと、差の大部分がその乱数の差になる。**CRN で揃えれば、同じ試行回数でも ΔR の信頼区間は大きく縮む。
- **「発散したケースを除外しない」**という規則は、planner 評価の「シミュレーションが途中で落ちたエピソードをどう扱うか」にそのまま対応する。除外すると、壊れやすい planner ほど良く見える。
- **「推論の単位はタスク (シナリオの種類)」**という立場は、「1 万エピソードで有意差があった」式の報告を防ぐ。エピソード同士は独立ではない。

R1 の solvability (その状況で自車に残っている逃げ道の本数) を使って planner を並べるなら、**その比較の実験設計はこの論文の型で書ける。**指標をどれだけ作り込んでも、比較の手順がずさんだと査読で指摘されるのはそちらである。

### P3 (次世代アーキテクチャ) — 「オンラインで world model を更新すれば良くなる」は前提にできない

continual adaptation (展開しながら学習し続けること) は world model の売りとしてよく挙げられる。**この論文の結果は、少なくとも素朴な更新則ではそれが逆効果になりうることを示している。**P3 で「走行中に world model を適合させる」構成を検討するなら、更新するかどうかを決めるゲートが必要で、そのゲートの良し悪しは fork ledger で測れる。

### 試すべき実験

1. **(30 分・学習なし) 手元の 2 つの planner / 2 つの checkpoint で、「対 (paired) の比較」と「非対 (unpaired) の比較」の信頼区間の幅を比べる。**同じシナリオ・同じ seed で両方を走らせ、(a) 各エピソードの差を取ってから平均した場合と、(b) 別々に平均してから差を取った場合で、bootstrap の 95% 区間の幅を並べる。**(a) が (b) の半分以下なら、今の評価手順は必要な試行回数を数倍無駄にしている。**
2. **シミュレータの「落ちたエピソード」を除外した場合と含めた場合で、planner の順位が入れ替わるかを見る。**入れ替わるなら、今の評価指標は壊れやすさを報酬として扱っている。
3. (P3) world model を fine-tuning で更新する実験をするときは、**更新前の checkpoint を必ず残し、同じ評価セットで ΔR を記録する。**「更新したら良くなった」ではなく「更新しなかった場合より良くなった」を報告の形にする。

## 注意点

- 実験は CartPole / Walker / Cheetah という古典的な制御タスクだけで、world model も大規模なものではない。**「更新は損」という結論をそのまま一般化してはいけない。**一般化できるのは結論ではなく、測り方のほうである。
- CRN が効くのは、シミュレータの乱数を外から完全に制御できる場合に限られる。**マルチスレッドや非決定的な GPU 演算が混ざるシミュレータでは、seed を揃えても軌跡が一致しない。**導入前に「同じ seed で 2 回走らせて同じ結果になるか」を確かめること。
