# EnvHarness: Awakening Static Worlds for Agent Learning

- arXiv: https://arxiv.org/abs/2608.19880
- topic: **sns_wildcard** (分野外だが注目度の高い探索枠) / hf_upvotes **224** — 本日の候補中で最大
- 分野: LLM agent の学習環境。P1/P2/P3 のどれとも直接は重ならない

## 何を解決する論文か

LLM agent は環境と相互作用して学習する。ところがその環境は**人手で作られ、そして静的である。** agent の弱点がどこにあるかを環境は知らないし、agent が上達すると環境のほうが取り残されて、学習信号が枯れる。

近年の environment generation (学習環境を自動生成する研究) はこれに答えようとしたが、3 つの難点を抱えていた: ドメインごとに専用パイプラインが要る、高価または信頼できない verifier (生成したタスクの正解判定器) に依存する、そして**生成した環境がまた静的になる。**

EnvHarness の答えは「環境を作り直す」ではなく「**既存の環境を包む**」である。

## 手法の核心

- **EnvHarness = 差し込み可能なコンポーネント層**: 静的な環境の周りを包み、内部ロジックには一切手を入れずに、環境の振る舞いだけを作り変える。プログラム可能な wrapper 層と考えればよい。
- **標準インターフェース越しに動くので、ドメイン非依存**: 環境の中身を知らなくてよいため、専用パイプラインを組み直す必要がない。
- **元の verifier が必ず保持される**: 環境の中身を書き換えないので、その環境が元々持っていた正解判定はそのまま生き残る。**上記 3 難点のうち「verifier の信頼性」を、新しく作らないことで回避している。** 設計上いちばん賢い部分。
- **EnvRigger による自動化**: 対象方策を black box として扱い、その実行 trajectory を観察して弱点を診断し、その弱点を狙う EnvHarness コンポーネントを合成する。合成したものは新しい rollout で検証してから採用する。
- **結果**: 4 ドメイン 5 ベンチマークで、元の環境にもドメイン専用の環境生成パイプラインにも勝つ。held-out (学習に使っていない) インスタンスで最大 +9.0 ポイント、しかも実行ステップ数は 9.8% 少ない。RL の最適化信号としても優れ、**方策と環境が継続的に共進化する。**

## なぜこの枠で採るか / P1/P2/P3 への適用可能性

分野は LLM agent で、P1/P2/P3 のどれでもない。それでも本日の探索枠に採る理由は、**この論文の設計原理が P1 の評価環境の問題に、ほぼそのまま移せるからである。**

**P1 (planner + 評価) への移植。** 自動運転の closed-loop simulation は EnvHarness が批判している環境と同じ性質を持つ —— シナリオは人手で作られ、静的で、planner の弱点を知らない。planner が上達すると既存シナリオでは差が出なくなる。EnvRigger の発想 (方策の trajectory を観察して弱点を診断し、その弱点を狙う環境改変を合成し、新しい rollout で検証する) は、**adversarial scenario generation (planner を落としにいくシナリオの自動生成) をやりたいときの、そのままの設計図になる。**

そして最も効くのが「**元の verifier を保持する**」という原則である。自動運転のシナリオ生成が実務で信用されない最大の理由は、生成したシナリオの「正解」や「そもそも起こりうるか」を誰も保証できない点にある。既存シナリオを包んで改変し、元の評価規則を壊さない、という構成は、この不信に対する答えの形をしている。survey [2608.20111](2608.20111.md) が open challenge に挙げた **long-tail testing と reproducible benchmarking の両方に、同時に触れる位置**にある。

**R1 への含意。** R1 は「planner を測る指標」の側から入っているが、本論文が示すのは **測る対象を作る側 (環境) も方策に応じて動かないと、指標だけでは足りない**ということである。指標と環境を対にして設計する、という論点は R1 の主張を一段広くする。ただし広げすぎると論文が散るので、position paper の future work に置くのが妥当な扱いだろう。

### 試すべき実験アイデア

1. **既存の driving scenario 1 本に対して、EnvHarness 相当の wrapper を手で 3 つ書く** (他車の反応性を変える / 遮蔽を足す / 到着タイミングをずらす)。自前の planner の成功率がどれだけ動くかを見る。自動合成の前に、手書きで効果量を確認するのが安い。
2. **EnvRigger の「弱点診断 → 環境合成 → rollout で検証」ループのうち、診断だけを移植する。** planner の失敗 trajectory を集めて、失敗を説明する環境要因を分類する。これは合成なしで回せて、W34 課題カード1 の「臆病すぎる / 強引すぎる」の二分にそのまま繋がる。
3. **共進化の副作用を測る。** 環境が方策の弱点を狙い続けると、方策はその環境に過適合しうる。**held-out シナリオでの性能が、共進化のどの時点から落ち始めるか**を測る。論文は held-out で勝ったと報告しているが、閉ループで長く回した場合の話は別問題であり、ここは自分で確かめる価値がある。
