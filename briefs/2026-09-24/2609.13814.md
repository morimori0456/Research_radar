# Realtime-Venus: A full-duplex interaction system with asynchronous delegation

- **arXiv:** https://arxiv.org/abs/2609.13814
- **topic (割当):** sns_wildcard (探索枠) / hf_upvotes 199 (本日最高)
- **スコア:** P1 2.0 / P2 1.0 / P3 **2.5**
- **根拠:** abstract と arXiv HTML 版の本文 (§3 runtime、§5 harness、§7.6 delegate benchmark) を読んだ。
- **公開コード:** https://github.com/inclusionAI/Realtime-Venus

## 何を解決する論文か

音声や映像でリアルタイムに対話する AI は、聞きながら話す必要がある。full-duplex (相手の発話中も入力を受け続け、割り込みや相槌に即応する対話方式) である。一方で、検索やツール実行などの重い処理は数秒〜数十秒かかる。この論文は、**対話を止めずに重い処理を裏で走らせ、結果が返ってきたら会話の流れを崩さずに差し込む**仕組みを作った。9B の対話モデル 2 種 (映像+音声用、音声専用) と、裏の処理を管理する harness (モデルの外側で task の実行・管理をする仕組み) を組み合わせている。

## 手法の核心

- **dual-loop runtime (2 つのループを並走させる構成)。**前景の interaction loop が 1 秒単位の chunk で知覚・発話の判断を続ける。重い要求が来ると、モデルは自分で delegation request (裏の処理への依頼文) を出力する。それを受けた capability loop が非同期に実行する。前景は待たずに会話を続ける。
- **依頼時点の証拠を snapshot で固定する。**依頼には「依頼を出した時点で手元にあった観測」の snapshot を付けて確定させる。裏の処理はその snapshot だけを見る。そのため、実行中に前景の状況が変わっても、裏の入力は揺れない。
- **freshness deadline (結果の賞味期限)。**依頼ごとに期限を持たせる。結果ができた時点で期限切れなら、会話に戻さず捨てる。期限内の結果は private context (ユーザーには見えない内部メッセージ) として前景に渡る。**いつ口に出すかは前景モデルが会話の流れを見て決める。**「内容は裏が決め、タイミングは前景が決める」という分担である。
- **1 本の時系列に全部並べて学習する。**ユーザー入力、モデル出力、依頼、返ってきた結果を、同じ causal timeline (時刻順に並んだ 1 本の token 列) に置く。「いつ依頼を出すか」「返ってきた結果をいつ使うか」も、次 token 予測として学習させる。学習データ全体は約 2.8M 件で、そのうち delegation は約 6%。
- **「依頼すべきか」を単独で評価する。**自作の Delegate Benchmark で、task の成否とは切り離して「依頼を出すべき場面で出したか」を測る。依頼すべき場面での recall (取りこぼさない率) と、依頼不要な場面での specificity (余計に依頼しない率) を別々に出す。**音声モデルは recall 92% だが specificity 39% (何でも裏に投げる)。映像モデルは逆に specificity 84%、recall 68%。**overall の routing accuracy (依頼判断の正解率) は 76% / 69% で、判断を 1 つの数字にまとめると、この正反対の失敗の型が見えなくなる。

## プロジェクトへの適用可能性

### P3 (次世代アーキテクチャ) — 2.5: dual-system 運転 VLA の「遅い結果をどう扱うか」の設計例

運転の VLA (Vision-Language-Action; 画像と言語から行動を出すモデル) には、dual-system 構成がある。重い VLM (画像を理解する大型言語モデル) が低頻度で考える slow 系と、軽い planner が高頻度で軌道を出す fast 系を組み合わせる ([07-16 ABot-N1](../2026-07-16/2607.10383.md) でも扱った)。**この構成の弱点は、slow 系の出力が届く頃には状況が変わっていることである。**多くの論文は「最新の slow 出力を常に使う」で済ませている。

Realtime-Venus はこの問題に 3 つの明示的な答えを出している。

1. **slow 系の入力は依頼時点の snapshot に固定する。**
2. **結果には賞味期限を付け、期限切れなら捨てる。**
3. **結果を使うタイミングは fast 系が決める。**

いずれも運転へそのまま持ち込める仮説である。運転では「期限切れで捨てる」の基準を時間ではなく状況の変化量 (例: 自車の移動距離や周辺物体の位置ずれ) にする方が自然だろう。ここは論文には無い拡張である。

**実験アイデア (1 日・GPU 不要・2D toy で可):**
1. 2D toy の planner を 2 層にする。fast 系は毎 step 軌道を出す。slow 系は N step ごとに「目標レーン」などの高レベル指示を出し、指示は K step 遅れて届く (遅延は擬似的に与える。VLM は不要)。
2. 指示の扱いを 3 通り比べる: (a) 届いた指示を常に採用する、(b) 賞味期限 T step を超えたら捨てる、(c) 依頼時と到着時の状況差 (例: 周辺車両の位置変化) が閾値を超えたら捨てる。
3. K を 0〜20 step で振り、衝突率と目標到達率をプロットする。
4. **判定:** K が大きいとき (b)(c) が (a) より衝突率で勝てば、「遅い結果を捨てる規則」が設計軸になる。R3 の分類マップに「slow 系の出力の鮮度をどう扱うか」の軸を 1 本足す根拠になる。差が出なければ、toy の環境変化が遅すぎる。周辺車両の速度を上げて再確認する。

**R3 は今月は着手しない方針なので、実験は積まない。**分類マップ用のメモとして残すに留める。

### P1 (Planner AI + 評価) — 2.0: 「判断」と「結果」を分けて評価する形

Delegate Benchmark の作り方は、planner 評価にも使える。**「介入すべき場面で介入したか」(recall) と「不要な場面で介入しなかったか」(specificity) を別々に測る。**これを、planner の緊急ブレーキやフォールバック (安全側の代替動作への切り替え) の判断にそのまま当てはめられる。1 つの正解率にまとめると、「何でもブレーキ」と「ほぼブレーキしない」が同じ点に見える。R1 で新しい指標を作るときにも、1 つの数字に潰していないかの点検項目になる。新しい実験は不要で、R1 の指標設計メモに 1 行足せば済む。

### P2 (蒸留 + fine-tuning) — 1.0

MiniCPM-o 4.5 (公開の 9B マルチモーダルモデル) を post-training (事前学習後の追加学習) で対話用に適合させている。ただし、蒸留や少データ適合の工夫は論文の主題ではない。

## 読むときの但し書き

- Delegate Benchmark は自作 (in-house) で、公開されているかは本文から確認できなかった。
- 裏の処理が遅れたとき、会話品質や遅延がどう変わるかの定量評価は見当たらない。freshness deadline の値をどう決めたか、何割の結果が期限切れで捨てられたかも書かれていない。**運転への移植で一番知りたい数字は、この論文には無い。**
