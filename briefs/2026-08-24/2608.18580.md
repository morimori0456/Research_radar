# FACET: Preserving Source Intent and Executable State in Terminal Task Synthesis

- arXiv: https://arxiv.org/abs/2608.18580
- topic: **sns_wildcard** (分野外だが注目度の高い探索枠) / hf_upvotes **114** — 本日の候補中で最大 (重複を除く)
- 分野: terminal agent (シェル/コマンドラインを操作する LLM agent) の学習データ合成
- 公開日: 2026-08-18 (本日の候補では 6 日前。lookback_days:2 を超過 — 後述の欠陥#3 による)

## 何を解決する論文か

terminal agent を学習させるには、**executable supervision** (実際に実行して正解/不正解を機械的に判定できる教師信号) が大量に要る。ところがその学習タスクを自動合成するのが難しい。1 個のタスクは 4 つの成果物 (artifact) が噛み合って初めて成立するからである — instruction (指示文)、初期化済みの環境、reference solution (模範解答)、そして executable verifier (実行結果から正誤を判定するプログラム)。

**この 4 つが食い違った前提から別々に生成されると、そのタスクは「解けない」か「誤って採点される」かのどちらかになる。** さらに多段階の合成パイプラインは、元ソースが持っていた目的・依存関係・状態遷移・手続き上の制約を、段を経るごとに捨ててしまう。FACET (Fine-grained Agentic Construction of Executable Tasks) は、この **情報の保存** と **成果物間の整合性** の 2 つを同時に狙う枠組みである。

## 手法の核心

- **生成の順序を変える。** 従来は指示文から出発して環境を後付けするが、FACET は **先に実行環境を実現 (realize) して修復してから**、その環境を土台に最終成果物を生成する。順序そのものが手法の主張になっている。
- **container state を共有 grounding にする。** 出来上がったコンテナの実状態 (どのファイルがあり、どのプロセスが動き、どの依存が入っているか) を、instruction・solution・verifier の 3 つが**同じ 1 つの参照点**として使う。食い違いは「別々の前提から書いたから」起きるので、前提を 1 個に物理的に固定して潰す。
- **agent skill の再構成。** 関連する複数のスキルを、まとまりのある情報密度の高いシナリオへ組み直す。元ソースの意図 (source intent) を段階間で落とさないための設計。
- **execution-based validation + targeted repair。** 実際に実行して壊れている成果物を特定し、**壊れたものだけを狙って修復する。**正常な成果物を巻き込んで再生成しない。合成コストが素直に効く部分。
- **結果**: dense executable checks (1 タスクあたりの実行チェックが密) な複雑タスクが得られ、そこから集めた成功 trajectory (成功した実行系列) で fine-tuning すると、**複数のモデル規模で一貫して** Terminal-Bench 2.1 (ターミナル操作 agent のベンチマーク) の性能が上がる。生成方式を差し替えた比較が、environment-grounded な構成が **task validity (タスクが本当に成立しているか)** に効くことを支持している。

## P1/P2/P3 への適用可能性

分野は terminal agent で、P1/P2/P3 のどれとも直接は重ならない。それでも探索枠に採るのは、**「4 つの成果物が 1 つの実状態を共有していないと、生成したタスクは評価に使えない」という主張が、P1 のシナリオ生成の急所とそのまま同じ形をしているからである。**

**P1 (planner + 評価) への移植 — 本日の主眼。** 自動運転の評価シナリオも、実は同じ 4 点セットである: 指示 (どこへ何をする意図か)、初期シーン状態、reference behavior (模範となる走行)、そして評価指標/判定規則。**シナリオ生成が実務で信用されない理由は、この 4 つが別々に作られて整合していないこと**に相当する — 初期配置からして物理的に回避不能なのに「衝突した」と減点する、模範解答が存在しないシナリオを平均に混ぜる、といった形で現れる。FACET の答えは「**先にシーンを実現して修復し、成立したその状態から指示・模範・判定を導出する**」であり、これは順序を入れ替えるだけで実装できる。

**08-22 の [EnvHarness](../2026-08-22/2608.19880.md) との関係が本日いちばんの収穫である。** 両者は同じ不信 (生成シナリオの正解を誰も保証できない) に、**正反対の方向から**答えている。EnvHarness は既存環境を包んで **元の verifier を壊さない**ことで保証する。FACET は **実状態を共有 grounding にして新しい verifier を整合的に作る**ことで保証する。前者は既存シナリオ資産がある場合に、後者は新規シナリオを増やしたい場合に効く。**R1 (HIL評価 × conformal 安全指標) の position paper で「シナリオの信頼性をどう担保するか」を書くなら、この 2 つは対になる引用になる。**

**P2 (蒸留 + 適合) への含意。** 本論文の fine-tuning は「良いタスクから採れた成功 trajectory は data-efficient な教師信号になる」と言っている。これは R2 (蒸留の capacity gap 系統則) に **データ側の変数**を 1 本足す — teacher/student 比だけでなく、**教師データの verifier 密度**が破綻境界を動かす可能性がある。

**P3 への寄与は薄い。** アーキテクチャの主張はない。

### 試すべき実験アイデア

1. **順序の効果だけを切り分ける (最も安い)。** 手持ちの driving scenario を 10 本、2 通りで作る — (a) 指示文から出発して初期配置を後付け、(b) 初期配置を先に実現・修復してから指示と判定を導出。**「解けない/誤採点されるシナリオ」の混入率**を数える。FACET の主張が自分のドメインで再現するかを、モデル学習なしで確認できる。
2. **targeted repair の歩留まりを測る。** 壊れたシナリオを丸ごと再生成する場合と、壊れた成果物だけ直す場合で、**成立シナリオ 1 本あたりの生成コスト**を比較する。これは実務でそのまま効く数字になる。
3. **R2 に繋ぐ。** verifier のチェックが密なタスク由来の trajectory と、疎なタスク由来のものとで student を fine-tuning し、**capacity gap の破綻境界がデータ品質でどれだけ動くか**を見る。R2 の系統則にデータ軸を 1 本追加する予備実験になる。
