## 何を解決する論文か

**on-policy distillation (OPD; student に自分で回答を生成させ、その出力を teacher が採点・矯正する形の蒸留。teacher が作った固定コーパスを真似させる従来型と対照的)** には、**length inflation** という実務上うるさい破綻がある —— 学習が進むにつれて student の回答が際限なく長くなり、生成 budget を使い切って打ち切られるようになる。

この論文は、その原因の 1 つを**拍子抜けするほど具体的な場所**に特定した: **base の student と post-trained の teacher が、「止まれ」の確率を別々の EOS token (end-of-sequence; デコーダに生成終了を伝える特殊トークン) に置いている。**しかも**両者の「停止トークン集合」の宣言は同一**なので、設定ファイルを見比べても気づけない。Qwen3 / Llama / Gemma の 3 系統すべてで起きる。

## 手法の核心

- **診断: termination-token mismatch。**停止トークン集合が同じでも、その集合**内部での確率質量の置き方**が teacher と student で違う。チャットテンプレートを持つモデルには `<|im_end|>` 系と `<|endoftext|>` 系のように**機能的に等価な EOS が複数ある**のが普通で、どちらに質量を置くかは post-training で変わる。
- **なぜ「伸びる」のか (機序):** OPD の勾配は、**student が好む停止トークンを押し下げる** (teacher がそこに質量を置いていないため) が、**teacher が好む代替トークンを確実に持ち上げるとは限らない。**結果、**どの停止トークンにも十分な質量が乗らない状態**になり、生成が止まらなくなる。「片方を消すが、もう片方を渡せない」という非対称が本体。
- **デコード側の停止集合を揃えるだけでは不十分** —— これが一番に思いつく対処だが、**効かないことを実験で示している。**揃えるべきは推論時の停止条件ではなく **loss の側**。
- **効く対処: 機能的に等価な EOS 群を「1 つの共有された意味的停止アクション」として扱う。**すなわち蒸留目標を計算する前に**それらの確率質量を合算**し、トークン単位で照合するのをやめる。3 系統すべてで mismatch 由来の inflation が大幅に緩和。
- **学習段階を追った分析 (K2-Horizon の各段階で OPD):** 停止の好みは**学習中に大きく動く** (固定の性質ではない)。さらに **OPD の後半に、termination alignment を施しても消えない別種の length inflation** が現れる。著者自身が「termination mismatch は重要だが唯一の原因ではない」と明記している。
- **実装公開あり** (termination-handling の修正を組み込んだもの)。

## 追っているプロジェクトへの適用可能性

### P2 / R2 — 「蒸留の破綻境界」に、3 つ目の、しかも最も安く検査できる説明が加わった

`RESEARCH_PIPELINE.md` の **R2 (蒸留の破綻境界)** は現在、説明候補を 2 つ持っている: **① CLL 集中度 (UC-MOPD 由来) / ② clipping で切り捨てられる推論 token (Echo-GRPO 由来)。**そして「容量比 1.0 でも蒸留が効く反例 5 本」で**当初の「容量差が原因」という前提は既に棄却済み**である。

**本論文は 3 つ目の説明候補を出すが、性質が前の 2 つと決定的に違う:**

| 説明 | 原因の所在 | 検査コスト |
|---|---|---|
| ① CLL 集中度 | 学習ダイナミクス (分布の形) | 過去ログに後付け計算 |
| ② clipping で捨てる token | 目的関数の設計 | 再学習が要る場合が多い |
| **③ EOS mismatch** | **語彙・テンプレートの食い違い** | **再学習不要・ログの 1 位置だけ見ればよい** |

**③ は「モデルの性質」ですらない —— tokenizer とチャットテンプレートの事故である。**だからこそ**交絡因子として真っ先に潰しておく価値がある。**①②の効果を測る前に③が混ざっていると、「破綻した run」の集合に③由来のものが紛れ込み、①の相関を汚す。

### 試すべき実験 —— 再学習ゼロ、過去ログだけで YES/NO が出る

1. **過去の蒸留 run それぞれについて、teacher と student の「宣言された停止トークン集合」を列挙する** (tokenizer の設定と生成設定から取れる)。
2. **各 run の最終位置で、その集合の各トークンに teacher / student がどれだけ確率を置いているかを出し、argmax を比較する。**argmax が食い違う run = **mismatch あり。**
3. **mismatch の有無で run を 2 群に分け、「学習中の平均応答長の伸び」を並べる。**
4. **判定:**
   - **伸びた run が mismatch 群に偏る** → **R2 の過去の観測の一部は③を測っていた。**①の相関を測り直す必要がある (これは R2 にとって悪い知らせだが、**知らずに①で論文を書くよりはるかに良い**)。
   - **偏らない** → **①②が本物の交絡因子検査を 1 つ通過した。**R2 の主張が強くなる。

> **どちらに転んでも R2 は前に進む。**しかも**必要なのは既存ログの読み出しだけで、GPU は 1 分も要らない。**R1 に絞る方針 (2026-09) と衝突しないのはこの点による —— これは新しい種ではなく、**既にある R2 の前提検査**である。

**もう 1 つ持ち帰る点:** 著者が報告した「**alignment 後も残る後半の inflation**」は、①②が説明すべき残差そのものである。③を除去した後に残る伸びこそが R2 の測定対象、という切り分けができる。

### P3 — VLA の action chunk の終端にも同じ形の問題がありうる (1.0)

**VLA (Vision-Language-Action; 視覚と言語を入力に、ロボット/車両の行動を直接出力するモデル) の action chunk (複数ステップ分の行動をまとめて 1 回で出す出力単位)** は**可変長**で扱うことがあり、その場合「chunk の終わり」を表すトークンが要る。base モデルから蒸留・fine-tuning する構成なら、原理的に同じ mismatch が起きうる。**ただし本論文は言語モデルしか扱っておらず、これは類推であって裏付けではない。**確認は安い (終端トークンの確率を見るだけ) ので、VLA の蒸留をやる時にチェックリストに 1 行足す、程度の扱いが妥当。
