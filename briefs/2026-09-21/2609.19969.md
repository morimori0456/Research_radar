# DeepSeek-V4.1-Flash — 「読む」ときと「書く」ときで活性パラメータ数を変える。持ち帰るのは KV の数字ではなく、この非対称

**topic:** sns_wildcard (EXPLORE) / **project: P3** (+P2 少し)
**hf_upvotes:** 131 (本日最高) / **公開 (HF の publishedAt):** 2026-09-16T20:00Z
**スコア:** **P3 3.5** / P2 2.0 / P1 0.5

> **本日 3 件の中で、唯一「分野外の探索枠」に本当に該当する 1 件。**next_arch の keyword (`efficient transformer` 等) には 1 つもヒットしない、datacenter の推論基盤の論文である。**それでも採ったのは、後述する CED の非対称性が P3 で未使用だから。**

## 何を解決する論文か

**long-horizon agent (長い手順を自律的に回し続けるエージェント) のワークロードは input-heavy である** —— 読ませる文脈が巨大で、生成する出力は相対的に短い。この形だと **prefill (入力を一度に読んで内部状態を作る段階。出力の生成前に行う)** の計算が重く、さらに **KV cache (attention の key/value を保存して再計算を避ける仕組み。文脈が長いほど際限なく膨らむ)** が **HBM (High Bandwidth Memory; GPU に直付けされた高速メモリ。容量が小さく、ここが最初に足りなくなる)** と SSD の容量、そして転送帯域を圧迫する。

DeepSeek-V4.1-Flash は、**552B の backbone を持つマルチモーダル MoE (Mixture-of-Experts; トークンごとに一部の expert だけを活性化し、総パラメータ数と 1 トークンあたりの計算量を切り離す構成)** で、文脈長 100 万トークンに対応しつつ、**計算・容量・帯域の 3 つを同時に下げる**ことを狙った設計である。

## 手法の核心

- **CED (Causal Encoder-Decoder) —— 段階ごとに活性パラメータ数が違う。**decode 時は 1 トークンあたり **16B** を活性化するが、**prefill 時は 8B しか活性化しない。「読む」のは「書く」の半分のコストで済ませる。**agentic な用途でコスト効率が大きく改善する、というのが売り。**この論文で唯一、構造として新しいのはここ。**
- **CSA2 (Compressed Sparse Attention 2) + 層をまたいだ KV の再利用。**各層が自前の KV を持つのをやめ、層間で共有する。
- **FP4 KV caching** —— KV cache を 4bit 浮動小数点で保持する。
- **結果: 常時 HBM に載せる global KV は 890 bytes/token**、前世代 DeepSeek-V4-Flash の**約 1/4。**
- **SWA Bounded Replay** —— SSD / ホストメモリに常駐する persistent KV 側の配置最適化で、こちらは**約 1/8** に。**SWA (Sliding Window Attention; 全トークンではなく直近の窓だけを見る attention)** の範囲に限り、**保存せず再計算で復元する量に上限を設ける**という発想。
- **KV を大幅に削ったのに baseline より性能は上、**と報告している。

## 追っているプロジェクトへの適用可能性

### P3 —— 持ち帰るべきは CED の非対称性。VLA は構造的に同じ形をしている

**KV の数字 (890 bytes/token、1/4、1/8) は P3 にそのまま移らない。**552B のモデルを datacenter で捌く話であり、車載の運転モデルは桁が 2〜3 つ小さく、**ボトルネックも「HBM の容量」ではなく「制御周期あたりのレイテンシ」**である。この点は割り引く必要がある。

**移るのは CED の主張の方である: prefill と decode は別の仕事なので、同じだけのパラメータを使う理由は無い。**

**VLA (Vision-Language-Action; 視覚と言語を入力に行動を直接出力するモデル) はまさにこの非対称を持っている:**

| | 中身 | 量 |
|---|---|---|
| **prefill 側** | 複数カメラの画像 token、地図、指示文、走行履歴 | **巨大** |
| **decode 側** | action chunk (複数ステップ分の行動をまとめた出力単位) | **数十 token** |

**にもかかわらず、現行の VLA は両方を同じ 1 本の trunk で同じ容量で処理している。**CED は「入力側を半分の活性パラメータで済ませてよい」と 552B 規模で実証しており、**この比が VLA でもっと極端なら、削れる余地はもっと大きいはずである。**

### 試すべき実験 —— まず 30 分の測定で前提を潰す

1. **手元の VLA / driving policy を 1 本選び、1 制御ステップあたりの prefill token 数と decode token 数を数える。**コードを変えずログを 1 行足すだけで出る。
2. **判定:** 比が 1 桁以上開いていなければ **NO** —— CED の前提 (input-heavy) がそもそも成り立たないので、ここで打ち切る。**この時点で捨てられるのが重要。**
3. **YES なら、学習せずに推論時だけの ablation を試す:** MoE 構成なら **context token の top-k を下げ、action token の top-k は据え置く。**性能劣化を測る。劣化が小さければ「非対称にして良い」ことの安い証拠になる。
4. **これとは独立に、FP4 KV cache は構造を変えずに試せる。**車載のメモリ予算に直接効くので、既存モデルへの量子化 ablation として単独で価値がある。

> **1→2 は本日の 3 件の中で最も早く NO が出る実験であり、それが利点である。**P3 は今月着手しない方針なので、**2 で NO なら在庫にも積まずに捨ててよい。**

### P2 —— 直接の関係は薄い (2.0)

蒸留の論文ではない。**唯一つながるのは「teacher の推論コストが下がれば、on-policy 蒸留で teacher を呼ぶ回数を増やせる」**という運用面の話で、手法上の示唆ではない。本日の [EOS mismatch の論文](2609.20511.md) の方が P2 には比較にならないほど近い。
