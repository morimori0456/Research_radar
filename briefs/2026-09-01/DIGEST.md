### 1. [LoopArena — 安い指標と高い指標を、対にして同時に作る](2608.28281.md) — P1 **3.5** / hf **82** / *真正の wildcard*

**理由: この論文の評価設計をそのまま当てはめると、R1 が 9 週間止まっている場所の詰まりが解ける。それも「定義を精密にする」方向ではなく、「先に測ってしまう」方向にである。**

題材は自動運転ではなく **coding agent** の評価で、そこだけ見れば分野外である。だが著者が解いている問題は R1 と同型だ —— **1 回の実行結果からは、成功が「指示の質」によるのか「実行側の実力」によるのか区別できない。**帰属 (credit assignment) の問題であり、評価設計でしか解けない。

著者の 1 手目は明快で、**実行側 (Worker) を固定し、指示側 (Controller) だけを評価対象にする。**測りたいもの以外を動かさない、というだけのことだが、**これを明示的にやった瞬間に差が Controller に帰属する。**

**そして本題は 2 手目である。**評価をコストの違う 3 層に分ける —— **Type I (実行せずに次の一手の選択だけを問う。安い)、Type II (タスクの一部だけ実行)、Type III (フルタスクを丸ごと実行。高い)。**重要なのは層を分けたことではなく、**Type I と Type III が同じタスクの対として作られていること。**つまり **「安い代理指標が高い本指標をどれだけ予測できるか」を測れる形で、ベンチマークが最初から作られている。**

**ここが R1 に効く。**W35 で R1 の主指標候補に浮上した **solvability (いまこの状態から、まだ助かる候補が何本残っているか)** は、kinematic rollout (車両の運動モデルで数秒先まで空走させる計算。学習不要) だけで出せる **安い量 = Type I の位置にある。**そして W35 の精読で立てた第一の問い —— **「solvability の絶対値は候補集合の設計に依存するのではないか」** —— は、この枠組みに翻訳すると **「Type I は Type III を予測するか」** になる。

**翻訳した途端、やるべきことが変わる。**定義の正しさを先に確定させる作業ではなく、**粗い定義のまま計算して、閉ループ結果との対応を見る作業になる。**対応すれば定義は十分だったのであり、対応しなければそこで初めて定義を詰める。**ICRA まで約 2 週間という条件では、この順序のほうが明確に速い。**そして必要なログと運動モデルは、08-31 の実験 2 とまったく同じである。

> 最良モデルでもフルタスクの Strict Success Rate は **24.69%**。長期ループの制御は解けていない。**この research_loop 自体が論文の言う Loop Engineering の構成であり、9 日間示している挙動は論文の失敗モード 2 番目・3 番目 (必要な検証を飛ばす / 予算を間違った方向に使う) に一致する。**冒頭に Type I 指標を置いたのはこの論文の帰結である。

### 2. [VLAct — 下流データを 5 倍集めるより、その手前の表現を作り直すほうが安い](2608.27550.md) — P3 **5.0** / P2 **4.5** / hf **54**

**理由: 本日唯一の P3 本流であり、同時に P2 の評価基準に対する直球の回答でもあるから。1 本で 2 プロジェクトに刺さる。**

VLA (Vision-Language-Action; 画像と言語指示を入力してロボットの行動を直接出力するモデル) を汎用化させる標準路線は「軌跡データをもっと集める」だが、実機収集は高価で物理世界をまばらにしか覆えない。**著者は問いを立て直す —— データ量が固定されているとき律速は何か。答えは表現の質である。**

そこで VLM (画像と言語を扱う基盤モデル) と task-specific fine-tuning の間に、**異種 embodiment (ロボットの機体・形態) の混在データで学ぶ段**を 1 つ挿入する。設計判断は 3 点 —— **元の VLM が持つ知識を壊さずに残す / 機体ごとに複数の行動ヘッドを並べて同時に監督する / 行動空間の並びを「揃う部分だけ」揃える** (完全統一でも完全分離でもない中間)。**共有するのは表現であって出力層ではない、という線引きが手法の実質である。**

**そして数字がこれ —— 学習時に見ていない humanoid 機体で、下流軌跡の 20% しか使わない VLAct が、フルデータの GR00T-N1.6 を上回った。**`topics.yaml` の P2 基準は「少データでの適合、ドメインギャップの克服、基盤モデルを別ドメインに転用する recipe」を高優先と書いており、**これはその基準にまっすぐ答えている。**

**さらに W35 の P2 の結論と形が揃う。**W35 は「蒸留・適合の支配変数は loss ではなく周辺工程だった」と結論したが、**本論文は同じことを一段外側で言う —— 支配変数は fine-tuning の中身ですらなく、その手前に何を挟むかである。**

> **引用前に確認が要る:** 「20% で勝った」は **VLAct と GR00T-N1.6 という別系統モデルの比較**であって、同一モデルでの data-efficiency ablation ではない。**continued pre-training の寄与なのか backbone が強いだけなのかは abstract では切り分けられない。**R2 が系統則を主張する立場である以上、原論文の ablation を見るまでこの数字は使えない。

### 3. [DART-SD — 罰する範囲を間違えている、が 3 例目になった](2608.18524.md) — P2 **4.0** / P1 2.5 / hf **60**

**理由: 単体の手法としてより、「3 本目」であることに価値があるから。W35 の P2 の観察が、分野をまたぐ命題に格上げできる。**

LLM に multi-turn tool-calling (複数ターンで外部ツールを呼びながらタスクを進める能力) を仕込む標準手法は、成功軌跡をまるごと模倣させること。**著者はこれが原理的に頭打ちだと言う** —— 順序を入れ替えても等価な sub-goal が複数あるとき、**最適解は 1 本の線ではなく、始点と終点を共有する無数の経路が張る格子になる。**それを 1 本の軌跡に押し込めて教師にすれば、**「正しいが順序が違うだけ」の経路まで一律に罰することになる。**

手法は、実行過程をグラフとして持ち (順序違いの等価経路が同じ状態に合流する)、**「ここまでは正しく、ここから外れた」という 1 点**を特定し、**そこから先の復帰ステップにだけ loss を当てる。**手前の正しい推論には**勾配を一切通さない。**

**つまり制御変数は loss の関数形ではなく、loss を「どこに」当てるかである。**W35 は蒸留について「支配変数は loss ではなく周辺工程」と結論し、根拠に [UC-MOPD](../2026-08-29/2608.26735.md) と [Echo-GRPO](../2026-08-29/2608.26684.md) の**「更新する token の選択」**を挙げた。**本論文は別分野で同じ場所に、より極端な形で着地した 3 例目である。**

**そして capacity gap (教師と生徒の能力差が大きすぎて蒸留が効かなくなる現象) の読み方が 1 つ増える。**標準的な説明は「生徒が教師の出力分布を表現しきれない」だが、**この見立てを当てると別の筋が出る —— 生徒が再現できないのは教師の「答え」ではなく、教師が通った「経路」かもしれない。**もしそうなら **capacity gap は容量の問題ではなく監督範囲の問題であり、R2 の系統則の独立変数が 1 本増える。**仮説だが、検証は既存の蒸留設定に条件を 1 つ足すだけで済む。
