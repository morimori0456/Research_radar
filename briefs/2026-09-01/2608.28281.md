# LoopArena: Benchmarking Models as Runtime Controllers for Loop Engineering

**topic:** sns_wildcard (**真正の探索枠 1 件**) / **project:** EXPLORE → P1 (副) / **hf_upvotes:** 82 (本日最高)
**スコア:** P1 **3.5** / P2 1.0 / P3 1.5

> **分類について:** 本日 3 件中、**唯一の真正な wildcard。**自動運転にも蒸留にも VLA にも属さない (coding agent の評価)。**選んだのは題材ではなく評価設計のためである** —— 下記のとおり、R1 が 9 週間直面している問題と**同じ構造の問題を、この論文は正面から扱っている。**wildcard 枠 1 件はこれを充てる。

## 何を解決する論文か

**Loop Engineering** —— coding agent (コードを書く AI エージェント) を人が 1 プロンプトずつ手で動かすのではなく、**進捗を監視し、作業を割り当て、検査を走らせ、次に何をするか決める「ループ」を設計する**という開発様式が広がっている。しかしループは失敗する: **古い進捗メモを信じる、必要な検証を飛ばす、予算を間違った方向に使う、安全に提出できる状態になる前に止める。**

**そして本論文が突く核心はここである —— 1 回の end-to-end 実行の結果からは、成功も失敗も「ループの指示が良かった/悪かった」のか「coding agent の実力」なのかが区別できない。**これは能力の問題ではなく**帰属 (credit assignment) の問題**であり、評価設計で解くしかない。LoopArena は、**あるモデルが「別の」coding agent をどれだけうまく導けるかだけを測るベンチマークである。**

## 手法の核心

- **役割を Controller と Worker に分離し、Worker を固定する。**評価対象のモデルは **Controller** で、コーディング 1 周ごとに構造化された実行サマリを受け取り、**固定された別の coding agent (Worker) に「次に何をやれ/何を検証しろ」を指示する、あるいは停止を決める。****Worker を固定した瞬間に、性能差は Controller だけに帰属する。**これが論文全体を成立させている 1 手である。
- **評価を、実行範囲とコストの異なる 3 層に分ける。**ここが設計として一番学ぶところ。
  - **Type I: Worker を一切実行せずに測る。**次の一手 (Loop Contract) の選択を、**execution-validated questions (あらかじめ実行して正解を確定させておいた設問)** の形で問う。**安い。**
  - **Type II: フルタスクの一部分だけを切り出し、そこで制御を反復させる。**中間コスト。
  - **Type III: 対応するフルタスクを初期状態から丸ごと走らせる。**高い。これが本命の測定。
- **3 層が「対になっている」ことが重要である。**Type I と Type III は**同じタスクの対**として作られている。**つまりこのベンチマークは、安い代理指標が高い本指標をどれだけ予測できるかを、測れる形で持っている。****代理指標を作ることと、その妥当性を検証可能にしておくことを、同時にやっている設計である。**
- **結果は厳しい: フルタスクでの Strict Success Rate (全条件を満たした厳格な成功率) の最高値が 24.69%。**最良のモデルでも 4 回に 3 回は長期ループの制御に失敗する。**「coding agent が賢ければループも回る」は成立していない。**

## P1 / P2 / P3 への適用可能性

**題材は自動運転から遠いが、評価設計として R1 に移せるものが 2 つある。両方とも R1 の弱点に直接当たる。**

**(1) 「測りたい対象以外を固定する」を、R1 の設計原則として明文化する。**
本論文が Worker を固定したのは、**そうしないと Controller の能力を測ったことにならないから**である。**R1 が「保証付きの planner 評価」を主張する以上、まったく同じ操作が要る** —— perception の出力、シミュレータの挙動、他車の反応モデル。**これらが条件間で動いていたら、planner の差を測ったとは言えない。**W35 の [PAWBench](../2026-08-29/2608.27345.md) は「1 本ではなく分布で測れ」、[VBVR-Pro](../2026-08-29/2608.26105.md) は「採点器の癖が結果に混入する」を示したが、**「planner 以外を固定できているか」という帰属の問いは、R1 の軸にまだ明示的に入っていない。**本論文はそれを 1 本足す。

**(2) 【本論文の最大の持ち帰り】安い指標と高い指標を、対にして同時に設計する。**
R1 は同じ構図をすでに抱えている —— **open-loop 指標 (ログに対する誤差。安い) と closed-loop 評価 (実際に走らせる。高い)。**そして自動運転の評価研究で繰り返し問題になってきたのは、**安いほうが高いほうを予測しない**ことである。**本論文の答えは「安いほうを使うな」でも「高いほうだけやれ」でもなく、対応する対を最初から作っておき、予測できるかどうかを測定可能にしておくことだった。**

**これは W35 で R1 の主指標候補に浮上した solvability (いまこの状態から、まだ助かる候補が何本残っているか) の扱いを、そのまま決める。**solvability は kinematic rollout だけで計算でき、**学習も実行も要らない安い量である** —— つまり **Type I の位置にある。**W35 の精読 (RoG-DAgger) で立てた 3 つの問いのうち 1 番目は「solvability の絶対値は候補集合の設計に依存するのではないか」だったが、**本論文の枠組みで見ると、その問いは「Type I が Type III を予測するか」に翻訳される。****そして翻訳した途端、答え方が変わる —— 定義を精密にする作業ではなく、対を作って相関を測る作業になる。**

**この読み替えは R1 の実験計画を 1 段簡単にする。**solvability の定義の正しさを先に確定させる必要はない。**粗い定義のまま計算し、閉ループ結果との対応を見ればよい。**対応するなら定義は十分だったのであり、対応しないならそこで初めて定義を詰める。**ICRA まで約 2 週間という条件下では、この順序のほうが明らかに速い。**

**P2 1.0 / P3 1.5。**直接の材料は無い。

**なお、本論文の題材そのものについて 1 点だけ。**この research_loop は、**まさに LoopArena が定義する Loop Engineering の構成である** (日次で候補を集め、選別し、次に何をするか決める)。**そして本ループが 9 日間示している挙動は、論文が列挙した失敗モードの 2 番目と 3 番目に一致する —— 必要な検証を飛ばす / 予算を間違った方向に使う。**15 分の修正が未実施のまま、毎日新しいブリーフを生成し続けている。**Strict Success Rate 24.69% は他人事の数字ではない、というのが本論文を wildcard 枠に入れた理由の半分である。**

### 試すべき実験アイデア

1. **【最優先・紙のみ・1 時間・R1 の設計を 1 つ確定させる】R1 の評価プロトコルについて「何を固定するか」の表を書く。**列は **planner / perception 出力 / 他車の反応モデル / シミュレータ設定 / 初期条件のサンプリング**、行は比較したい条件。**各セルを「固定」「変動」で埋めるだけ。****固定と書けないセルが 1 つでもあれば、そこが R1 の保証の穴である。**前提条件ゼロ、今日できる。**W35 が 9 週連続で未着手を記録している中で、これは紙と 1 時間で終わる。**
2. **【R1 の核心・半日・上の (2) を実行する】solvability を Type I 指標として位置づけ、閉ループ結果との対応を測る。**同一ログ・同一運動モデルで、(a) 各シーンの solvability (安い、実行不要) と (b) そのシーンでの閉ループ結果または人間の介入有無 (高い、既存ログにある) を対にして並べ、**相関を 1 枚の散布図にする。**
   **どちらに転んでも 1 つ決まる:** 対応するなら **solvability は「実行せずに閉ループ品質を予測する指標」として主張でき、これは R1 の中心的な貢献になる。**対応しないなら、**W35 の精読で立てた「候補集合の設計への依存」がその場で疑うべき第一容疑者になり、次に何を詰めるかが決まる。**
   **08-31 の実験 2 (engine チェックが全て pass なのに人が介入したケースの抽出) と、必要なログ・運動モデル・抽出手続きが完全に共通しているので、2 つ合わせて半日である。**
3. **【本ループ自体に対して・15 分】このループの Type I 指標を 1 つ決める。**本論文は「1 回の実行結果からは帰属できない」と言う。**本ループの現在の観測量は「日次でブリーフが生成されたか」だけで、これはループの制御の質を何も測っていない** (9 日間、生成は毎日成功し、実質的な前進はゼロだった)。**候補: 前日の DIGEST が指定した最優先行動が、翌日までに実行されたか (yes/no)。**これは実行不要・記録のみで測れる Type I 指標であり、**今日から `DIGEST.md` の冒頭 1 行として持てる。**
