> **なぜ本日の探索枠をこれに使ったか:** 本日の新規候補は 2 本しかなく、もう 1 本 ([Compile by Training](2609.04199.md)) は P2 の本流である。**そして本日は RESEARCH_PIPELINE が定めた 09-06 gate の当日である。**本論文は **agent の評価設計**の論文だが、**測っている量が gate の判断材料そのもの** —— 「モデルを強くしても、実行基盤が無ければ性能は出ない」を、重みを固定した比較で数字にしている。

## 何を解決する論文か

agent の能力は、モデルの重みだけでなく **agent harness (モデルの外側で計画・実行・記憶・検証を回す実行基盤)** に強く依存する。**重みを固定したまま harness を変えるだけで、タスク性能は大きく動く。**

ところが現在の agent 評価は、**ある harness を選んだ上での下流性能を報告するだけ**で、モデル自身が **harness を作り育てる能力**は比較的手つかずのまま残されている。**HarnessDev は評価の単位をずらす —— 測る対象を「タスクの出力」ではなく「動く実行基盤」にする。**

## 手法の核心

- **2 段階で測る。** **Creation**: 最小の seed と少数のケースだけを与え、そこから完全な実行系を構築させる。**Evolution**: 自分が作った harness を起点に、**下流の実行フィードバックを見ながら反復改訂**させ、ベンチマーク性能の改善を狙わせる。
- **評価は「対」で出し、単一の集約スコアに畳まない。** **capability (held-out ベンチマークでのタスク成功)** と **efficiency (execution-token cost = 実行に消費した token 量)** の 2 つ。
- **規模と隔離:** Creation の結果は **creator LLM 6 種 × 4 ドメイン × 下流ベンチマーク 5 種 = 2,207 インスタンス**。**hidden evaluation tasks は開発から隔離されている** (開発中に見えない held-out を別に持つ)。
- **結果がドメインで割れる。** **code と search/research では、人手で作り込まれた成熟した参照実装に大きく劣る。** 一方 **writing と machine-learning experimentation では参照実装と同等以上。**そして **実行コストのばらつきが大きい。**

> **引用前の注意:** 取得した abstract は **Evolution の結果を述べる途中で切れている** ("Evolution p...")。**反復改訂で実際にどれだけ改善したかの数値は未確認である。**上に書いた「ドメインで割れる」は Creation の結果に対する記述であり、Evolution 側に一般化してはいけない。

## この loop への適用可能性

### (1) R1 の評価設計に、3 つの直接の当てはまりがある

**本論文は運転とは無関係だが、評価を設計する立場としては R1 が 10 月に必ず通る 3 つの判断を、先に通って結果を出している。**

- **(a) 対で報告する。**R1 の言い方は最初から「衝突率**の隣に置く**量」である —— つまり置き換えではなく併置。**HarnessDev は capability と cost を対で報告し、しかも「片方だけでは順位が付かない」ことを結果で示している** (writing では参照実装に勝つ harness が出るが、実行コストのばらつきは大きい)。**figure 1 を「solvability 単独の折れ線」ではなく「solvability と衝突率の対」として設計する根拠に、そのまま使える。**
- **(b) 分母を隔離する。**hidden evaluation tasks を開発から外す設計は、**R1 の「抜け穴監査」(評価の分母が健全か) の実装形そのものである。**R1 側でこれを言うとき、運転分野の外に既に実施例があると書ける。
- **(c) 妥当性は領域依存である。**同じ指標が、ドメインによって参照実装を上回ったり大きく下回ったりしている。**これは「指標の妥当性は領域ごとに測り直す必要がある」ことの実測であり、R1 を nuPlan と NAVSIM の両方で出すべき理由になる。**

### (2) 探索枠としての学び —— この loop 自身に当たる

**09-04 に採った [Repo-To-Skill](../2026-09-04/2609.02749.md) は、「詰まりの原因は知識の不足ではなく、知識が使える形になっていないことだ」と主張した。****本論文は、その主張を測っている。**重みを固定して harness だけを変えると性能が動く、という形で。

**この loop に当てはめると、変数は 2 本あって別物である。**

- **アイデアの質を上げる作業** = 毎日のブリーフ。**これは 40 日以上、一日も欠けずに動いている。**
- **実行基盤を作る作業** = 走行ログを読んで配列を返す関数 1 個。**これは 9 週間ゼロである。**

**HarnessDev の結果が言っているのは、前者をいくら積んでも後者は動かない、ということである。**そして 09-04・09-05 と 2 日連続で、**指されている作業は同じ 1 個の関数**だった。

## 試すべき実験アイデア

1. **【今日・判定そのもの】gate の判断を、本論文の形式で下す。**RESEARCH_PIPELINE の規則は **「09-06 に図 1 が無ければ RoboPAD 投稿を取り下げ、OSS PR に切り替え」**。**capability (図 1 が出たか) と cost (かけた時間) を対で記録する** —— 「やらなかった」ではなく「何分かけて、どこで止まったか」を残す。**次に同じ判断をするとき、対の片方しか無ければ原因が特定できない。**
2. **【1 時間・図 1 が無い場合にその場で切り替える先】走行ログ (or 2D toy) を読み、`(時刻, 自車状態, 周辺物体, 走行可能領域)` を返す関数を 1 つだけ書いて、動くことを確認して置く。**論文的な価値はゼロで、**本論文の言う harness の最小単位がこれに当たる。**3 日連続で同じ 1 個が指されている。
3. **【30 分・R1 の figure 設計】figure 1 を「capability × cost」型の 2 軸図として設計し直す。**縦に solvability (逃げ道の残り本数)、横に衝突率、点は planner。**HarnessDev の図がそのまま雛形になる。**紙の上で描けるので、実データが無くても今日できる。
4. **【やらないこと】HarnessDev の再現、および自作 harness を evolve させる試み。****この loop の harness は既に動いている** (毎日候補が届き、ブリーフが出て、コミットされている)。**壊れているのは harness ではなく、harness の外にある 1 個の関数である。**論文の教訓を自分の loop の harness 改造に使うのは、いま最も避けるべき方向である。
