## 何を解決する論文か

繰り返し現れるテキスト処理には、「言葉で説明するのは簡単だが、ルールとして実装するのは難しい」ものが多い。かといって入力のたびに大きな remote model (API 越しの大規模モデル) を呼べば、**コスト・レイテンシ・プロバイダ依存が処理のたびに積み上がる。**

本論文の **compile by training** は、自然言語で書かれた仕様を、**再利用可能な neural function (小さなニューラルネットとして実装された関数) に変換する。**compile 時に teacher model がそのタスク専用の例を生成し、それで **compact interpreter (関数どうしで共有される小さめのモデル本体)** 用の **adapter (本体を凍結したまま差分だけを学習する小さな追加パラメータ。LoRA などがこれに当たる)** を学習する。

**出来上がった関数は teacher なしで動く。**そして普通のソフトウェアと同じように保存・バージョン管理・合成ができる。

## 手法の核心

- **「compile」という比喩が設計そのものになっている。**入力は自然言語の仕様、出力は成果物 (adapter の重み)。**実行時には compile 時に使った teacher が一切要らない。**依存が compile 時に閉じている点が、この論文の実務的な主張の中心である。
- **教師データを既存コーパスから拾ってこない。**teacher model が仕様から生成する。つまり**蒸留の対象が、teacher の入出力分布ではなく「仕様の意味」になっている。**
- **学習するのは adapter だけで、本体は共有される。**関数がいくつ増えても interpreter は 1 つ。多数の小さなタスクを抱える運用に効く形。
- **先行方式との trade-off を正面に置いている。**比較相手は **Program-as-Weights の fast compiler (仕様を数秒で重みに直接写す方式)**。本手法は **FuzzyBench-Hard で semantic accuracy 83.6%** を出すが、**compile 時間は「数秒」から「約 1 分」に増える。**速さと正確さのどちらを買うかを明示している。
- **動くデモが 3 つ:** 公開の対話サービス上に compiler を配備し、multi-site の website helper、言語で制御する 3D avatar、双方向翻訳を compiled function として実装。

> ### 引用前の注意 (2 点。どちらも数値を引く前に本文が要る)
>
> **① `FuzzyBench-Hard` は「比較相手が失敗した問題」として定義された部分集合である。**abstract の言葉どおりに読むと、これは **fast compiler が完全一致を 1 件も出せなかった subset** である。したがって **83.6% 対 0% は、比較相手の失敗によって選ばれた分母の上の数字**であり、手法の総合的な優劣ではなく「fast compiler が落ちる領域を、training がどれだけ拾えるか」を測っている。
> **これは R1 が「抜け穴監査」で問題にしている分母の健全性と、まったく同じ論点である。**引用するなら full set の数字が要る。
>
> **② semantic accuracy の判定方法が abstract に無い。**完全一致でないなら何で測っているのか (別モデルによる判定か、規則か) が書かれていない。**判定器が teacher と同系統だと循環する**ので、ここは本文で確認する必要がある。

## この loop への適用可能性

**P2 (R2) への接続が本体である。**

R2 の現在の主張は「蒸留の破綻を決めるのは容量差ではない」であり、**容量比 1.0 でも蒸留が効く反例 5 本によって、当初の前提 (容量差が原因) は既に棄却されている。**代わりに 3 例が同じ方向を指していた —— **支配変数は loss ではなく「監督を当てる範囲」である** (UC-MOPD / Echo-GRPO / DART-SD)。

**本論文はその 4 例目になり得るが、性格が違う。**前 3 例はいずれも**既にある監督のどこを切るか**の話だった。本論文は**監督そのものを仕様から作り出す。**つまり同じ軸の上で、**範囲を最大に広げた端点**に当たる。軸が 1 本で説明できるなら端点も乗るはずで、乗らないなら軸の立て方が間違っている —— **反証の機会として使える 1 本**である。

**P1・P3 への接続は薄い。**運転にも planner 評価にも触れていない。

### 試すべき実験アイデア

1. **【30 分・紙と鉛筆でできる】R2 の 4 例を「監督が当たる範囲」という 1 軸に並べ直した表を書く。**UC-MOPD (CLL の集中度で範囲を絞る) / Echo-GRPO (clipping によって範囲が意図せず狭まる) / DART-SD (復帰ステップにのみ当て、正しい prefix には勾配を通さない) / **本論文 (範囲を仕様から生成する = 端点)**。**4 例が一列に乗れば、R2 の主張は「容量差ではなく監督範囲」と 1 文で書ける。**乗らない例が出たらそこが R2 の本当の問いになる。
2. **【やらない: 半日・GPU 必要】**過去の蒸留ログで、teacher 生成データのみの学習と実データ学習とで CLL 上位 1% 占有率がどう動くかを比較する。**筋は良いが、今月は R1 に絞る方針 (RESEARCH_PIPELINE) なので着手しない。**R2 を再開する段で最初にやる 1 手として記録に留める。
3. **【やらないこと】FuzzyBench の再現と compiler の実装。**この loop に必要なのは compiler ではない。
