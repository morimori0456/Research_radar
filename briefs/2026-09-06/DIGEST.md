### 1. [評価の単位を「出力」から「動く実行基盤」へ移すベンチマーク](2609.01437.md) — P1 **3.5** / 探索枠

**理由: ① 今日 30 分で、figure 1 の描き方が決まる。② そして本論文が測っているのは、この loop が 9 週間動いていない理由そのものである。**

HarnessDev が扱うのは **agent harness (モデルの外側で計画・実行・記憶・検証を回す実行基盤)**。出発点の観察はこうである —— **モデルの重みを固定したまま harness だけを変えると、タスク性能が大きく動く。**なのに今の agent 評価は「ある harness を選んだ上での下流性能」しか報告しない。そこで著者は測る対象をずらし、**モデル自身に harness を作らせ、育てさせ、その harness を評価する。**

**R1 にとっての価値は、結論ではなく評価設計の 3 点にある。**

- **capability (タスク成功) と efficiency (実行に使った token 量) を対で報告し、単一スコアに畳んでいない。**そして**片方だけでは順位が付かないことを結果で示している** (writing では人手の参照実装に勝つ harness が出るが、実行コストのばらつきは大きい)。**R1 の言い方は最初から「衝突率の隣に置く量」だった。figure 1 を solvability 単独の折れ線ではなく「solvability × 衝突率」の 2 軸図にする根拠が、これで外部から取れる。**
- **hidden evaluation tasks を開発から隔離している。**これは **R1 の「抜け穴監査」(評価の分母が健全か) の実装形そのもの**で、運転分野の外に既に実施例があると書ける。
- **同じ指標が、ドメインによって参照実装を上回ったり大きく下回ったりする。**指標の妥当性が領域依存だという実測であり、**R1 を nuPlan と NAVSIM の両方で出すべき理由になる。**

**そして探索枠としての学びは別のところにある。**09-04 に読んだ Repo-To-Skill は「詰まりの原因は知識の不足ではなく、知識が使える形になっていないことだ」と主張した。**本論文はそれを測っている。**この loop に当てると変数は 2 本あって別物である —— **アイデアの質を上げる作業 (毎日のブリーフ) は 40 日以上一日も欠けず動き、実行基盤を作る作業 (ログを読んで配列を返す関数 1 個) は 9 週間ゼロ。**前者を積んでも後者は動かない、というのが本論文の結果である。

> **注意:** abstract は Evolution (自作 harness の反復改訂) の結果の途中で切れている。**改訂による改善幅は未確認**で、上の「ドメインで割れる」は Creation 側の結果である。

### 2. [自然言語の仕様を、teacher なしで動く小さな関数にコンパイルする](2609.04199.md) — P2 **4.0**

**理由: R2 の主張を 1 文に畳めるかどうかが、30 分の紙作業で判定できる。**

**compile by training** は、自然言語で書かれた仕様を **neural function (小さなニューラルネットとして実装された関数)** に変換する。compile 時に **teacher model がそのタスク専用の例を生成**し、それで **compact interpreter (関数どうしで共有される小さめのモデル本体)** 用の **adapter (本体を凍結したまま差分だけ学習する小さな追加パラメータ。LoRA などがこれ)** を学習する。**出来上がった関数は teacher なしで動き、保存・バージョン管理・合成ができる。**速い先行方式 (Program-as-Weights) との trade-off も明示されていて、**FuzzyBench-Hard で semantic accuracy 83.6%、ただし compile 時間は数秒から約 1 分に増える。**

**R2 にとっての位置づけがはっきりしている。**R2 では既に「容量比 1.0 でも蒸留が効く反例 5 本」によって当初の前提 (容量差が原因) が棄却され、代わりに 3 例が同じ方向を指していた —— **支配変数は loss ではなく「監督を当てる範囲」である** (UC-MOPD / Echo-GRPO / DART-SD)。**本論文は同じ軸の端点に当たる。**前 3 例が「既にある監督のどこを切るか」だったのに対し、**本論文は監督そのものを仕様から作り出す。**軸が 1 本で説明できるなら端点も乗るはずで、**乗らなければ軸の立て方が間違っている。反証の機会として使える。**

> **数値を引く前に本文が要る。**`FuzzyBench-Hard` は **「比較相手が完全一致を 1 件も出せなかった問題」として定義された部分集合**である。**83.6% 対 0% は、比較相手の失敗によって選ばれた分母の上の数字**であって、総合的な優劣ではない。**これは R1 が抜け穴監査で問題にしている分母の健全性と、まったく同じ論点である。**加えて semantic accuracy の判定方法が abstract に無い (判定器が teacher と同系統なら循環する)。
