## 何を解決する論文か

コーディング agent を RL (reinforcement learning; 報酬を最大化するように方策を学習する枠組み) で鍛えるには、「多様なタスク」と「正解を機械的に判定できる verifier (答えの正誤を自動判定する仕組み。ここではテスト)」が大量に要る。既存手法は GitHub の issue や commit からタスクを切り出していたため、取れるタスクの範囲が狭かった。この論文は**ソースコードそのものだけを入力にして**、実行可能な RL 環境を自動で作る pipeline を提案している。

## 手法の核心

- **仕様をコードから逆算する:** agent がリポジトリ内の実装済み機能を探索し、「この機能は何をするべきか」という behavioral specification (振る舞いの仕様) を書き起こす。
- **正解は元のコードの実行結果:** テストは元のコードを実際に動かした結果に基づいて作る。人間がテストの期待値を書く必要がない。
- **作ったタスクを 2 段で検証・選別する:** (1) 実行チェックで壊れたタスクを除く。(2) 解答の rollout (モデルに同じ問題を複数回解かせる試行) を繰り返して、使えないタスクを除く。**選別の具体的な基準は abstract に無い。**よくある実装は「一度も解けない」と「毎回解ける」の両方を落とすもの (推測)。
- **規模:** 3,185 リポジトリ・23 言語から 5,545 タスク。これで MiMo-V2.5 を GRPO (Group Relative Policy Optimization; 同じ問題への複数回答を互いに比べて相対的な良し悪しを報酬にする、PPO の簡略版の RL 手法) で学習した。issue 修正 (DeepSWE +11.7%)、プログラム全体の構築 (ProgramBench +17%)、ターミナル操作 (Terminal-Bench v2.1 +8.5%) を含む 5 ベンチすべてで改善している。
- **ablation (構成要素を 1 つずつ外して効果を測る実験)** では、**質の高いタスクを増やすほど性能が上がる**。学習後の agent はコードベースをよく探索し、自己検証の仕方も多様になった。

## プロジェクトへの適用可能性

### P1 (Planner AI + 評価) — 3.0: 題材ではなく「タスクの選別」の考え方が R1 に移る

コーディングも運転も関係ない。**移るのは 2 番目の選別 (rollout を繰り返してタスクを残すか決める) の考え方である。**RL の側では「誰も解けない / 誰でも解ける問題は学習信号にならない」ので落とす。**閉ループ評価 (planner の出力でシミュレーションが先に進み、その結果が次の入力になる評価) でも同じ構造がある:**

- 回避不能なシナリオ (どの planner でも衝突する) は、衝突率の分母を水増しするだけで planner を区別しない。
- 自明なシナリオ (どの planner でも衝突しない) も区別しない。
- **planner の差を決めているのは、その中間のシナリオだけである。**

これは R1 の「抜け穴監査 (分母の健全性)」とそのまま同じ問いである。**CodeMidas はそれを「作ったタスクを学習前に検査する」手順として実際に回し、効果 (5 ベンチ全改善) まで出している。**R1 の論文で「分母を検査すべき」と主張するとき、隣接分野の実例として引ける。

**実験アイデア (半日・GPU 不要・2D toy で可):**
1. シナリオ集合を用意し、planner を K 種類 (または 1 つの planner に摂動を入れて K 回) rollout する。
2. シナリオごとの成功率 (衝突しなかった割合) を出し、**ヒストグラムにする** (横軸: 成功率 0〜1、縦軸: シナリオ数)。
3. 成功率 0 のシナリオを solvability (逃げ道の残り本数) で検査し、「本当に回避不能 (逃げ道 0 本)」と「planner が下手なだけ (逃げ道あり)」に分ける。
4. **判定:** planner 2 つの衝突率の差のうち、中間のシナリオが何割を説明するかを測る。中間が全体の 1〜2 割しかないのに差のほとんどを説明しているなら、**「衝突率は分母の大半がノイズ」という R1 の主張を裏づける図 1 の候補になる。**逆に 0 と 1 にほとんどシナリオが無ければ、この toy では抜け穴監査は効かない。これも結果として記録する。

### P2 (蒸留 + fine-tuning) — 1.5

蒸留ではなく RL なので直接は関係ない。**唯一移りそうなのは「データ量より質」の ablation** で、蒸留で使う prompt の選別にも同じ理屈が効く可能性がある。ただし on-policy distillation (student 自身が生成した文に teacher が token ごとの確率で教師信号を付ける蒸留) では、全 prompt から信号が出る。GRPO のように「全回答が同点で信号ゼロ」にはならないので、効き方は弱いはず (推測)。**R2 の範囲では追わない。**

### P3 (次世代アーキテクチャ) — 1.0
