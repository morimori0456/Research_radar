# ControlledShifts: Towards Standardizing Robustness Evaluation in Trajectory Prediction Under Distribution Shifts

**topic:** planner_ai (P1) ・ **arXiv:** 2608.17882 ・ **published:** 2026-08-18 ・ **hf_upvotes: 0** ・ **relevance 4.5 / 5**

> **主張を一行で:** **「この予測モデルは頑健である」という主張が今まで比較不能だったのは、各論文が勝手な軸で汎化を測っていたから。** 本論文は **「どの軸で測るか」と「その軸の裾をどう切り離すか」を 2 つの関数として明示的に書かせる**ことで、頑健性評価を標準化する。
>
> **なぜ重要か:** **R1 が作ろうとしているのは評価プロトコルであり、本論文は「評価プロトコルを提案する論文の書き方」の同時代の実例である。** しかも **自動運転の trajectory prediction (周囲の車や歩行者が今後どう動くかの予測) という、P1 のど真ん中で。** **中身より先に、構成を真似する対象として読むべき 1 本。**

## 何を解決する論文か

**学習ベースの trajectory prediction は、訓練データに乏しい状況に出会うと急激に劣化する。** これに対して **data-centric な対策 (データを足す・作る) や test-time adaptation (実行時にモデルを状況へ適応させる) が多数提案されてきたが、それぞれが別々の「汎化の軸」で検証されている。** ある論文は未知の都市で、別の論文は未知の道路形状で、また別の論文は珍しい挙動で測る。**結果として、頑健性を横並びで比較する手段が分野に存在しない。**

**本論文の解決は、新しいデータセットを作ることではない。** **既存の trajectory データセットを、共通の定式化に従って in-distribution (訓練で見た分布) と out-of-distribution (見ていない分布) に再分割する枠組みを与えることである。** **「何を測るか」を人が選ぶ自由は残しつつ、その選択を明示的に書かせる。**

## 手法の核心

- **中心は characterization-and-splitting formulation という 2 関数の分解。** **characterization function が「このベンチマークはどの変動軸を調べているのか」を固定し、splitting function が「その軸の裾 (tail) をどう取り除いて unseen 側に回すか」を固定する。** **従来は暗黙だった 2 つの判断が、明示的な関数として書かれる。** 比較可能性はここから出る —— **2 つの手法の頑健性を比べるとき、少なくとも同じ characterization と同じ splitting の下でなら比べてよい、と言えるようになる。**

- **3 つのベンチマークを用意し、topological な shift (道路の接続構造・形状の違い) と behavioral な shift (挙動の違い) を狙い撃つ。** **「都市が違う」のようなひとまとまりの shift ではなく、変動軸を 1 本ずつ切り分けている**のが要点。

- **unified robustness score を、直交する 2 次元に分解して定義する。** **prediction quality (相対的な性能の高さ) と prediction stability (shift 下で性能をどれだけ保てたか)。** **この 2 分割が本論文でいちばん借りる価値がある部分である** —— **「そもそもよく当たるか」と「崩れにくいか」は別の量で、単一のスコアに混ぜると、弱いが安定なモデルと強いが脆いモデルが区別できなくなる。**

- **transformer 系の代表的な予測モデル群を実際に走らせ、容量の違うモデルが latent relevance (どの周辺物体が効いてくるかの潜在的な重要度) と環境構造をどう扱うかの差を露出させている。** **ベンチマークを出すだけでなく、それで何が見えるかを示している。**

## 追っているプロジェクトへの適用可能性

- **P1 / R1 —— 「評価指標の論文はこう書く」の型として最優先。** **R1 の狙いは HIL (Human-In-the-Loop) 評価と保証付き指標だが、論文としての形はまだ決まっていない。本論文の形はほぼそのまま流用できる:** ① 分野が測れていない量を特定する → ② **測り方をパラメータ化された定式化として書く** (人の判断を消すのではなく、明示させる) → ③ その定式化から具体的なベンチマークを複数インスタンス化する → ④ **多次元の結果を集約するスコアを、混ぜずに直交分解して定義する** → ⑤ 既存手法を走らせて、既存の順位が変わることを見せる。**R1 の骨格を、この 5 段に一度写してみるべきである。**

- **P1 / R1 —— 2 軸分解が、我々が既に持っている分解と 3 例目の一致を示す。** **R1 は「衝突率 (成立性) と過保守さ (目的達成)」を持ち、08-19 の VibeWorlding が「physical feasibility と intent fulfillment」で同じ形を示し、本日は「quality と stability」。** **分野をまたいで独立に同じ 2 軸分解が現れている。** **R1 の導入部で「単一スコアは 2 つの異なる失敗様式を混ぜる」という主張を立てるとき、引ける実例が 3 つになった。**

- **P1 / R1 —— ただし本論文は R1 が狙う場所を占領していない。** **本論文が測るのは predictor 単体の性能劣化であって、planner の運転結果ではない。** **予測が崩れたときに planner が何をするか、衝突率と不要停止率がどう動くかは扱われていない。** **R1 の主張は「shift 下の予測誤差」ではなく「shift 下の運転の operating curve」に置ける。本論文は前段の標準を作ってくれた側であり、競合ではなく土台である。**

- **P2 —— 「未知ドメインで壊れるか」の測り方として、蒸留・適応の評価にそのまま移植できる。** **P2 の criteria にある「ドメインギャップの克服」は、克服できたかを測る手段が要る。** **characterization / splitting の 2 関数は、蒸留した student を「どの軸に沿って未知に押し出すか」を書く言語として使える。** **W34 課題カード2 の「機種を跨いだ性能保証」も、characterization function を embodiment の統計量に取れば同じ枠に収まる。**

- **P3 —— 直接の設計指針は無いが、E2E (end-to-end) モデルの頑健性を報告する際の様式として効く。**

- **留保:** (1) **「既存データセットを再分割する」方式は、元データに存在しない shift は作れない。** **裾の切り出しである以上、真に未知の状況 (訓練データのどの軸にも現れない事象) は扱えない。** これは本論文の限界であると同時に、**R1 が「では真に未知はどう測るのか」を問える隙間でもある。** (2) **unified robustness score の具体的な合成式が abstract から読めない。** **2 軸をどう 1 つにまとめるかで、また混合の問題が再発しうる** —— 本文で最初に確認すべき箇所。(3) **評価されているのが transformer 系のみで、diffusion 系の予測モデルが入っているかは不明。**

### 試すべき実験

1. **本論文の 5 段構成に R1 を写経する (最優先・所要 1〜2 時間・実験環境不要)。** **紙の上で「R1 の characterization function は何か / splitting function は何か / 直交する 2 軸は何か」を埋める。** **R1 の場合、characterization は「planner の保守性パラメータ」、2 軸は「衝突率」と「不要停止率」になるはず。** **埋まらない欄が出たら、そこが R1 に足りていない設計判断である。** 本日の作業で最も着手が速い。

2. **ControlledShifts で予測器を選び、その予測を planner に食わせたときの運転指標を測る (優先度高・R1 の新規性を確定させる)。** **本論文が示した「予測性能の順位」と、「その予測を使った planner の衝突率・不要停止率の順位」が一致するかを見る。** **一致しないなら、それが R1 の主張の中核になる** —— **予測の指標で planner を選ぶのは誤りである、という具体的な反例が手に入る。** **一致するなら、予測側の標準に乗るだけでよいことになり、R1 は別の場所を狙うべきと分かる。どちらでも次が確定する。**

3. **quality と stability の 2 軸で、既存手法の順位が入れ替わるかを確認する (優先度中)。** **入れ替わりが起きる実例は、「単一スコアは混ぜている」という R1 の導入部の主張を支える最良の証拠である。** 本論文が既に出しているなら引用で済む。

4. **splitting function を「機体・機種」に取り替えて P2 に移す (優先度中・W34 カード2 の安い入口)。** **Open X-Embodiment のような cross-embodiment データで、embodiment を characterization 軸にして裾を unseen に回す。** **「未知の機体での性能低下」を標準化された形で測る枠が、そのまま手に入る。**
