# Thinking in a Low-Resource Language: What SFT Builds, What RL Fixes, What Accuracy Cannot See

**topic:** fm_distill_finetune (P2) ・ **arXiv:** 2608.17744 ・ **published:** 2026-08-18 ・ **hf_upvotes: 0** ・ **relevance 4.5 / 5**

> **主張を一行で:** **基盤モデルを新しいドメインへ適合させたとき、accuracy はほぼ動かない。だが「動かなかった」は「何も起きなかった」ではない。** 本論文は **accuracy が見ていない場所で何が変わり、SFT と RL がそれぞれ何を直すのかを、計測器を自分で検証しながら分離した。**
>
> **なぜ重要か:** **P2 の適合実験は、今後ほぼ確実に「ベンチマークの数字が動かない」に何度もぶつかる。そのとき「効果が無かった」と結論して捨てるか、別の測り方を持つかで、得られるものが変わる。** **本論文は後者の具体的な作法を、失敗の告白込みで示している。** **そして本論文は同時に、R1 が欲しがっている「評価器の検証」の教科書でもある。**

## 何を解決する論文か

**frontier MoE (Mixture-of-Experts; 入力ごとに一部の専門家サブネットだけを使う疎な大規模モデル) 3 種 (Alibaba / OpenAI / NVIDIA、いずれも active parameter 3.6-4.0B) を、低資源言語 (ここではギリシャ語) で推論するよう fine-tuning する。**

**accuracy ベンチマークではほとんど何も起きない。しかもその「起きない」自体が信用できない —— random seed を変えるだけでスコアが 7.7 ポイント動き、これは著者らが測ったあらゆるデータ・recipe の効果より大きい。** **本論文はこの null を第一の結果として提示する。**

**では本当に何も変わっていないのか。変わっている。** **base model は問いがギリシャ語でも 1,000 本の推論トレースのうち 0 本しかギリシャ語で考えない。** つまり **モデルは正解を出すが、その過程はユーザーが読めず、監査もできず、訂正もできない形で進んでいる。** **これは accuracy には決して現れない。**

## 手法の核心

- **SFT (Supervised Fine-Tuning; 正解の出力をそのまま模倣させる学習) が作るもの:** **公開した全チェックポイントで、問いと同じ言語で推論する割合が約 98% に到達。** ある系列は **トークン数 3 分の 1** で同じことをする。**文法性の判定は 4 モデルすべてで改善し、一般能力は base から数ポイント以内に留まる —— 忘却は起きず、流暢さだけが増えた。**

- **SFT が直せないもの:** **回答の 4 分の 1 が要求された形式を外れ、回答が推論チャネルに漏れ出し、「英語で考えよ」という明示的な指示に従うのは半分以下。** **模倣で身につくのは習慣であって、自分の欠陥の修正ではない。**

- **RLVR (Reinforcement Learning with Verifiable Rewards; 正誤が機械的に判定できる報酬で強化学習する手法) が直すもの:** **形式外れ 24% → 2.5%、漏れ 3.5% → 0.0%** —— **いずれも「報酬をランダムにした対照条件」に対しての改善として報告されている。** 指示追従は +9.1 ポイント。**そして SFT が作ったギリシャ語推論の習慣は、accuracy だけを見る勾配の下でも壊れずに残る。** **学習前に pre-registration (何を測るかを事前登録する) を行っている。**

- **本論文でいちばん借りる価値があるのは、測る側の設計である。** **6 つの behavioural dimension を提案し、各次元に「出力長と相関する指標は棄却する」という gate を掛けている** (長く書けば上がる指標は、能力ではなく冗長さを測っている)。**さらに「我々自身の計測器が嘘をついた 6 件」を、それぞれどの対照条件で検出したかと併せて報告している。**

- **手法・計測器・対照条件・事前登録の一式は、任意の低資源言語へ移せる形で公開。チェックポイント 5 本を release。**

## 追っているプロジェクトへの適用可能性

- **P2 —— 「適合の効果を何で測るか」に対する、現時点で最も実用的な回答。** **P2 の criteria は「他機種・他ドメインへの適合」を評価対象にしている。本論文が示したのは、その評価を accuracy 単独でやると、(a) 効果を見逃し、(b) しかも seed ノイズに埋もれて見逃したことにすら気づけない、という 2 段の失敗である。** **「seed だけを変えた反復を先に走らせ、ベンチマークのノイズ床を測ってから効果量を語る」** —— これは P2 のあらゆる適合実験に無条件で導入すべき手続きであり、**追加コストは学習の再実行数本ぶんしかない。**

- **P2 —— SFT と RL の役割分担が、蒸留 recipe の設計に直接効く。** **「SFT は振る舞いを作るが自分の欠陥は直せない、RL は欠陥を直すが振る舞いは作らない」という切り分けは、R2 の文脈にそのまま置ける。** **08-19 の SOPD は SFT と on-policy distillation を step length という 1 本の軸の両端として結んだが、本論文は「両端で直る不具合の種類が違う」と言っている。** **同じ軸を、性能ではなく「どの失敗様式が消えるか」で見直すべきである。** **これは R2 の予備実験に、ほぼ追加コスト無しで足せる観測項目である。**

- **P1 / R1 —— 計測器そのものを検証する作法として、08-19 の CaliBench に並ぶ 2 冊目。** **R1 は評価指標を提案する研究であり、「その指標は正しく測れているのか」に必ず答えねばならない。本論文が実演しているのは 3 点:** ① **各指標に棄却条件を先に付ける** (出力長と相関したら不採用)、② **対照条件を必ず置く** (ランダム報酬という flat control)、③ **自分の計測器が失敗した事例を数えて公開する。** **特に ③ は、評価論文の信頼性を作る最も安い方法である。R1 でも同じ節を用意すべきだ。**

- **P1 / R1 —— そして「auditable であること」自体を評価軸に立てる発想が使える。** **base model が「読めない形で正しく推論する」状態を欠陥と見なしたのが本論文の出発点である。** **運転 planner に翻訳すると、「正しい軌道を出すが、なぜそう判断したかを人が検査できない」状態がまさにこれにあたる。** **W34 課題カード3 の takeover lead time (システムが自分の失敗を人が介入できるだけ手前で予告できたか) は、この「監査可能性」の時間版である。** **VLA が言語で理由を出せることの価値を、accuracy ではなく監査可能性の軸で測る、という R1 の拡張が書ける。**

- **P3 —— 直接の構造上の示唆は無い。ただし MoE の active parameter が 4B 規模で frontier を名乗る事実は、車載を見据えた容量設計の参照点になる。**

- **留保:** (1) **対象タスクは言語であり、我々の適合対象 (機種・センサ・ドメイン) とは変数の性質が違う。** **「6 つの behavioural dimension」の中身は移植できない。移せるのは計測器を検証する手続きのほうである。** (2) **abstract が末尾で切れており、公開物の一覧と最後の主張が読めない。** (3) **seed による 7.7 ポイントの変動は「このモデル規模・このベンチマーク」での値であり、我々のタスクでいくつになるかは自分で測るしかない。** **測る、というのが本論文の要点でもある。**

### 試すべき実験

1. **P2 の適合実験に「seed のみを振る対照群」を常設する (最優先・今すぐ・所要は再実行数本ぶん)。** **手法を変える前に、seed だけを変えた 3〜5 本でベンチマークのノイズ床を測る。** **効果量がノイズ床を下回るなら、その実験は結論を出せていない。** **この 1 手続きだけで、P2 の今後の全実験の解釈が変わる。** 08-19 に決めた R2 の予備実験 (step length の系統測定) にも、着手前に入れておくこと。

2. **R2 の step length 掃引を、性能ではなく「失敗様式の内訳」で再集計する (優先度高・追加学習は不要)。** **既に走らせるつもりの実験のログに対して、失敗を種類別に数え直すだけでよい。** **step length を振ったとき、消える失敗の種類が変わるなら、SOPD の 1 本の軸は「性能の軸」ではなく「どの失敗を直す軸か」だったことになる。** **これは R2 の主張を、単なるスケーリング則から一段深いものにしうる。**

3. **各指標に棄却 gate を先に書く (優先度高・所要 1 時間・R1 の下ごしらえ)。** **R1 が使う指標それぞれについて「この量と相関したら、その指標は能力ではなく別のものを測っている」という条件を、測定前に書き出す。** **運転の場合、真っ先に疑うべき交絡は走行距離・シナリオ長・平均速度である。** 事前に書いておかないと、後から自分に有利な解釈ができてしまう。

4. **「監査可能性」を P3 の VLA 評価軸として定義できるか検討する (優先度中・紙の上)。** **本論文の「読めない形で正しい」を運転に写すと何になるか、そして本日の [MANIGUARD](2608.17386.md) の「成功したが仕様違反」とどう違うかを 1 枚に整理する。** **両者はどちらも「成功が隠している欠陥」だが、前者は過程の不可視性、後者は結果の仕様違反であり、別の軸である。**
