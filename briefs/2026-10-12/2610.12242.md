# TokenRouter: Efficient Serving System for Token-Level LLM Routing

- arXiv: 2610.12242
- トピック: sns_wildcard (P2 寄り) / hf_upvotes: 129 / relevance: 2.5

## 何を解決する論文か

LLM routing (入力ごとに複数の LLM から処理させるモデルを選び、コストと品質のバランスを取る仕組み) のうち、1 token ごとにモデルを切り替える token-level routing を、実際に高速に serving (推論サーバとして運用) するための system 論文。token-level routing はアルゴリズムとしては品質と効率の改善が報告されているが、既存の serving system は「1 つの LLM を回す」前提で作られており、モデル間で decoding の step がずれる (step desynchronization) ことや batch に入るまでの待ちが大きく、実装も複雑になる。これを解消して decoding throughput を 2.01〜64.15 倍にしたと主張する。

## 手法の核心

- request-centric programming, model-centric execution: 開発者は「1 つの request がどう routing されるか」だけを書き、runtime が LLM ごとに subserver (そのモデル専用の推論プロセス) を立てて request を非同期に振り分ける。
- 各 subserver が delayed-batching scheduler (batch を少し待って大きくまとめる scheduler) を持つ。待ち時間などの hyperparameter は、system の throughput を表す数理モデルから最適値を導出する。
- token ごとにモデルが変わると、request ごとの進み具合が揃わなくなる。非同期 dispatch でこのずれを許容するのが設計の肝。
- 様々な routing algorithm・workload・model pair で評価し、既存 system に対する throughput 向上を報告している。コードは公開予定/公開済みと abstract に記載あり (URL は途切れていて未確認)。

## プロジェクトへの適用可能性

- **P2 (Foundation Model 蒸留 + 適合)**: 蒸留の目的は「大きな teacher の品質を小さな student で出す」ことだが、token-level routing は「易しい token は小モデル、難しい token だけ大モデル」という別解。蒸留した student と元の teacher を組む hybrid 構成が成立するかの比較対象になる。routing が効く token の割合は、student が teacher にどれだけ届いていないか (capacity gap) の診断にも使える可能性がある。
- **P1 / P3**: 直接の接点は薄い。VLA (Vision-Language-Action; 画像と言語から行動を出す大型モデル) を車載で動かす場合に、軽いモデルと重いモデルを切り替える発想は参考になるが、本論文は LLM の text decoding が対象で、運転のような低 latency の制約は扱っていない。

## 試すべき実験アイデア

1. 手元の蒸留済み student と teacher の組で、token ごとの logit の差 (または entropy) を測り、「student で十分な token の割合」を出す。routing の余地がどれだけあるかを、serving system を入れる前に見積もる (数時間で可能)。
2. 上記の割合が高ければ、既存の token-level routing 実装を使って品質-コストの Pareto (どちらも良い側の境界) を、student 単体・teacher 単体と比較する。
3. TokenRouter 本体は GPU を複数使う serving 規模の話なので、まず 1 を済ませてから本文とコードを確認する。

## 注意点

- 数字 (2.01〜64.15 倍) は比較対象 system と条件の幅が大きく、abstract だけでは何に対する倍率か判断できない。
- 研究対象が serving 効率であり、モデルの精度改善ではない。蒸留 recipe として直接使える知見は無い。
