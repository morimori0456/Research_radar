# Unlocking Lossless Speedups in LLMs via Discrete Diffusion (Uno)

- arXiv: https://arxiv.org/abs/2609.04010 (2026-09-02)
- topic: sns_wildcard で配信 → **fm_distill_finetune / P2 に再分類** — スコア **4.0** (hf_upvotes 63)
- 再分類の根拠: 中身が Diffusion Distillation という蒸留 recipe であり、`relevance_criteria` の「再現可能な recipe / 新しい loss」に正面から当たる。HF 経路で来ただけで分野外ではない。

## 何を解決する論文か

LLM が速くならない理由は **NTP (Next-Token Prediction; 次の 1 トークンを当てる学習目標)** から来る **AR (autoregressive; 直前までの出力に条件づけて 1 個ずつ生成する)** 構造にあり、生成が逐次になる。本論文は **AR モデルの分布はそのまま定義しておきながら、diffusion (ノイズから多数の位置を並列に復元する生成方式) を使ってその分布から複数トークンを同時に引く**、diffusion-augmented LLM を提案する。狙いは **lossless** な高速化 —— 元の AR モデルの品質を落とさずに throughput だけ上げることである。

## 手法の核心

- **パラメータを 2 組に分離する。** **AR weights** は通常の NTP で学習する。別に**軽量な diffusion weights** を置き、こちらだけが「複数トークンを同時に出す」役を負う。
- **Diffusion Distillation phase。** diffusion weights の学習は、既存の LLM 学習パイプラインに足す短い工程として行う。追加コストは僅少と主張。**teacher は外部の大モデルではなく、自分自身の AR 分布**である (self-distillation)。
- **Ψ-Spec** — sampler (生成時の引き方) の族。**context 長を固定したまま** lossless な加速と **inference-time scaling** (推論時に計算を積んで品質を上げる操作) を可能にする。
- **既存 2 路線との差。** **speculative decoding** (小さな draft model に先を読ませ、本体でまとめて検証・棄却する高速化) と違って **draft model が要らない**。**d-LLM (diffusion LLM; 生成全体を diffusion で置き換えたモデル)** と違って**元の AR モデルの品質を犠牲にしない**。
- **結果。** 既存の open-weight AR LLM を「増築」しても、ゼロから学習してもよい。評価した全 batch size で主要な speculative decoding 系より高 throughput、base AR 比で最大 3 倍。8B の Uno が 26B の DiffusionGemma を上回る。

## P2 / R2 への適用可能性

**R2 の現在の軸は「支配変数は loss ではなく、監督を当てる範囲である」**(UC-MOPD / Echo-GRPO / DART-SD の 3 例が同じ方向を指した結果として立てた軸)。本論文は、**その軸のほぼ純粋な操作実験になっている**点で価値がある —— 監督の *中身* は AR 分布のまま一切変えず、**当てる範囲だけを「1 位置」から「複数位置の同時分布」に広げている。**loss 族の入れ替えでも容量の増減でもない変数が動いているので、R2 の軸が正しければここでも効くはずである。

**当初仮説 (容量差が破綻の原因) への含意も明確。**AR weights を凍結したまま軽量な diffusion weights を足す構成は、student 側の容量が teacher 以上になる側 —— **すでに棄却済みの「容量比 1.0 でも効く反例 5 本」と同じ側**に、6 本目として乗る。容量比では説明できない例がまた 1 つ増えた、という位置づけで在庫に足せる。

### 試すべき実験アイデア

1. **過去の蒸留ログの再解析に「監督位置数」を軸として足す。**R2 の次アクションは「過去ログに CLL (Concentration of Log-Likelihood; 対数尤度が少数トークンに集中する度合い) を後付けし、上位 1% 占有率が容量比とともに単調に動くか」だった。ここに**監督が当たった位置数**を第 2 軸として記録すれば、同じログから軸の当否を 2 通り検定できる。**追加の学習は不要で、集計スクリプトの列が 1 本増えるだけ。**
2. **lossless の定義を検証の起点にする。**「品質を落とさない」が (a) 出力分布の一致なのか (b) ベンチマークスコアの一致なのかで、蒸留の話としての意味が変わる。(a) なら R2 の「監督範囲」軸に厳密に乗り、(b) なら乗らない。**本文で最初に確認すべき 1 点。**

> **注意:** abstract は比較対象の記述の途中 (`the proprietary Me...`) で切れている。3 倍・8B 対 26B といった数値は本文で確認すること。また Diffusion Distillation の「negligible overhead」は相対値であり、絶対の GPU 時間は abstract に無い。
