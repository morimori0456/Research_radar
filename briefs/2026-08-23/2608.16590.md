## 何を解決する論文か

**end-to-end の policy model (画像などの観測から行動を直接出す学習モデル) は単体では取りこぼしが多い。そこで policy の外側に agent を置き、失敗を検知して立て直させる構成 —— harness (方策を包んで実行を管理する外殻) —— が広まった。**

**ところが既存の harness はほぼ全て open-loop である。** rollout (方策を環境で実際に走らせた 1 エピソード) の最中は**あらかじめ決めた skill を順に実行するだけ**で、振り返りはエピソードが終わってからしか行われない。

**この post-hoc reflection (事後の振り返り) では、実行が進行している最中を支配できない。** 理由は単純で、**物理的な相互作用ではロボットと環境の状態が刻々と変わり、それに追随する判断周期が、今日の大きな agentic model の推論速度を超えているから**である。要するに **「考えてから動く」では間に合わない。**

**Zetta の答えは、判断を 1 つの周期に押し込むのをやめ、3 つの時間スケールに分けることである。**

## 手法の核心

- **base policy は凍結したまま、周りの足場だけを進化させる。** 学習し直すのは方策の重みではなく、**code-based runtime critic (実行中に方策の出力を監視して異常を判定する、コードとして書かれた判定器)** と **recovery skill (失敗から立て直すための復帰動作)** である。**方策には一切触らない。**

- **3 つの time-scale separated loop (時間スケールを分離したループ) —— ここが本論文の構造そのもの。**
  1. **action-frequency governance**: 行動の周期で効く監督。ここは大きなモデルを呼ぶ余裕がないので、コードとして書かれた critic が担う。
  2. **rollout-level critic-recovery proposal**: 1 エピソード単位で、critic と復帰動作の候補を提案する。ここは遅くてよいので agentic model が担える。
  3. **validation-gated skill update**: 提案された skill は、検証を通ったものだけが採用される。**思いつきをそのまま本番に入れない関門。**

- **critic が「学習された判定器」ではなく「コード」であること。** 実行が速く、中身を人間が読めて、なぜ発火したかを説明できる。**agentic model は critic を*書く*側に回り、*判定する*側には立たない。** 遅いモデルを遅くてよい場所に、速い判定を速い場所に置いた配置である。

- **Z-Infra**: agent のロジックと、異種の実行資源 (実機・シミュレータ等) を切り離す rollout 基盤。**手法の主張ではなく、self-exploration を現実的な時間で回すための土台。**

- **結果**: LIBERO-Pro と RoboCasa (いずれもロボット操作の標準ベンチマーク。多数のタスクで方策の成功率を測る) で **90.8% / 93.6%**、**推論 11.1 倍高速化**。自己探索の経験量に応じて成功率が伸び続け、獲得した skill は **zero-shot (追加学習なしで) 他へ転移**する。

## 追っているプロジェクトへの適用可能性

### P1 / R1 —— 本日いちばん効くのはここ。W34 課題カード 3 の「measurable でない」に、実装可能な形が与えられた。

**W34 のカード 3 は *takeover lead time* —— システムが自分の失敗を、人が介入できるだけ手前で予告できたか —— を測れと書いた。だが「何をもって予告とするか」の実装が空いていた。Zetta の action-frequency critic は、まさにその予告器の作り方である。**

そして **R1 が 08-18 に決めた「審判に学習モデルを使わない」と、本論文は正面から整合する。** 08-21 の SemComp-Bench は VLM を審判に据えた例で、R1 の立場と対立していた。あのとき出した精密化は「学習審判を使うなら判断を検証可能な粒度に分解せよ」だった。**Zetta はさらに踏み込んで、判定器そのものをコードとして外に出す。** 分解ではなく**種類の分離**である —— 生成は学習モデル、判定はコード、採用は検証。**R1 の規範をもう一段書き直せる: 「学習モデルは審判を*書いて*よいが、審判を*務めて*はならない」。** 否定形でも条件付きでもなく、役割分担の規範になる。これは通しやすい。

**さらに W34 カード 1 (「臆病すぎる」と「強引すぎる」を 1 本の operating curve にする) との接続。** critic は本来、両側に置ける —— 衝突リスクを検知する critic と、不要な停止を検知する critic。**両方を実行時に走らせれば、カード 1 が「分母が観測不能」と諦めた不要停止側に、少なくとも*発火回数*という観測量が入る。** 真の分母は依然得られないが、**同一の critic を全 planner に当てれば比較は成立する。** 絶対値を諦めて相対比較に落とす、という逃げ道が見えた。

### P3 / R3 —— 「統合はモデルの中でやらなくてよい」という対抗仮説。

**R3 は VLA × world model の統合アーキテクチャを探しており、暗黙に「1 つのネットワークに統合する」を前提していた。本論文はその前提を外す。** base policy を凍結し、能力の追加を外側のコードと skill に置く。**分類マップの軸に「統合の場所: 重みの内側 / 実行時の外殻」を足すべきである。** 08-22 の EnvHarness と並べると意味がはっきりする —— **EnvHarness は環境 (試す側) を凍結核の外で作り変え、Zetta は監督と復帰 (実行側) を凍結核の外で作り変える。分野も著者も違う 2 本が、同じ週に、同じ設計原理に独立に到達している。** 「凍結した基盤モデル + 進化する足場」は、今の潮流として書ける。

### P2 / R2 —— fine-tuning の対抗手段としての「重みを触らない適合」。

**08-22 の Self-Demonstrated Generative Control は、新機体での性能劣化を自己生成 rollout を混ぜた fine-tuning で解いた。Zetta は同じ問題に重みを一切触らずに答える形になっている。** **W34 カード 2 (retrofit / embodiment gap) は「機種を跨いだ性能保証の手段がない」と書いたが、保証の手段として「機種ごとに critic と recovery skill だけを差し替える」は、fine-tuning より検証が容易である —— コードは読めるが重みは読めない。** R2 の capacity gap とは別軸だが、**「適合に必要なものは本当に重みの更新か」という問いは P2 の前提に直接刺さる。**

## 留保 (読む前に持っておく疑い)

1. **「state-of-the-art **under our current rollout budget**」という条件付きの主張。** 計算量を揃えた比較なのか、単に多く回したのかが abstract から読めない。**本文で最初に確認する箇所。**
2. **11.1 倍高速化の比較対象が不明。** 「毎ステップ agentic model を呼ぶ harness」に対してなら当然であり、主張としては弱い。
3. **LIBERO-Pro / RoboCasa はいずれもシミュレーション。** 「physical intelligence」を掲げる論文としては、実機の結果がどこまであるかが評価を分ける。
4. **validation-gated というが、検証に使う分布が学習と同じなら過適合を止められない。** held-out での検証かどうかは要確認。**08-22 の EnvHarness に対して立てたのと同じ疑い** (共進化がベンチマークへの過適合を生まないか) が、こちらにも同じ形で当てはまる。
5. **"Aha Moments" は測定ではなく修辞。** 定量的な裏付けがあるかを見て、無ければその段落は読み飛ばしてよい。

## 試すべき実験アイデア

1. **【優先度・高／2〜3 日】code-based critic を driving planner に 2 つ書く —— 衝突側と過保守側。** 前者は TTC (Time-to-Collision; 現在の相対速度のまま進んだ場合に衝突するまでの残り時間) が閾値を割ったら発火、後者は「前方に障害がないのに停止・徐行が N 秒続いたら発火」。**nuPlan か CARLA で planner の保守性パラメータを 5 点振り、W34 カード 1 が求めた散布図の縦横を、衝突率と*不要停止 critic の発火率*で描く。** カードは「不要停止には分母がない」で止まっていたが、**critic の発火回数を代理の分子にすれば、少なくとも planner 間の相対比較としての曲線は引ける。** 論文 figure 1 の候補がここで実物になる。

2. **【優先度・高／1〜2 日】critic の発火時刻と失敗時刻の差分 = lead time の分布を測る。** W34 カード 3 が要求した *takeover lead time* そのものである。**失敗ログを集め、critic が何秒前に発火していたかをヒストグラムにする。** 「0.5 秒で介入可能／2 秒あれば可能／予告以外に手段なし」の 3 分類は、この分布から機械的に出せる。**カードでは人手分類の作業として書いたものが、critic を 1 本書くだけで自動化される。**

3. **【優先度・中】凍結 vs fine-tuning の直接比較。** 同じ embodiment gap に対し、(a) Zetta 流に critic + recovery skill だけ差し替える、(b) 08-22 の SDGC 流に自己生成 rollout で fine-tuning する。**回復した性能あたりの「検証コスト」で比べる。** 重みを更新しない側は再検証が軽い、という仮説が立つかを見る。P2 の「適合に重み更新は要るのか」に自分の数字が持てる。

4. **【優先度・中】validation gate の効き目を壊してみる。** 検証を学習と同じシナリオ分布で行った場合と、held-out で行った場合で、採用される skill の質がどう変わるか。**留保 4 を自分で潰す実験であり、同時に 08-22 の EnvHarness に対する疑い (共進化の過適合) と共通の答えを出す。1 つの実験で 2 本の論文への疑問が片付く。**
