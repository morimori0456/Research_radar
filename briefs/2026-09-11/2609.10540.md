# Programmable World Model — world state の更新を、生成モデルから引き剥がして「プログラム」に任せる

**topic:** next_arch (P3) / **project:** P3
**hf_upvotes:** 59 / **公開:** 2026-09-09T17:59:32Z
**スコア:** **P3 4.0** / P1 2.5 / P2 1.0

## 何を解決する論文か

video world model (映像を生成しながら世界の推移を模擬するモデル。ユーザ入力に応じて次のフレームを作り続ける) は、見た目のリアルさと対話性を急速に上げてきた。**だが長い対話を通して world state を保持する仕組みも、ルールを守らせる仕組みも持っていない。**画面外に出た物体は消え、体力や所持数のような非視覚的な属性は保存されず、「壁は通れない」といった規則は生成モデルの気分次第になる。

**Programmable World Model の設計判断は 1 行で言える: world state の更新と、映像の生成を、完全に分離する。**状態は決定的なプログラムが更新し、生成モデルは**その状態を絵にするだけの renderer に降格する。**

## 手法の核心

- **自然言語の指示を、エージェントが実行可能なプログラムに翻訳する。**プログラムが記述するのは **entity state (各実体の状態) と state-transition rule (状態遷移規則)。**
- **軽量なエンジンがそのプログラムを実行し、明示的で永続的な global world state を保持する。****画面外の実体も、非視覚的な属性も、ここに残る。**生成モデルは状態を持たなくてよい。
- **状態と映像を繋ぐ中間表現が state-augmented 3D OBB (oriented bounding box; 姿勢を持った 3 次元の直方体)。**各実体を「位置・姿勢・寸法 + 状態」の箱として表す。
- **OBB と target camera trajectory (見せたいカメラの動き) を、決定的に pixel-aligned な時空間 conditioning 信号にコンパイルし、事前学習済み video model に渡す。****「決定的に」が重要で、ここに学習は入らない。**生成モデルは条件付き renderer として使われる。
- **CombatStateBench を新たに提案。**programmable world model の評価用ベンチマーク。**Count Accuracy 94% / State Accuracy 98%** で既存の interactive video world model を大きく上回り、長時間の一貫性も保つ。

## 追っているプロジェクトへの適用可能性

### (1) P3 への含意 —— world model は必ずしも「全部を 1 本のネットワークで予測するもの」ではない

**P3 で world model を検討するとき、暗黙の前提として「観測の未来を予測するネットワークを 1 本学習する」形が置かれがちである。本論文はそこに楔を打つ:**

> **予測すべき量には、決定的な規則で書けるものと、学習しないと書けないものが混ざっている。分けたほうが、両方とも良くなる。**

自動運転に引き直すと分かりやすい。**車両運動学、交通規則、車線の接続関係 —— これらは決定的に書ける。**書けないのは、**他車の意図と、その意図が生む多峰性**である。**「全部を 1 本の生成モデルに predict させる」設計は、書けるものまで学習で当てさせている。**その分のサンプル効率とルール遵守を捨てている。

**Bench2Drive のような closed-loop シミュレータは、実はこの分離を既にやっている** (物理エンジンが状態、レンダラが絵)。**本論文の新しさは、その分離を「生成 video model の時代にもう一度やる」点にある。**

### (2) P1/R1 との接続 —— 「シナリオを言語で書いて、決定的に実行する」

**R1 で safety-critical シナリオを扱うなら、これは使える形をしている。**09-10 の [PlannerForge](../2026-09-10/2609.08965.md) が示した問題 —— **生成された safety-critical シナリオの過半が物理的に妥当でない** —— は、まさに**「状態遷移を生成モデルに任せた」ことの帰結である。**

**Programmable World Model の答えは直球で、状態遷移をプログラムに書けば物理的妥当性は構成的に保証される。**シナリオを自然言語で書き、プログラムにコンパイルし、決定的に実行する。**生成モデルは絵を作る段階にだけ関わる。**

**この 2 本を並べると、R1 のシナリオ生成に関する立場が 1 文で書ける:「シナリオ生成の妥当性は、生成後に検査するのではなく、状態遷移を決定的にすることで構成的に保証すべきである。」**

### 試すべき実験

1. **CombatStateBench の評価軸だけを借りる。**Count Accuracy (実体の個数が合っているか) と State Accuracy (状態が合っているか) は、**運転シナリオにそのまま移せる** —— 「シナリオ中の車両台数は保存されているか」「先行車の車線は指示通りか」。**生成シナリオの妥当性を測る指標として、TTC より先にこれを見るべきである。**
2. **P3 の world model 検討で、「決定的に書ける部分」の棚卸しを 1 枚作る。**列は「量」「決定的に書けるか」「書けない理由」。**この表を作る作業は 1 時間で終わり、そのあとの設計判断を全部支える。**
3. **OBB を中間表現に置く構成は、自動運転では既に馴染みがある** (3D 検出の出力形式そのもの)。**既存の検出器の出力を、そのまま world model の条件付け信号に流用できるかを見る。**

## 注意点

- **デモは「ルールが事前定義された遊べるゲーム」であり、開いた実世界ではない。**ルールを人が書ける領域でしか成立しない。**運転で「他車の意図」をプログラムに書こうとすると、そこで破綻する** —— **書けないから学習しているのだ、という反論は正当である。**本論文の分離は、書ける部分を学習から外す効果はあるが、書けない部分を解決してはいない。
