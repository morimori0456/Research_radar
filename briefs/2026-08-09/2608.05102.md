# ABSeeker: Training Long-Horizon Search Agents via Answer-Backtracked Credit Assignment

**topic:** sns_wildcard (EXPLORE) ・ **arXiv:** 2608.05102 ・ **published:** 2026-08-04 ・ **hf_upvotes: 63**

> **wildcard 枠 (分野外の探索枠、本日の初出候補)。** 本業は「Web を何十回も検索して答えにたどり着く LLM agent の学習」で自動運転からは遠い。採用理由は、本日もう1件の [[2608.05987]] (AgentOPSD) と **同じ問題 (疎な結果報酬から密な段階報酬をどう作るか) を正反対の材料で解いている**ため。2本を並べて読むと「密な supervision の作り方」の設計空間が見える。

## 何を解決する論文か

long-horizon search agent (検索・取得・検証・統合を何ステップも繰り返して答えを出すエージェント) の学習では、**「最終的な答えが合っていたか」しか報酬がない**。そのため SFT (supervised fine-tuning; 正解の手順をそのまま真似させる学習) でも RL でも、trajectory 内の全ステップが一律に扱われ、**有用な検索と、的外れ・重複した検索が区別されない**。ABSeeker は、**正解から逆向きにたどって中間の手がかりを復元し、それを物差しにして各ステップを採点する**ことで、疎な結果報酬を密なステップ報酬に変換する。

## 手法の核心

- **Answer-Backtracked Clue Recovery (正解からの逆算)。** 質問と ground-truth の答えの両方を持っている学習時の立場を利用し、**「この答えに至るには途中でどんな事実を掴んでいる必要があったか」**という中間 clue (手がかり) を答え側から復元する。前向きに「良い検索とは何か」を定義するのではなく、**ゴールから逆に引いて中間マイルストーンを作る**のが発想の中心。
- **Clue-Anchored Step Scoring (clue を基準にした採点)。** 復元した clue の集合に対して各検索ステップを照合し、**どの clue をどれだけ回収したか**でステップごとの報酬を出す。二値の結果報酬が、ステップ数だけの連続値報酬に化ける。
- **失敗した trajectory も捨てない。** 最終的に答えを外した軌道でも、**途中で正しい clue を掴んだステップには報酬が入る**。逆に、誤った・冗長なステップは抑制される。ここが実務的に一番効く部分で、**成功軌道だけを残す rejection sampling (採点に通ったものだけ学習に使う手法) が捨てている情報を回収している**。
- **SFT と RL の両方に差し込む。** ABC-SFT は各 turn の loss をステップスコアで重み付けし、ABC-GRPO はステップスコアを GRPO (Group Relative Policy Optimization; PPO を簡略化し critic なしで複数回答の相対比較から advantage を作る LLM 向け RL 手法) の報酬として使う。**同じ信号を2つの学習段階で使い回す**構成。
- **少データで効く。** Qwen3.5-4B ベース・**わずか 8.5k 例**の学習で、BrowseComp (実際に Web を辿らないと答えられない難問ベンチ) 37.3%、その中国語版 BrowseComp-ZH 39.1%。さらに context management を併用すると上積みされる (abstract は途中で切れており数値未確認)。

## 追っているプロジェクトへの適用可能性

- **P2 (本命):** 我々の fine-tuning データは基本的に **「成功した走行 = 良いお手本」**という二値で選別している。本論文の主張は **その二値化が捨てている情報が大きい**ということで、実装上は「軌道を採用するか捨てるか」を「軌道内の各区間に重みを付ける」に置き換えるだけで済む。**データを増やさずに実効的な学習信号量を増やす**方向の改善なので、収集コストがかかる我々の設定と相性が良い。
- **P2 (逆算という道具):** 「答えを知っている立場から中間目標を復元する」構図は、運転では **参照走行 (人間のデモや事後的に最適と分かった軌道) から逆に中間サブゴールを引く**ことに対応する。前向きに reward shaping (途中報酬を人手で設計すること) を書くと恣意的になりがちだが、**逆算なら中間目標がゴールから機械的に決まる**ので設計の自由度 = 恣意性が減る。
- **P1 (評価への転用):** clue の回収率という考え方は、そのまま **部分点付きの評価指標**になる。現在の「衝突したか / しなかったか」だけの指標を、**「必要な認知イベント (対向車の存在に気付く、死角を減速で埋める) をいくつ踏んだか」**に分解できれば、失敗走行同士の優劣が付けられるようになる。飽和ベンチ問題への別角度からの答え。
- **[[2608.05987]] との対比 (ここが本日の学び):** 同じ「密な credit を作る」目的に対し、**ABSeeker は ground-truth の答えという外部の正解から逆算**し、**AgentOPSD は teacher と student の確率差という内部のモデル比較から推定**する。前者は正解が明示的に手に入る設定でしか使えないが根拠が固い。後者は正解がなくても回るが teacher の質に全面的に依存する。**我々の設定は「事後的に最適軌道が計算できる」場合が多い = 前者が使える**ので、まず ABSeeker 側から試すのが筋が良い。
- **注意点:** clue の復元自体を LLM にやらせている点が弱点で、**復元された clue が本当に必要条件だったかは検証されていない**。運転に移す場合、「このサブゴールを踏まなければ本当に成功しなかったのか」は反実仮想 (counterfactual) の問題になり、シミュレータで実際に踏まずに走らせて確かめる手間が要る。また BrowseComp のスコア帯 (37%) は絶対値としてはまだ低く、手法が飽和領域で効くかは未知。

### 試すべき実験

1. **逆算でサブゴールを引けるか確認する。** 成功した走行ログ 50 本について、終端状態から逆向きに **「この地点でこの車線/この速度に入っていなければ成功しなかった」区間**を機械的に抽出する (単純には、その区間の行動を摂動して再シミュレートし、成功率が落ちるかを見る)。**抽出された区間が人間の直感と合うか**が最初の関門。
2. **失敗軌道の部分点を測る。** 衝突した走行に対し、1 で作ったサブゴールの回収率を計算する。**回収率が高いのに失敗した軌道**と**回収率が低くて失敗した軌道**が分離できれば、評価指標として使える証拠になる (P1 への直接の成果物)。
3. **重み付き SFT を1本回す。** ABC-SFT に相当する最小版として、既存の imitation 学習の loss に区間重みを掛けるだけの実験を走らせ、**成功軌道のみで学習した baseline と比較**する。失敗軌道を重み付きで足したときに性能が上がるかが本命の検証。
4. **データ効率を測る。** 3 で効くなら、**学習データ量を半分に減らしても baseline に並ぶか**を確認する。本論文の売り (8.5k 例で成立) が我々の設定でも再現するなら、収集コスト削減の根拠になる。
