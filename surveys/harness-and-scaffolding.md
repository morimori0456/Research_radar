最終更新: 2026-08-23

> 既存4サーベイのどれにも収まらなくなったため分離した。**P1(評価環境)・P2(適合)・P3(統合の場所)の3つに同時に効く横断テーマである。**

## 一言でいうと
基盤モデルが十分強くなった結果、性能を決めるのが**モデルの中身ではなく、モデルを包む外殻 (harness) の設計**になった領域。
外殻とは **推論時にモデルの外側に置く足場のコード** —— 処理の振り分け、決定論的な計算、出力形式の強制、実行中の監視、
環境の作り替え、そして評価の採点。**共通する主張は1つ: 遅くて確率的なモデルを、遅くてよい場所・確率的でよい場所に置き、
速い判定と厳密な判定はコードに任せる。** 保証の観点でこれが決定的に効く ——
**コードは読めるが重みは読めない。** 逆に最大の弱点も1つ: **足場は、書いた分しか働かない。**

## 系譜マップ
- **★ 役割の分離 —— 学習モデルは審判を*書いて*よいが、審判を*務めて*はならない(本サーベイの芯)**
  - **Zetta ζ (16590)** — embodied agent の harness。**既存の harness はほぼ全て open-loop** で、
    rollout の最中は決め打ちの動作を順に流し、反省はエピソードが終わってから行う。
    理由の説明がうまい: **物理的な相互作用では状態が刻々と変わり、それに追随する判断の周期が、今日の大きな agentic model の
    推論速度を超えている。だから「考えてから動く」構成は物理的に間に合わず、事後反省に退避するしかなかった。**
    **Zetta の解き方は、判断を1つの周期に押し込むのをやめて3つの時間スケールに分けること**:
    **① 行動の周期で効く監督 / ② 1エピソード単位での改善案の提案 / ③ 検証を通ったものだけを採用する関門。**
    **base policy の重みには一切触らない。学習し直すのは外側の critic と復帰動作だけ。**
    **★ 最も重要な設計判断は critic が学習された判定器ではなく「コード」であること** ——
    速く、人が読め、なぜ発火したかを説明できる。**agentic model は critic を*書く*側に回り、*判定する*側には立たない。
    遅いモデルを遅くてよい場所に置き、速い判定は速い場所に置いた、という配置である。**
  - **AI4AI at Test-Time (12307、W33)** — **強いモデルが弱いモデル用の harness をコードとして書き、
    パラメータは一切更新されないまま 0.49 → 0.91。** 著者自身が利得の源を**決定論的コードへの外出し・routing・回答形式の強制**と明示し、
    **「より長く考えさせたから」ではないと否定。**
    **留保が重い**: harness は**ベンチマークごとに正解データ 5% を見て作り込まれている**ので、
    「能力が移った」のか「採点との噛み合わせを直しただけ」かは分解されていない
  - **独立な傍証**: **MANIGUARD (17386)** が判定に **LTL_f オートマトン**を使い **"rather than learned classifiers or LLM judges"** と明示、
    **CaliBench**(W33)が **FID を避けて閉じた式の参照分布**を選択。**分野も手段も違う複数の論文が独立に同じ結論に至っている**
  - **反対側の実例も押さえる**: **SemComp-Bench (17426)** は VLM を審判に据えるが、
    **全体的な判断を検証可能な二値質問の集合に分解する**という緩和策を持つ。**VibeWorlding**(08-19)は
    **rubric による検証器を評価にも RL の報酬にも同じものを使う** —— **評価器と報酬が同一物であるとき、
    エージェントは検証器の癖に最適化でき、その最適化は評価上は改善として現れる。
    「本当に良くなったのか、物差しを攻略したのか」が原理的に分離できない**(R1 が「学習審判を使わない」根拠として引く実例)
- **★ 環境の側を、中身に触れずに作り替える**
  - **EnvHarness (19880、hf 224)** — 既存の評価環境は**人手で作られ、静的で、方策の弱点を知らない。方策が上達すると差が出なくなる。**
    答えは「環境を作り直す」ではなく **「既存の環境を包む」** で、**内部ロジックに触らないため元の verifier (正解判定器) が必ず保持される。**
    **★ シナリオ生成が実務で信用されない最大の理由が「生成したシナリオの正解を誰も保証できない」ことである以上、
    この設計原理は自動運転の closed-loop simulation に真っ直ぐ刺さる**
  - **OpenART (00677、W33)** — **目標を固定し、環境状態だけを正規の操作で進化させて失敗を探す。**
    重要な数字は攻撃成功率ではなく **「指示文だけを変える手法に対する優位が、単純な環境の約2%から最複雑環境では 17% 超へ広がる」** ——
    **運転に写せば、固定シナリオ集は混雑場面ほど失敗率を過小報告している**
  - **RST (05466、W32)** — 検証済み seed から **(instruction, environment, reference solution, verifier) の4点を整合させたまま再帰的に難化。**
    肝は「作ってから検証」ではなく **「検証を通ったものだけが次の種になる」**(15 ラウンドで強モデルの pass@4 が 90% → 2.5%、1件 $0.05)。
    **ただしターミナルは決定的で verifier が書きやすいという圧倒的に有利な条件があり、
    連続・確率的・多目的な運転で verifier をどう追従させるかが我々側の研究余地**
  - **GaP (05369)** — planner を計算グラフとして生成し、失敗シナリオから回帰テストを自動生成する自己改良ループ
  - **★ 3本に共通する形**: **「凍結した基盤 + 進化する足場」。Zetta は実行側(監督と復帰)を、EnvHarness は試す側(環境)を、
    それぞれ元の中身に触れずに外側から進化させる。分野も著者も違う2本が同じ週に独立に到達した**
- **★ 足場は、書いた分しか働かない —— 本サーベイ最大の弱点**
  - **仕様ベースの検査は書き漏らした危険を原理的に見つけられない (MANIGUARD 17386)**、
    **サンプリングは測度ゼロの不連続モードに届かない ((1-r)^N, 17956)。どちらの手段でも届かない領域が存在し、
    「両方使えば埋まる」は証明されていない**(planner-evaluation サーベイに詳述)
  - **AI4AI の留保も同じ形**: **正解データを見て作り込んだ harness は、その採点との噛み合わせを直しただけかもしれない**
- **足場の側を評価する: 局面分解型の採点**
  - **Beyond Final Scores (13417)** — LLM agent が自律的に研究開発をどこまで回せるかを 7 モデル × 36 の長期タスクで測る。
    **読むべきは agent の話ではなく評価の立て方**: **最終スコアだけを見ていると、進歩がどこで生まれてどこで失われたのかが分からない。**
    run の振る舞いを **問題の立て方 / 実装と実行 / 結果を受けた次の手の修正**の3局面に分解し、
    **ログから機械的に判定できる規則ベースの指標**で測る(**ここでも判定器は学習モデルではない**)。
    結論は **「最終成績が同じ2つの run でも、詰まっている局面は違う」**
  - **論文としての型: LLMRouter (06867)** — **乱立した手法を要素に分解し直し、supervision を自動生成し、
    品質・コストの2軸で測るベンチを出す**というインフラ論文の型。**R1 が評価指標でやろうとしていることと構造がそのまま同じ**(前例として登録)
- **接続: どのプロジェクトに効くか**
  - **P1 / R1** — **critic をコードで書く**ことが、W34 課題カード1(operating curve)と カード3(takeover lead time)の両方に実装を与える。
    **過保守側にも critic を置けば「発火回数」という観測量が入り**(真の分母は諦めて相対比較に落とす)、
    **critic の発火時刻と失敗時刻の差を取れば lead time 分布が機械的に出る**
  - **P2 / R2** — **「適合に重みの更新は本当に要るのか」。** 機種ごとに critic と復帰動作だけを差し替えるほうが、
    **保証という観点では検証が容易である —— コードは読めるが重みは読めない。**
    **比較軸は性能ではなく「回復した性能あたりの検証コスト」**(fm-distillation サーベイと相互参照)
  - **P3 / R3** — **分類マップの軸5「統合の場所は重みの内側か、実行時の外殻か」**(vla-world-model サーベイと相互参照)

## Open Questions
- **★ code-based critic を driving planner に2本書く —— 衝突側と過保守側**(16590 × W34 カード1)。
  前者は TTC が閾値を割ったら発火、後者は「停止してよい条件」を満たさない停止で発火。
  **nuPlan か CARLA で保守性パラメータを5点振れば、カード1 が要求した散布図の実物が出る**
- **★ critic の発火時刻と実際の失敗時刻の差は、どういう分布になるか**(16590 × W34 カード3)—
  **これが takeover lead time そのものである。人手でログを分類する作業として見積もっていたものが、critic 1本で自動化される**
- **★ 既存の driving scenario 1本に EnvHarness 相当の wrapper を手で3つ書く**(19880)—
  他車の反応性を変える / 遮蔽を足す / 到着タイミングをずらす。**自前の planner の成功率がどれだけ動くかを見る**
- **★ 「凍結した基盤 + 進化する足場」は、重みの更新に対してどれだけ安いか**(16590 × 19490)—
  **比較軸は性能ではなく「回復した性能あたりの検証コスト」**
- **AI4AI の利得は「能力が移った」のか「採点との噛み合わせを直しただけ」か**(12307)—
  **harness がベンチごとに正解データ 5% を見て作り込まれている以上、この分解が無いと主張は成立しない**
- **運転の verifier をどう再帰難化に追従させるか**(05466)— シナリオを難しくすると
  **何をもって成功とするかの定義自体が曖昧になる**(譲るべきか進むべきか)。**ここが本丸の研究余地**
- **固定シナリオ集は、混雑場面ほど失敗率を過小報告しているか**(00677)—
  目標固定・環境進化のプロトコルを closed-loop 運転シムで最小構成で回し、**環境の複雑さに対する優位の広がり**を再現できるか
- **harness をコードで書く側に立つとき、そのコードは誰がレビューするのか** —— 本サーベイの全論文が暗黙に置いている前提。
  **「コードは読める」が利点だとして、critic が 100 本になったとき、読めることは維持されるのか**
