# Planner Evaluation & Safe Motion Planning — Living Survey
最終更新: 2026-09-06

## 一言でいうと
自動運転プランナを「衝突率」一本で測る時代を終わらせ、**過保守も含めて保証付きで**測る評価を追う分野。
論点は 採点 → 診断 → 定義の破綻 (W33) → 保証の天井 (W34) → **では何を代わりに測るのか** (W35) と降り、
**2026-W36 で提案が証拠に変わった** —— **集約された指標は、飽和したあとも劣化を報告しない。**これが運転・連続制御・歩行・操作・agent 評価の
**5領域で独立に実測された**以上、指標設計の巧拙ではなく**平均を取るという操作そのものの性質**として書ける。
**証明の型も1文で固まった: 測りたい能力「だけ」を取り上げた対照条件を作り、同じ指標で走らせる。同点が取れるなら、その指標はその能力を測っていない。**
残りは**順序を付ける量** —— **事後に監査するのではなく、失敗が起きる前の状態が持つ余裕 (solvability) を事前に数えること。ここだけがまだ空いている。**

## 系譜マップ
- **★ 集約指標は、飽和したあとも劣化を報告しない —— 対照条件で示す(2026-W36 の芯。R1 の主張の前半が「提案」から「証拠付きの提案」に変わった)**
  - **★ 型: 測りたい能力だけを取り上げた対照条件を作り、同じ指標で走らせる。同点なら測っていない。**
    **5領域で独立に、しかも 2026-09 の1週間に出ている。R1 の導入はこの表を置くだけで書ける**

    | 領域 | 論文 | 飽和していた指標 | 実際には落ちていたもの |
    |---|---|---|---|
    | 自動運転 | **Driving on Memory (31029)** | NAVSIM の集約スコア | **動的シーンへの反応 (そもそも要求されていない)** |
    | 連続制御 | **Intervention Gap (29998)** | reward 予測誤差 | 介入忠実度 → episode return |
    | 運転 (圧縮) | **圧縮運転方策 (00718)** | 集約スコア | **特定の運転 curriculum が丸ごと** |
    | 運転 (学習) | **PDT (02688)** | component BCE | 実際に選ばれた軌跡の質 |
    | 歩行 | WM-LOCO (02542) | 地形をまとめた平均 | 特定地形での全滅 |
    | 操作 | R2S-Eval (03276) | 二値の成功率 | 実行の質・順位の再現性 |

  - **① 情報チャネルを剥がす: Driving on Memory (31029)** — **end-to-end 運転モデルからカメラを丸ごと取り上げ、
    「同じ場所を過去に走ったときの記憶」に差し替える。**記憶は道路の形と走り方の癖は持つが、**いま前に何がいるかは一切持たない。
    それで NAVSIM のスコアがほとんど落ちなかった。**
    **★ 落ちてくる量に注目する: `score(フル観測) − score(記憶のみ)` は、そのベンチマークが実際に測っている「動的シーンへの反応」の幅である。**
    著者は名前を付けていないが実質的な出力はこの差分で、**NAVSIM では小さく Bench2Drive / RealEngine では大きい。**
    **結論は「ベンチが壊れている」ではなく「ベンチごとに反応の余地が違い、それを測れる」。**
    **拡張は自明で安い: チャネルは他車位置 / 他車速度 / 信号状態 / 自車の過去軌跡 / 地図と複数ある。1つずつ落とせば「その指標が何を要求しているか」のプロファイルが出る**
  - **② 測る前に資格を審査する: Intervention Gap (29998)** — **intervention fidelity** (モデルが環境に触れずに想像した数ステップ先の遷移が、
    環境側で同じ介入をしたときと同じようにタスク変数を動かすか) を独立に測れる性質として立てる。
    **この誤差が大きいほど episode return は下がるのに、reward 予測誤差は平坦なままである。**
    **★ R1 にとっての本体は capture-gated という2段構成のほう**: **まずモデルがその問い合わせを内部に表現しているかを判定し、
    表現している事例だけを測定に進める。**表現していないものを混ぜて平均すれば「表現していない」と「表現しているが間違っている」が混ざる。
    **R1 では「分母の健全性」を守りの作業として書いていたが、これは測定手続きの前段として組み込む設計である。図1の骨格がそのまま取れる。**
    > **反直観な副産物: タスク信号を一切使わない自己教師あり world model のほうが、タスクに合わせて学習したモデルより介入の作用素をよく保存していた** (R3 の軸に記録)
  - **③ 段階を分けると、消えた能力が名指しできる: 圧縮運転方策の閉ループ評価 (00718)** — PPO で学習した運転方策から actor を取り出し、
    **圧縮を1段ずつ (structured pruning → distillation → integer quantization) 適用して、各段の出力を5つの driving curricula で閉ループ評価する。**
    **運転能力が最初に失われるのは pruning。distillation は回復させるが rehearsal data の被覆で頭打ち。回復後の quantization で
    「一旦停止して再発進する」curriculum だけが落ちる。そして pruning を通さずに同じ手順を踏むと5つ全部が残る** ——
    **損失は quantization 単体ではなく、pruning が先に壊した上に乗った合成である。段階を混ぜていたら分離できなかった。**
    **★ 代替指標が「新しいスカラー」ではなく「縦=段階 × 横=curriculum × セル=通過/不通過 の表」であることが重要。定義の議論が要らない。**
    ASCEND (NHTSA × SAE ITC) の3要件では **objective と repeatable を満たし proactive を満たさない ——「失敗が起きてから数えている」からで、そこが R1 の差分**
  - **④ 差を主張してよいかを検定する: PDT / Proxy-to-Decision Transfer (02688)** — **proxy objective の改善が実際の意思決定に伝わっているかの検定枠組み。**
    **component BCE が 0.705 → 0.530 と大きく下がるのに、実際に選ばれた軌跡の PDM スコアは 0.963 → 0.961 とわずかに悪化した。**
    **ある候補は 512 件では区間が 0 を含まないのに、2048 件と全データでは含む。432 通りの設定で、データ2分割 × seed 2つの再現ゲートを通ったものはゼロ。**
    **★ R1 との関係は競合ではなく配置**: **PDT は事後 (走らせた結果を対にして検定)、R1 は事前 (現在の状態から計算)。**
    **★ ただし最も危険な隣接概念でもある: `support-versus-selection regret`** (良い軌跡が候補集合に在ったか / 選べたかを分離する量) は
    **既存概念の中で solvability に最も近い。**違いを図1のキャプションで書けなければ「言い換え」と読まれる。
    **そして R1 が受け取るべき最大の指示: 主張を「solvability を入れると順位が変わる (小さく勝つ)」から
    「集約スコアが同じ2つの場面を solvability が分ける」へ変えること。前者は PDT が 432 設定で潰した領域に入り、後者は同じ検定に晒されない**
  - **⑤ 同じ不満が別領域で: R2S-Eval (03276)** — 実機の操作評価は人手がかかり、**同じ方策を測り直すと順位が変わり、
    二値の成功率からは「どう下手なのか」が分からない。**対策は real-to-sim 較正 + VLM の対比較。
    **★ 手法ではなく「順位の再現性を評価手法の欠陥として扱った」点を借りる —— R1 が「solvability は順位を入れ替える」と言う瞬間に最初に問われるのがそこである。
    PDT の two-half / two-seed ゲートと合わせ、順位の安定性は最初から測って出す。後から言われて足すのでは遅い**
  - **★ 学習側にも同じ失敗がある (IMPACT 00161)** — 全体で平均を取る MSE の denoising objective の下では、
    **画面の大半を占める静止内容が最適化を支配し、面積は小さいが相互作用に決定的な動的物体が不釣り合いに学習されない。**
    > **評価: 集約された指標は、稀だが決定的な部分を隠す。 / 学習: 集約された目標は、稀だが決定的な部分を学ばせない。**
    **★ 評価側だけで論じると「指標の設計が下手だっただけでは」と読まれる余地があるが、学習側でも独立に報告されているなら、
    これは設計の巧拙ではなく平均を取るという操作そのものの性質である。引用1本で主張の一般性が上がる。**
    **同時に R1 への警告でもある: 走行ログで solvability を集計するとき大半の時間は「逃げ道が十分ある」状態なので、
    そのまま平均すれば決定的な数秒が薄まる。自分の指標の集計側で全く同じ罠を踏みうる。平均を出す前に分布を見ること**
  - **★ 抜け穴には2種類ある (Self-Play Driving 30819)** — self-play で育てた運転方策は**信号で reward hacking を起こし、
    一時停止標識には止まる動機がそもそも無かった。**著者は **抜け穴 (別の方法で点が稼げる) と 欠落 (項が無い)** を区別している。
    **前者は報酬を締めれば直り、後者は項を足さないと直らない。R1 の「抜け穴監査」はこの2種類を両方カバーしないと成立しない**
- **★ 衝突率の隣に置く3つの量 —— 1回のログ走査で全部出る(2026-W35 の芯。R1 の第一図)**
  - **① 逃げ道の本数: solvability (RoG-DAgger 24525)** — **「いまこの状態から、まだ助かる候補が何本残っているか」**を
    kinematic rollout (車両の運動モデルで数秒先まで空走させる計算。学習不要) で数える。ゼロになる直前が
    **point of no return (これ以降は何をしても助からない点)。** 論文は学習の介入タイミングを決めるために作ったが、
    **評価指標として独立に使える。★ 1つの量の両端に危険と過保守がそろって載る** —— **ゼロに近づく頻度が高いのが危険、
    常に多すぎるのが過保守。** R1 が9週間探していた「過保守を測る量」がこの形で出た。
    **後付け計算は半日・学習ゼロ**(SimLingo で Bench2Drive +5.3、Longest6 v2 は 22 → 44、Fail2Drive 55% → 66%。
    **ただし 22 は長距離で実質破綻していた水準であり、倍という表現に引っ張られないこと**)
    > **移植前に決めるべき恣意性**: 候補の張り方 (本数・格子の粗さ・horizon・「助かった」の判定) を変えれば残存本数は動く。
    > **絶対値が候補設計に依存するなら、planner 間の比較には使えてもシーンの危険度を表す量としては使えない。**
    > 正規化 (初期状態での残存本数で割る等) を先に定義すること —— **これは移植ではなく我々の貢献になる。**
    > もう1つ: **kinematic 近似は低摩擦・高速域で楽観側にずれ、「まだ助かる」と誤判定する。指標の妥当性は近似の妥当性を超えない。**
  - **② 逃げ道の種類数: mode coverage (Anytime GTMP 25830)** — **solvability を homotopy class
    (障害物にぶつからず連続変形するだけで移り合える経路の同値類。要は「柱の右を通るか左を通るか」) で数え直したもの。**
    **逃げ道が10本あっても、全部が「少し右にずれる」なら種類としては1つ。**
    論文はサンプルしたグラフ1つで極端に細い隙間を除く全類を覆えることを証明し、**既存の効率的手法が解を1〜2 類に集中させる**ことを実験で示した。
    **★ ここから過保守の捉え方が変わる: 過保守は「重みが保守的すぎる」という連続的な問題ではなく、
    「候補集合が構造的に痩せている」という離散的な問題として書き直せる。**待つ以外の類を生成していないから待つのである。
    **AD での実装は近似で足りる** —— 前方障害物に対し「左/右/停止」の3値ラベルを軌跡と障害物の位置関係から機械的に付けるだけ。
    **理論からの持ち帰り: 幅 (各層のサンプル数) を広げると取りこぼし確率は指数的に下がるが、局所 planner を強くしても必要な層数は sublinear にしか減らない**
    —— **計算資源は賢い局所 planner ではなく幅に使え。** 比較にならない差がついている
  - **③ 分母の健全性: 抜け穴監査 (PDPO 27158)** — 著者は crowd navigation ベンチマークに**明示的な境界条件が無い**ことに気づき、
    **学習したエージェントが有効領域の外へ出て混雑を迂回していた**ことを発見した。**成功率は上がる。だが解いていない。**
    境界逸脱を衝突として数える設定を足すと、**評価を厳しくした側でこそ設計判断 (action chunk) の優劣が入れ替わった。**
    **★ AD での同型はすぐ思い当たる: 経路から逸脱して交通の薄い側へ出る / 極端に減速して評価区間内に危険地点へ到達しない /
    シナリオ終了まで停止し続ける。どれも衝突率は改善し、どれも運転として失敗している。**
    **監査は3列で足りる (経路逸脱量・平均速度・危険地点到達)。「衝突ゼロだが危険地点に一度も近づいていない」割合が出れば、
    それ単体で図が1枚成立する** —— 「現行の衝突率は、この割合ぶん水増しされている」
  - **★ 3つは同じ rollout 積分から落ちる。**solvability を計算するコードに列を足すだけで mode coverage と抜け穴監査が同時に手に入る。
    **どれか1つでも planner の順位が動けば、R1 の主指標がその場で決まる。動かなければ R1 は保証の付け方に新規性を寄せる。どちらに転んでも決着する**
  - **★ 定義の空欄が 2026-W36 で全部埋まった —— もう発明する部分は残っていない**
    - **候補の張り方 (W35 の精読で最大の未決だった): Versatile Samples (01799)** — **記録された人間の軌跡を、車両が実際にずれうる2方向へ押し出す ——
      横は走行可能領域の境界へ、縦は前走車へ。**摂動の生成規則は論文にあり、衝突・走行可能領域の判定は NAVSIM の既存判定器がそのまま使える。
      **定義は1文で書ける: 「記録された自車軌跡を横 M 段 × 縦 N 段に摂動して K 本張り、各時刻で衝突せず走行可能領域に留まる本数を solvability とする」。**
      **★ 副産物として mode coverage の前提を自分で示す必要が無くなった** —— 「強い planner ほど候補が安全な挙動の周りに固まる」という観察が、
      **scorer の学習という別目的から独立に報告されている。R1 は「その偏りを測る量を出せ」と言えばよい**
      > **警告として読む点: 本論文の改善幅は +0.4 / +0.3 EPDMS。桁としては PDT が「判定不能」に分類した領域に入る。R1 が同じ桁の改善を主張する側に回ってはならない**
    - **判定器の連続量版: SV-WAM (03602)** — **differentiable drivable-area compliance regularizer** (自車の車体四隅が
      走行可能領域の境界に近づくことを微分可能な罰則にする項) は、solvability の判定とほぼ同じ計算である。
      **★ 図1は「生存本数 (0/1 の数え上げ)」と「境界余裕の最小値 (連続量)」を同じ時系列に重ねて出せる。どちらが衝突の手前で先に落ちるかが、そのまま指標選択の根拠になる。**
      > **同時に防御線が要る**: 本論文は同じ量を**学習の loss** に入れて planner を強くする側で使っている。**R1 が同じ量を評価指標として出すと「それは学習に使う量だ」と返される。
      > R1 の防御線は「1本の軌跡の余裕」ではなく「候補集合の生存本数」という集合量にある。この一文を introduction の最初の段落に置くこと**
    - **図の形: HarnessDev (01437)** — **capability (タスク成功) と efficiency (実行 token 量) を対で報告し、単一スコアに畳んでいない。
      そして片方だけでは順位が付かないことを結果で示している。**R1 の言い方は最初から「衝突率の**隣に**置く量」だったので、
      **図1を solvability 単独の折れ線ではなく「solvability × 衝突率」の2軸図にする根拠が、これで外部から取れる。**
      加えて **hidden evaluation tasks を開発から隔離する設計は、抜け穴監査の実装形そのもの**であり、運転分野の外に既に実施例があると書ける。
      **同じ指標がドメインによって参照実装を上回ったり下回ったりする点も実測であり、R1 を nuPlan と NAVSIM の両方で出すべき理由になる**
    - **どの段で測るかの梯子: Qwen-Drive-1.0 (00111、hf 335)** — **open-loop / pseudo-closed-loop / closed-loop の3段を1本の論文の中で全部走らせている。**
      **R1 は「衝突率の隣に置く量」を提案する以上、その量をどの段で測るかを明示しないと査読で最初に突かれる。3段を借りて1行書けば済む (30分)。**
      設計側で面白いのは **外付けの BEV head を性能向上の部品ではなく「共有表現からどれだけ 3D 情報が取り出せるか」を測る probe として置いている**点 ——
      **中間表現を外から検査できるようにすること自体が設計目標になっている**
    - **隣接概念の言い換え可能性: WM-LOCO (02542)** — 四足歩行の **foothold feasibility (足を置ける場所が何箇所あるか)** は、
      **「衝突せず走行可能領域に留まる候補軌跡の本数」と同じ形をしている。書き直せるなら、R1 の主張は「新しい量」ではなく
      「既知の量を運転の閉ループ評価に持ち込んだ」に変わる。これは弱くなるのではなく通りやすくなる** (RoboPAD の 5 ページならこちらが安全)。
      **ただし WM-LOCO は先読みを学習して内部に持つ (外から読めない)。R1 は同じ情報を計算して陽に数える (読めることが目的)。
      R1 の位置は「事前に・陽に・読める形で」の3語で書ける**
- **★ 測る側が汚れている2型(2026-W35 で確定。R1 の主張の前半)**
  - **型1: 抜け穴 —— エージェントは指標から逃げる (PDPO 27158、上記③)**
  - **型2: 採点器の癖 —— モデルに採点させると judge のバイアスが混入する (VBVR-Pro 26105、hf 205)。**
    処方は **指標を「決定的な規則だけで計算できるか」で2分すること。**判断が混ざるものは保証の対象から外すか、決定的な近似に置き換える
  - **★ 傍証: 素朴な基準線が無い数字は解釈できない (SIREN-Bench 24094)** — 緊急車両との相互作用で
    **学習済み軌跡予測器9種が、「今の速度で直進し続ける」と仮定するだけの constant-velocity reference に平均で勝てなかった。**
    正しい読み方は「学習ベースは無意味」ではなく **「既存データで学習した予測器は、緊急車両との相互作用に一般化しない」**だが、
    **評価する側にとっては同じ結論に行き着く。** 失敗の分解も実用的で、「難しいシナリオ」ではなく **「どのモジュールにとって難しいか」**で切っている

      **過保守さの第一候補「モード取り逃し率」(真の分布にあったモードのうち planner が候補に残さなかった割合)はここから来る**
  - **層3: 使う側の定義 —— 目的関数・プロトコル・粒度**
    - **The Objective Is the Bottleneck (12959)** — 予測器は余っている(75 ステップ先でも静止仮定の 0.189 倍)のに
      **planner は 25 ステップ先しか想像していない**。壊れているのは **潜在二乗距離というコスト**で、真の距離との相関は
      **r=0.426、約80 unit で飽和し 120 を超えると減少に転じる(ゴールから離れるとコストが下がる領域が実在する)**。
      **予測精度と長horizon 成功は逆順に並ぶ —— 予測損失で checkpoint を選ぶと最も下手なものを選ぶ。**
      **フレーム間隔だけを教師にした temporal distance head** は空間距離の予測としては劣る(r=0.819 対 0.9897)のに planning は上手い:
      **壁越えコストを 24% 高く見積もる(二乗潜在距離は 4% 低く)= 学習されたのは proximity ではなく reachability**。
      再学習ゼロで到達率 **26.0% → 98.0%**、予算 1/3 でも 92.0%
    - **処方の側: AirForesight (12835)** — 中間表現から復号した軌道が**専門家の行動方向と一致するよう縛る
      cross-space planning consistency loss** 1本。**12959 が診断、本論文が処方**という対で読む(UAV 由来、移植できるのは loss の形だけ)
    - **プロトコル: OpenART (00677)** — **目標を固定し、環境状態だけを正規の操作で進化させて失敗を探す**。
      重要な数字は攻撃成功率ではなく **「指示文だけを変える手法に対する優位が、単純な環境の約2%から最複雑環境では17%超へ広がる」**。
      **運転に写せば、固定シナリオ集は混雑場面ほど失敗率を過小報告している**(分野外からの独立証拠なので査読で強い)
    - **粒度: Environment Scaling (03571)** — 環境は増やすより選べ。**見た目(ドメイン・画面)で多様性を測ると、
      同じ能力しか要求しない環境が並んでいても「多様」と誤判定する**。評価スイートを本数ではなく
      **「要求される判断のカバー率」**で語り直す(**FactorDrive (09591) の PCF が、その語彙をゼロから作らずに済む候補**)
- **学習済みモデルの外側に決定論的な検証層を貼る(2026-W33 で定着を確認)— ネットワークは提案し、別の層が審査する**
  - **DPC の位相的 feasibility 保証 (10332)** — 学習ポリシーに**確率的でない決定論的な安全保証**を、実行時の安全フィルタ無しで与える。
    根拠は **DPC が白箱であること**で、著者自身が **RL や黒箱の近似 MPC では構造的に不可能**と明言。
    **これは R1 の存在理由をそのまま補強する** —— 我々が評価したい E2E の学習型 planner は黒箱側にあり、**そこには確率的保証しか置けない**
  - **実車統合 (12198)** — NN は挙動を**提案**し、最適化ベースの監督層が走行可能性と安全制約を**強制**。
    open-loop → closed-loop 統合 → 実車走行まで一本で報告(数値は無く、価値は統合の詳細)。落選した **11451**(neuro-symbolic safety guard)が
    シミュレーションの数値で**まったく同じ構造**を独立に主張しており、**同日2本 = 設計パターンとして定着したと見てよい**
  - **保証の3型(R1 の見取り図。ここが今週揃った)**

    | 型 | 保証の種類 | 要求すること | 使えるか(E2E 学習型 planner) |
    |---|---|---|---|
    | **conformal 型** | 確率的 (1-α) | 何も要求しない(黒箱でよい) | **使える**(R1 の主線) |
    | **DPC 型 (10332)** | 決定論的・厳密 | **planner が白箱の model-based であること** | 使えない(だから R1 が要る) |
    | **clustered smoothing 型 (12037)** | **モードの和集合に対する下界** | 黒箱でよい | **使える。多峰性を保ったまま保証を書く言語** |

  - **★ 空き地の存在証明(R1 の中心主張。今週4本が独立に空けた)**: **UnsDrive (09098) / DPC (10332) / 実車統合 (12198) /
    11451(落選)の4本が、いずれも安全層を提案しながら、その安全層が生む「過保守さ」を1つも測っていない。**
    **制約を破らないポリシーは、止まり続けることで自明に達成できる** —— この当たり前が誰にも測られていない
  - **占有格子に unknown を持つ: UnsDrive (09098)** — occupancy を occupied/free/**unknown** の3値にして
    「見ていないから分からない」が「空いている」に潰れるのを止め、**unknown に踏み込む軌道を scorer で罰する**。
    **このペナルティの強さは過保守さのつまみそのもの**で、振れば **「衝突率 vs 過保守さ」の曲線が1枚で出る**(R1 の中心 figure の下書き)。
    鉱山向け closed-loop simulator **MineLoop** も同時提案(**simulator の妥当性検証の節が手法の節より我々に価値がある可能性**)
- **最終スコア1つを中間構造に分解する(2026-W32)— 一律スカラーをやめる4方向**
  - **被害を「確率 × 深刻度」に分解**: **Failing Gracefully / FailBench (05313)** — 故障は必ず起きる前提に立ち、
    「誰と接触しうるか」の確率と「その相手にとってどれだけ酷いか」の深刻度を**別々に定量化**して planner の
    意思決定に入れる。一律の衝突率は**歩行者と路側構造物を同じ重みで潰している**。あわせて **MuJoCo ベースの
    故障注入基盤**を公開し、センサ異常・アクチュエータ故障を「たまに起きる事故」でなく**制御可能な実験変数**にした。
    **R1(過保守・介入頻度を保証付きで測る)の骨格そのもの** — 深刻度重み付き被害期待値は conformal の
    非適合度スコアにそのまま載る(家庭サービスロボット由来、指標の定式化のみ移植)
  - **成否の1ビットを中間マイルストーンに分解**: **ABSeeker (05102)** — 正解から逆算して「途中で掴んでいるべき
    だった手がかり」を復元し各ステップを採点。**失敗軌道にも部分点が入る**ので、現在の「衝突したか否か」を
    「必要な認知イベントをいくつ踏んだか」に置き換えれば**失敗走行同士に優劣が付く** /
    **AgentOPSD (05987)** — teacher/student の確率差を log-odds 空間で再帰更新し **信念の変化量が大きい turn** を
    pivotal と判定。**衝突の 0.5 秒前(手遅れ)でなく 5 秒前の車線選択(真の分岐点)**を指せる可能性
    (fm-distillation サーベイと相互参照。運転では「1 turn とは何か」の設計が最初の壁)
  - **予測失敗を「予期ミス / 反応ミス」に分解**: **INTraJ (05673)** — social influence を **planning 段階
    (他者の未来から reference trajectory を作る)と reaction 段階(full-context 予測との残差)**に明示分解。
    予測が外れた時に**大枠の予期を間違えたのか局所反応の見積もりを外したのか**を切り分けられる。
    FDE と long-horizon 一貫性で効く = **planner が効く 3〜8 秒先**の改善を ADE 中心の評価は見落とす。Argoverse 2
  - **性能を「計算予算あたりの性能」に分解**: **Adaptive-WAM (06008)** — NAVSIM PDMS と **end-to-end latency
    (170ms)を同じ表で報告**。我々の評価は精度に偏っており、**latency 予算を固定した PDMS** を常設指標に足すべき。
    trajectory-quality scorer は軌道単位の信頼度を出すので conformal の非適合度スコア候補
    (vla-world-model / fast-generative-inference サーベイと相互参照)
- **評価の入力側を「再帰的に難化」させる(2026-W32 新設)— 飽和ベンチへの回答**
  - **RST (05466)** — 検証済み seed から **(instruction, environment, reference solution, verifier) の4点を
    整合させたまま再帰的に難化**。肝は「作ってから検証」ではなく **「検証を通ったものだけが次の種になる」**。

    **(シナリオ, 参照走行, 評価器) の三点セットを自動難化**するパイプライン。ただしターミナルは決定的で
    verifier が書きやすいという圧倒的に有利な条件があり、**連続・確率的・多目的な運転で verifier をどう追従させるかが

## Open Questions
- **★ 衝突の何秒前に solvability が落ち始めるか**(01799 × 02688)— **時間差が出れば、R1 の proactive という主張が図1枚で立つ。
  出なければ主張を弱める判断材料になる。**集約スコアを同じ図に重ねるだけで、**新しい計算は要らない。どちらでも決着する**
- **★ 生存本数 (離散) と 境界余裕の最小値 (連続) は、どちらが衝突の手前で先に落ちるか**(03602)—
  **これがそのまま R1 の指標選択の根拠になる。**罰則項の定義は論文から流用でき、**図1に相乗りで 30分**
- **★ solvability の順位は、候補の張り方を変えても保たれるか**(01799 × 04070)— **摂動の段数 K を振る (最小のチェック) →
  幾何摂動と行動潜在摂動で比べる (10月)。K 依存で順位が入れ替わるなら、生存本数ではなく生存率へ正規化する必要がある。**
  **PDT の family-level robustness に相当し、先に済ませておけば 10月の実データで作り直さずに済む**
- **★ minimum meaningful effect をいくつに宣言するか**(02688)— **図を作る前に決めること。後から決めれば、
  432 設定で再現ゲート通過ゼロという結果を出した論文と同じ穴に落ちる。紙・30分で、10月の実データにそのまま使える定数になる**
- **★ `support-versus-selection regret` は、正解軌跡なしで計算できるか**(02688)— **できるなら R1 の「事後 vs 事前」という差分は消える。
  消えるなら新規性は指標そのものではなく保証の付け方に移る。10月の実験を組む前に判定すべき分岐**
- **★ 集約スコアが同点なのに solvability が割れる場面ペアは、実際に何組あるか**(02885 × 03602)—
  **ペアが1組も無ければ solvability は集約スコアの関数でしかない。早く知るほど良い最悪の結果である。**
  10月の設計は1行で書ける: **NAVSIM v2 で EPDMS の差 < 0.5 の場面だけを抜き、その部分集合で solvability の分布を比べる**
  (同点ペアの供給源として **StyleDrive の multi-style (再学習なしで慎重/機敏を出し分ける)** が使える。実データを漁って偶然の同点を探すより速い)
- **★ 情報チャネルを1つずつ剥がしたとき、自分の評価指標のスコアはどれだけ落ちるか**(31029)—
  他車位置 / 他車速度 / 信号状態 / 自車の過去軌跡 / 地図。**並べれば「その指標が実際に何を要求しているか」のプロファイルになる。紙1枚 + 既存ログ**
- **★ 遮蔽区間で solvability を「見える範囲のみ」と「裏を最悪ケースで埋める」の2通りで計算すると、差はいつ立ち上がるか**(30692)—
  **主張は「集約指標はこの2条件を区別しないが、solvability の差は遮蔽の入りと同時に立ち上がる」。
  R1 の「起きなかったことで測る」が最も鮮明になる条件である**
- **★ engine のチェック (collision / kinematic feasibility / drivable area / 信号遵守 / TTC) が全部 pass しているのに人間が介入したケースは何件あるか**(25518)—
  **ゼロに近ければ「評価は engine のチェックで尽きる」= 人手なしで完全自動判定できるという強い主張。
  まとまった数が出れば、そこが engine では測れない領域であり、その中身の分類 (過保守か、チェック漏れか) がそのまま R1 の貢献になる。どちらでも1つ確定する**
- **solvability を集計するとき、平均は決定的な数秒を薄めていないか**(00161)— **大半の時間は「逃げ道が十分ある」状態のはずである。
  IMPACT が学習側で踏んだ罠を、指標の集計側で踏みうる。平均を出す前に分布を見ること**
- **自分の指標の各項目は、抜け穴 (別経路で稼げる) と 欠落 (項が無い) のどちらか**(30819)—
  **この2列が埋まらない指標を「保証付き」と呼ぶことはできない。紙・1時間・前提条件ゼロ**
