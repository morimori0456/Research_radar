## 課題カード (3枚)

### 課題: 運行時間・天候・地域の拡大が「暗所の小さな物体」のような希少クラスで律速されているのに、その検出が十分かを数字で言える人がいない

- **誰が困っているか / 深刻度**: Robotaxi 事業者 (Tesla は 1 時間刻みで拡大中・事実) と、夜間に同じ道を走る歩行者・ペット・自転車。夜は 1 日の約半分の需要帯なので、ODD (Operational Design Domain: 自動運転が動作を許される条件の範囲) が昼に限られると稼働率と収益に直結する (推測)。
- **なぜ未解決か**: 希少クラス × 低照度の組合せは実走行でほとんど遭遇しない。「見落としが 1 件もなかった」ことは母数が小さいと安全の証拠にならない (推測)。評価の側にも、条件 (照度・路面色) ごとの recall を信頼区間つきで出す慣行がない (推測)。
- **既存プレイヤーとその限界**: 各社は fleet で自社ログを積み、シミュレーションで条件を水増しする。ただし公開されるのは「運行時間を延ばした」という結果で、根拠の数字は出ない (事実: 今週の発表の形)。NHTSA は 2025 年から Tesla に低視程での挙動を問い合わせている (検索結果の記述。時期は未確認)。
- **対象者の技術との接続**: **P1 (planner 評価) と P3 (VLA)。** 「この条件でこの物体に対し、planner は何 % の確率で制動するか」を信頼区間つきで出す評価は、closed-loop 評価の一種である。E2E (End-to-End: 入力から操作まで 1 つのモデル) では perception と planning の境目がなく、検出 recall だけでは足りない点が研究課題になる (推測)。
- **最初の一歩 (1週末)**: nuScenes (公開の運転データセット) の annotation で、**夜間シーンの animal / 小型 obstacle クラスの件数を数え、昼との比を出す。** 件数が数十未満なら、「公開データでは夜間の希少クラスを統計的に評価できない」こと自体が主張になる。半日。

### 課題: teleop (遠隔操作) 主体で売り始めたロボットが、顧客に「自律で肩代わりできる割合」を約束できない

- **誰が困っているか / 深刻度**: 危険環境 (洋上・高圧電力・爆発物処理) の事業者と、その顧客。危険作業は人を離す価値が大きい反面、失敗の損害も大きい (推測)。Minerva は操作者が VR で細かい manipulation を行い、AI は balance・転倒回復・移動を担うと説明している (事実)。
- **なぜ未解決か**: 「半自律」は操作者の介入の頻度と、介入の種類 (緊急か、微調整か) で意味が全く変わるが、共通の指標がない (推測)。危険環境の電子機器には防爆認証が要るが、学習ベースの制御ソフトに対する認証の考え方は未整備とみられる (推測。要確認)。
- **既存プレイヤーとその限界**: 爆発物処理や点検の遠隔ロボット (非 humanoid) は既にあるが、完全な人手操作が前提。Humanoid 各社は「自律」を売り文句にし、介入率を開示しない (推測。W37 の「自律度を開示する規格が存在しない」カードと同じ型)。
- **対象者の技術との接続**: **P3 (VLA) と P1 (評価)。** 「操作者の行動のうち、学習済み方策が代わりに出せる部分の割合」は、方策と操作者の行動の乖離を測る問題で、評価指標の設計そのもの。
- **最初の一歩 (1週末)**: LeRobot の公開データセットを 1 つ選び、**小さな BC 方策を学習して、各 timestep で方策の行動が操作者の行動から ε 以内に収まる割合を、ε を変えて曲線にする。** これが autonomy fraction の最小実装になる。Jetson で回る規模 (推測)。

### 課題: robot 開発の土台になる OSS (MoveIt など) の保守を担う少数の会社が買収される — 依存する側にその影響を測る手段がない (仮説・要検証)

- **誰が困っているか / 深刻度**: MoveIt (ROS 上の motion planning ライブラリ) に依存する robotics 企業・研究室。PickNik が Qualcomm に買収された (事実: 上記の集計 1 件のみ。一次ソース未確認) とき、保守の優先順位が変わる可能性がある (推測)。規模は粗い見積もりもなく不明。
- **なぜ未解決か**: OSS の保守は少人数の会社の持ち出しになりやすく、依存する側は寄付以外の関与手段がない (推測)。依存先の「bus factor (その人が抜けると止まる度合い)」を定期的に測る人もいない (推測)。
- **既存プレイヤーとその限界**: Open Robotics / OSRF が ROS 本体を担うが、個別パッケージの保守体制までは保証しない (推測)。
- **対象者の技術との接続**: **planning との接続は直接的 (MoveIt は planner の実装基盤の 1 つ)。** ただし課題としての深さは 3 枚で最も浅く、「世の中の課題」として成立するかは未検証。
- **最初の一歩 (1週末)**: **GitHub API で MoveIt の直近 12 か月の commit を取り、author の所属 (email domain) 別の割合を表にする。** PickNik 所属の割合が高ければ仮説は成立、低ければこのカードは捨てる。W40 の fork 表と同じ手法で、半日。
